## REMOVED Requirements

### Requirement: Upgrade from the latest published template is proven

**Reason**: Its fixture replacement scenarios require RC1–RC4 transitions. The accepted support floor for this candidate is RC5 on adoption of the proposed ADR.

**Migration**: Replace this requirement with the supported-origin fixture contract below. Carry forward the immutable provenance, ownership, conflict, recovery and idempotence guarantees.

## ADDED Requirements

### Requirement: The packed CLI upgrades the supported published template

The repository SHALL keep fixtures holding the exact default and `--cloudflare` projects generated by the generator of the latest published release (for the 1.0.0 release, `create-lace@0.1.0-rc5`, template `0.50.0`), recording that package's published digests and source revision, and a test SHALL verify each retained fixture's manifest version, provenance and managed-file digests without naming a template version in the test. Fixtures of earlier templates SHALL NOT be kept once a later published template has fixtures. Acceptance SHALL materialize each fixture, add a user README and user edits to `lace.config.ts` and a `site/` source file, generate the current template with the same options, and upgrade with the packed CLI:

- a modified managed file SHALL be reported as a conflict, and apply SHALL fail without changing any project file other than its conflict-review and recovery records under `.lace/`;
- after the operator restores that file, the plan SHALL have no conflict, apply SHALL make every changed or new managed file equal the current template, record the current template version, and leave the README, `lace.config.ts` and all `site/` files byte-for-byte unchanged without adding files under `site/`;
- a following plan SHALL report no changes.

Each fixture SHALL be generated from the actual immutable published package
with recorded source revision, archive hash and registry integrity, never
reconstructed from the current workspace. Generic upgrade conflict,
user-file preservation, digest-tampering, recovery, idempotence and
image-identity tests SHALL remain when fixtures are replaced.
An independent synthetic upgrade test SHALL verify that an unmodified retired
managed file is removed. For RC5 the retired managed storage Dockerfile SHALL also be verified in the actual upgrade, including conflict refusal on an edited copy.

#### Scenario: Published-template project upgrade
- **WHEN** a project on the latest published template with user edits is upgraded to the current template
- **THEN** managed infrastructure is current and the user's README, configuration and site source are unchanged

#### Scenario: Modified managed infrastructure
- **WHEN** a managed file of the published-template project was edited by the operator
- **THEN** the upgrade reports the conflict and apply writes nothing

#### Scenario: Fixture integrity
- **WHEN** a retained fixture's managed file bytes no longer match the digests in its recorded manifest
- **THEN** the fixture test fails naming the fixture and file

#### Scenario: The supported origin replaces superseded fixtures

- **WHEN** the release fixture suite runs for 1.0.0
- **THEN** exactly the two authenticated RC5 variants supply its prerelease projects, and stale or additional prerelease template directories fail fixture verification

### Requirement: The executable upgrade suite covers the supported release floor

The repository SHALL retain release-specific migration coverage only for supported origins. For 1.0.0 its only prerelease origin SHALL be RC5. Superseded projects, seeded databases, block conversions, release-specific assertions, runners, snapshot expectations and CI jobs for migrations from earlier releases SHALL be removed or rewritten to cover current behavior. Generic ownership, journal recovery, unknown ledger refusal, migration idempotence, content synchronization and fresh-install coverage SHALL remain executable.

#### Scenario: Reviewing release migration coverage

- **WHEN** the checked-in tests, fixtures, assertions, acceptance entry points and CI jobs are inventoried
- **THEN** every release-specific migration starts at RC5, every retained generic case has a current behavioral assertion, and no runner provisions an older origin, even as a skipped test
