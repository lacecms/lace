## Decisions

1. **One stable set after EX7A.** Choose `1.0.0` for the 16 public npm packages (including the generator), runtime version, registry requirements and both GHCR images. Use `0.52.0` as the next independent template revision after the working-tree `0.51.0`. Keep the existing release-definition path so consumers of saved inventories and docs tooling can use the same model. Check registry coordinates read-only at selection. A conflict or intervening publication requires revisiting the candidate/origin evidence. RC6 publication is unnecessary.
2. **Keep the SQL chain.** A new 1.0 baseline would require translating Drizzle timestamps and Wrangler filename histories, introduce another failure point, and bring no data benefit here. Apply the existing five pending migrations. The post-RC5 SQL backfills actor profiles, adds an invitation index, installs preview state and fences, and classifies existing entry links as `url`. Verify fresh and upgraded databases against the same current constraints, indexes and triggers. The ledger identifies schema state. Several releases can share one state, so support is determined from the project's release and template as well. Avoid adding historical engine detectors to the migrators.
3. **Retire executable compatibility work below RC5.** Replace RC4 fixtures with genuine RC5 generator outputs. Remove the built-in gallery v5→v6 transform and its release-specific tests once RC5 synchronization is the documented precondition. Migration functions are runtime-only metadata. Keep gallery version 6, renderer behavior and structural hashes stable. Preserve generic block migration, conflict, journal, missing-step, unknown-ledger, fresh schema and retry tests with synthetic inputs. Verify current index behavior on RC5/fresh databases and drop tests that replay `0000`→`0001` as a supported upgrade. An immutable publication record or a generic current-feature check with an old sample name is not a migration journey.
4. **Stable distribution through existing entry points.** Use the saved inventory's validated version/channel pair consistently in preparation, npm publish/resume, remote verification, GitHub drafts/finalization and cleanup. Stable uses npm `latest` and a regular latest GitHub release. Prerelease operations retain `next` and GitHub prerelease behavior. Images use exact immutable version/platform references. Preserve matching-artifact retries, conflict refusal and exact-byte verification independently of mutable channels. On retry, report a dist-tag already advanced to a later release before moving it backwards.
5. **Document the 1.x contract.** Treat the public config API, REST `/api/v1`, SDK and build-export format 2 under architecture §22 as the compatibility boundaries. Keep config, export and block versions independent of the marketing version. Document EX4D changes for custom REST clients (ETags/preconditions, protected cursor lists), the site package updates for SDK/Astro and block source adoption. Require matching 1.0 packages/images at cutover. Continue forward migrations within the stable line and use architecture §22 for future breaking public-contract changes.
6. **Separate release evidence from approval.** Finish EX7A's toolchain qualification first. The RC5 stabilization change still has an unchecked receipt task although RC5 is recorded as published. Reconcile it against its own historical evidence in its own workflow. Do not use either change's receipts for 1.0. Qualify the clean stable inventory locally and stage those exact bytes on the existing real-VPS and real-Cloudflare owner checklist in `docs/verification.md`. Record explicit owner approval before exposing stable on npm. Subsequent registry publication, GitHub finalization and cleanup each retain their existing explicit action.

## Migration Plan

1. Identify the site's RC5 engine, template, site mode/path, installed block hashes, runtime, storage and deployment overrides. Finish pending RC5 DB migration and review/synchronize its content configuration on a private copy first, including pending block steps. Record a signed-in user, draft and published revisions, gallery, public route, original media checksums and served build. Verify a restorable coordinated backup before changes to the live installation.
2. Generate the same site mode, path and Cloudflare option using the target generator. Run the packed 1.0 CLI upgrade plan against the RC5 project. Resolve each edited managed-file conflict and review the plan again. Keep site source, config, ignored environment and operator Wrangler settings under their existing ownership. With writers quiesced, apply the reviewed managed changes, align user-owned site dependencies/lockfile, image overrides and installed block sources using the documented operator commands. Keep preview off unless explicitly configured.
3. **Node.** Pause ingress writes and dispatch/builds. Capture SQLite consistently (including WAL if using a file snapshot), stopped storage volume with metadata, image identity and previous served site. Keep the Compose project, bucket, credentials and volume identity. Follow the generated SILO procedure on a copy, verify old and new media checksums after restart, and retain the old image. Run the explicit migration with conflicting services stopped, sync reviewed configuration and rebuild. RC5 already has the private production API and loopback ingress. Carry forward operator overrides.
4. **Cloudflare.** Quiesce writes and scheduled work, capture D1 and R2 together, record Worker, bindings and Pages/site revisions. Rehearse with an isolated restored database/bucket. Use the documented explicit local/remote target, migrate D1 through its own ledger, deploy the matching Worker/admin/site graph, sync and verify the build and object readback before resuming. Keep credentials and backups outside the release receipt.
5. Verify the `1.0.0` status, original sign-in, draft vs published content, gallery, link destinations, media bytes and successful rebuilt site. Re-run migration and template planning. On failure keep maintenance active and previous static output serving. Restore matched RC5 files/packages/images or Worker, config, DB, object store and served site to the same recovery point, verify original reads and sign-in, then reopen. The filesystem journal covers its managed writes only.

## Risks / Trade-offs

- **Unsynchronized RC5 content or edited templates.** A deployed version alone does not prove the stored block shape or managed-file hashes. Rehearse from a private copy and resolve discrepancies while RC5 and its backup are available. If this site's supported upgrade cannot preserve its data, record the failed comparison and revisit the plan with the owner before contemplating a clean install.
- **Qualification cost.** The ordinary fixture journey checks file bytes but seeds dummy local data. A populated upgrade using the packed artifacts on both targets is a separate gate. Record the actual architecture running each consumer journey and both image smoke platforms.
- **Partial release.** npm publishes packages individually. Publish in dependency order, verify the selected artifacts and channel, and finalize GitHub only after both registries are complete. A failed attempt retains the inventory for retry. Changed shipping bytes require fresh preparation and acceptance.
