## Context

The published [v1.0.0](https://github.com/lacecms/lace/releases/tag/v1.0.0) identifies source revision `357ebbbc8d2eb73acf164ae62db40647dce2a046` and template `0.52.0`. The branch still selects those version coordinates. Its checked-in SQLite/D1 migration files and built-in block definitions match the published source. Its new thumbnail operation is a required member of the exported `LaceClient` interface, so existing structural implementations fail type checking. The current release acceptance and its receipt validator have a specific RC5-to-1.0.0 path.

## Goals / Non-Goals

**Goals**

- Use the ordinary packed generator, CLI, runtime images and Worker for both upgrade journeys. Keep disposable qualification separate from real deploys and publication.
- Make the public SDK contract compatible at the declaration entry point and prove the existing HTTP/build-export path with the released SDK.

**Non-Goals**

- A new schema revision, bulk thumbnail backfill, object-store relocation, direct RC5-to-1.1.0 qualification or automatic edits to operator-owned configuration.
- New dependencies, a new release workflow, or a redesign of the thumbnail transport.

## Decisions

1. **Record the published baseline.** Reconcile the 1.0.0 publication ledger and active roadmap against the actual npm, GHCR and GitHub identities before selecting `1.1.0`. Verify source and generator archive integrity, package coordinates and both image indexes read-only. Record those identities and verify unused target coordinates. Old source, receipts and the RC5-to-1.0.0 procedure stay attributable to 1.0.0. The prior OpenSpec change carries unsynchronized deltas for shared requirements. Reconcile both sets in release order before synchronizing the 1.1.0 deltas, with archival handled in its separate workflow. This preserves the accepted history while the current release guidance advances. Select the stable package and runtime set together and advance the independent template version to `0.53.0`.
2. **Keep `LaceClient` at its released shape.** Define a thumbnail-capable SDK client interface extending `LaceClient` and return it from `createLaceClient()`. Keep thumbnail option/result exports and use the expanded type only for the factory-created client in the published-site loader. Its media URL client can continue to use the base type. An optional member on the original interface would preserve basic assignment but would still change `keyof LaceClient` and require factory consumers to narrow the method. The extended return keeps both the base shape and a directly callable new API. Compile a class or equivalent custom implementation and a typed object mock authored against `1.0.0`, using the same source against both packed declarations. Check the full released member set, factory assignment and typed thumbnail call. Use the released 1.0.0 SDK for published reads and conditional export against the candidate API. Keep the existing rule that operators deploy the matching or newer minor API before upgrading the site's SDK.
3. **Start with real 1.0.0 projects.** Advance `release/upgrade-origin.json` and the active template fixtures to the published default and `--cloudflare` 0.52.0 outputs, with the generator's source and digests. Store no populated database or secret as a fixture. Use the old packaged CLI/API and old image or Worker package to initialize a disposable persistent SQLite/SILO or D1/R2 project and create representative state through the public operations. Include an original credentialed user and role, distinct draft and published content, v6 gallery, URL and typed entry references, media and durable build work. Reuse the cutover harness's state, output and restore probes. The old RC5-specific storage switch, five-migration and backfill assertions apply to historical 1.0.0 evidence. For the current path, use the same existing store and bucket and assert both ledger and schema are unchanged. Fresh install and synthetic refusal and conflict tests retain independent coverage.
4. **Verify the data before resuming writes.** Pause mutation and dispatch, save a coordinated backup, and record baseline identities and checksums. Use ordinary packed CLI commands and existing template plan/apply paths. Run the explicit migration command twice against each upgraded store and compare ledgers and schema after each run. Derive the applied count from the ledger because the CLI reports installed entries. Preserve pending work for comparison before dispatch resumes. Verify sign-in, authorization, draft/public reads and original objects after restart. Rebuild and serve the site, then exercise lazy derivatives with a local Images binding test double and confirm a Worker without the binding still serves originals. Restore the original packages, images or Worker, project config, database, media and served output to an isolated target and probe the recovered 1.0.0. Compare expected semantic output after upgrade and exact saved output after restore so intentional thumbnail markup adds no false mismatch.
5. **Bind both outcomes to exact release inputs.** Extend `acceptance:release` and `scripts/release-evidence.mjs` to require SQLite and local D1 upgrade and restore results when validating a 1.1.0 receipt. Record verified origin identities, candidate inventory identity, zero applied migrations and sanitized state/media/build and restore checks. Verify old receipt formats still qualify their own historical inventories, and reject missing runtime evidence, wrong origin, altered digests or unexpected migration counts for 1.1.0. The handoff names tested platforms and differentiates repeatable local D1/R2 checks from owner-operated staging on remote D1/R2, including the real Images binding, and on a real VPS.

## Risks / Trade-offs

- A generated project can have local edits. Prove byte preservation of user-owned files and keep the existing conflict and recovery path for edited managed guides.
- Thumbnail or cache changes can legitimately alter the rebuilt markup. Verify original bytes, authored state and meaningful published content separately from the new thumbnail behavior.
- The candidate could appear qualified with only a fresh install or an earlier receipt. Tie success to both populated trajectories and their restores, and check inventory and origin identities before trusting the receipt.

## Migration Plan

1. Identify the installation as fully migrated and synchronized 1.0.0 with template `0.52.0`. For an RC5 installation, follow the published 1.0.0 upgrade first. With writers and dispatch paused, back up project files, configuration and secrets securely, SQLite or D1, SILO or R2 originals, and the currently served output together.
2. Plan and apply the managed `0.53.0` update, resolve conflicts, and adopt matching 1.1.0 packages and images or Worker. Preserve the existing storage configuration. Run the normal explicit database migration step and expect zero pending migrations. Check configuration synchronization, then start or redeploy the matched runtime and verify existing credentials, content and originals.
3. On Cloudflare, optionally configure the `IMAGES` binding in `worker/wrangler.jsonc` and redeploy. After the CMS is ready, update the site's SDK and Astro adapter together and rebuild. Reopen writes after verifying the new served output and data.
4. On failed cutover, retain the last healthy static output and restore the coordinated 1.0.0 artifact, configuration, database, media and site backup. Verify restored reads, login and original bytes before reopening traffic. The CLI's template rollback covers its managed file operations. The recovery drill covers the full deployment.
