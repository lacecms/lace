## Why

rc2 (`0.1.0-rc2`, template `0.47.0`) is published, yet the repository still
treats rc1 as the oldest supported release: the upgrade fixtures, the
generated upgrade instructions, the operations guide, the public documentation
and the compatibility guide all describe the rc1 → current path, including a
database recreation that no rc2 installation needs. The owner decided
(2026-11-10) that rc2 is the oldest supported release, so later changes migrate
from rc2 only and nothing is kept for rc1.

This is the first of the owner-inserted feature changes after RF6, recorded in
[`docs/refactoring-roadmap.md`](../../../docs/refactoring-roadmap.md) under
"Owner-inserted feature changes after RF6". It is not an RF session and selects
no release.

## What Changes

- **BREAKING (support policy):** `0.1.0-rc2` becomes the oldest supported
  release. rc1 installations are no longer described or proven; their
  pre-baseline databases are still refused with `SCHEMA_UNSUPPORTED`.
- Replace the rc1 upgrade fixtures `tests/fixtures/template-0.46.0/` with
  `tests/fixtures/template-0.47.0/{default,cloudflare}.json`, generated by the
  published `create-lace@0.1.0-rc2` with recorded provenance.
- Advance the ownership template to `0.48.0`. Its upgrade instructions describe
  only the rc2 (`0.47.0`) → `0.48.0` steps: no database recreation, forward
  migrations through `lace db migrate`, configuration sync and rebuild.
- Replace "Database baseline and upgrading from rc1" in the generated
  operations guide, "Upgrading from rc1" in `docs/compatibility.md` and the
  rc1 upgrade paragraph of the public operations page with rc2-based guidance.
- Add ADR 0030 "rc2 is the oldest supported release", which supersedes the
  support-boundary decision of ADR 0029 while keeping its baseline migration
  and built-in block decisions. Update architecture §22.
- Update internal documents that point at rc1 as the oldest release
  (`docs/alpha-release.md`, `docs/personal-site-guide.md`, `docs/README.md`,
  ADR index).

Non-goals:

- No change to the upgrade, migration or block-migration mechanisms, the
  baseline migration, `publishedVersions` or release coordinates
  (`release/alpha.json` keeps describing published rc2).
- No release preparation; `pnpm release:check` keeps reporting the template
  identity mismatch until the owner selects the next candidate.
- No renaming of rc1-named acceptance journeys and test data
  (`scripts/journeys/*rc1*`); they are labels, not support claims.
- Changelog and `docs/architecture/history.md` keep their history.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `generated-project-acceptance`: the retained published-template fixtures come
  from rc2 (`create-lace@0.1.0-rc2`, template `0.47.0`).
- `project-generator`: upgrade instructions describe the rc2 → current steps
  without database recreation; delivered guides describe nothing older than
  rc2.
- `public-documentation`: upgrade guidance starts at rc2 and describes the
  rc2 → current upgrade instead of the rc1 database recreation.
