## Context

See the proposal. `bin.ts` currently branches by command and six modules parse their own flags. The operator parser permits flags interspersed with command words; other commands have their own positional and validation rules. Help is special-cased only for the exact top-level or command help invocation. Several parser functions are directly imported by tests. The CLI centralizes sanitized diagnostics, but import and upgrade have their own result handling and Cloudflare dependencies are lazy.

The Cloudflare wrapper currently owns its target grammar, local state defaults and remote confirmation; `dev:cloudflare` separately invokes its local migration helper. Compose sync currently executes inside the API container, where the selected database is mounted. The two Node/library base configs are identical; the browser base is also consumed by packages other than auth, mcp and server.

## Goals / Non-Goals

**Goals:** One dispatch table and reusable token parsing, preserving command-specific semantics and existing safety boundaries; wrappers delegate actual operator work to the CLI; shared compiler configuration remains equivalent.

**Non-Goals:** Changing the CLI grammar, error or success contract, remote authorization policy, database algorithms, or package layout. This session does not remove unrelated development helpers or move files into RF7C directories.

## Decisions

1. Define command entries with name, usage, parse and run; dispatch through the table, matching multiword names and preserving current interspersed operator flags. `parseFlags(argv, spec)` handles common flag tokenization, repeated options, `--json` and exact help handling; each command retains explicit validation of positionals, values, defaults and mutually exclusive flags. Keep public/tested parser entry points as thin adapters where needed. Capture baseline behavior first, including help with additional flags, unknown commands, duplicate options and missing values. Avoid a generic parser that silently normalizes formerly distinct edge cases or changes stream/exit behavior. Preserve error formatting, raw-argv JSON selection for parse failures, operation identification, and lazy imports.
2. Keep the Cloudflare wrapper's existing `--local`/`--remote` and `--persist-to` interface and confirmation, but delegate migration to `node packages/cli/dist/bin.js db migrate` with an explicitly mapped Cloudflare target and selected settings. Eliminate its separate argv parser from `cloudflare-lib.mjs`; place minimal wrapper translation at the boundary without creating another migration implementation. Resolve the same configured DB identity, Wrangler config and local persisted state; never select a different remote database. Keep placeholder rejection, noninteractive refusal outside CI and exact-name confirmation before delegation. The ordinary public `lace db migrate --target cloudflare-remote` contract continues to require account, database and API credentials. For this repository wrapper only, use an explicit private CLI entry path with the already-confirmed Wrangler config and database identity; do not infer it from missing credentials or make it a fallback for public commands. The private path reads the remote migration ledger through the project-pinned Wrangler using its existing OAuth or token authentication, validates the structured result, and applies migrations only after the same baseline check. Recognize only the known missing-ledger signature as a fresh database; authorization errors, failed commands and malformed or ambiguous output fail closed with sanitized diagnostics. Reject an unknown migration with `SCHEMA_UNSUPPORTED` and exit 5 before any write; query installed versions after a successful apply. Never print raw Wrangler output or credentials. Test that the ledger query and apply use the same verified config and DB binding. This preserves the wrapper's established authentication while the public CLI keeps its explicit-credential contract; requiring a new token in the wrapper or bypassing the baseline check would change existing guarantees. Keep the dev startup migration path independent unless separately routed safely; verify its behavior.
3. Compose sync must run the built CLI **inside the same API container**, with `content sync --target node` and optional `--check`, so the selected database, configuration and Compose safety guard see the correct environment. Ensure its image contains the built CLI and dependencies; preserve wrapper validation, exit propagation, running-service expectations and read-only check. Do not run host CLI against the mounted live database. Leave acceptance stack synchronization alone unless required for the image build.
4. Replace the identical `tsconfig.library.json` and `tsconfig.node.json` with one base and update all references including root and app configs. Rename `tsconfig.browser.json` to `tsconfig.web.json`, update every consumer, and document that DOM libraries provide fetch types rather than an entitlement to browser APIs. Remove CLI lib overrides only if effective compile settings remain valid; run root typecheck to expose hidden dependencies. Reject retaining aliases, which would preserve duplicate configuration.

## Risks / Trade-offs

- [Parser changes alter edge cases or leakage] → snapshot each exact help invocation and exercise valid/invalid, duplicate, JSON and secret-sentinel cases across all command families; preserve existing output and errors.
- [Wrangler output or authentication cannot be trusted] → require structured, unambiguous results, fail closed on authorization and malformed output, and test sanitized failures and unknown ledger entries before mutation.
- [Wrapper selects the wrong database or changes confirmation] → test invocation translation, state paths and confirmation without contacting remote infrastructure, then exercise isolated local D1 and CI-safe mocked remote paths. No credentials or subprocess text in diagnostics.
- [Container lacks CLI build or its dependencies] → inspect the built API image and run the real Compose sync and check on isolated development data; preserve failure codes and avoid host database access.
- [Type config rename breaks a less obvious consumer] → search all references and run root typecheck, boundary and formatting checks.

## Migration Plan

No data or deployment migration. Land configs, parser/table and wrappers together; build the CLI before wrappers execute. Existing project data and generated consumer commands are untouched. Reverting the change restores previous scripts and configurations; no database rollback is needed.
