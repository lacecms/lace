## MODIFIED Requirements

### Requirement: Upgrade from the published alpha template is proven

The repository SHALL keep fixtures holding the exact default and `--cloudflare` projects generated by the generator of the latest published prerelease (today `create-lace@0.1.0-alpha.7`, template `0.35.0`), recording that package's published digests and source revision, and a test SHALL verify each retained fixture's manifest version, provenance and managed-file digests without naming a template version in the test. Fixtures of earlier templates SHALL NOT be kept once a later published template has fixtures. Acceptance SHALL materialize each fixture, add a user README and user edits to `lace.config.ts` and a `site/` source file, generate the current template with the same options, and upgrade with the packed CLI:

- a modified managed file SHALL be reported as a conflict, and apply SHALL fail without changing any project file other than its conflict-review and recovery records under `.lace/`;
- after the operator restores that file, the plan SHALL have no conflict, apply SHALL make every changed or new managed file equal the current template, remove a retired managed file that was unmodified, record the current template version, and leave the README, `lace.config.ts` and all `site/` files byte-for-byte unchanged without adding files under `site/`;
- a following plan SHALL report no changes.

#### Scenario: Alpha project upgrade
- **WHEN** a project on the latest published prerelease template with user edits is upgraded to the current template
- **THEN** managed infrastructure is current and the user's README, configuration and site source are unchanged

#### Scenario: Modified managed infrastructure
- **WHEN** a managed file of the published-template project was edited by the operator
- **THEN** the upgrade reports the conflict and apply writes nothing

#### Scenario: Fixture integrity
- **WHEN** a retained fixture's managed file bytes no longer match the digests in its recorded manifest
- **THEN** the fixture test fails naming the fixture and file

### Requirement: Scenario links and current-template upgrade remain verifiable
Focused generated-contract verification SHALL check scenario file presence, local links/anchors, command scripts and ordered lifecycle sequences for every site mode with and without Cloudflare. Current packed-consumer acceptance SHALL use the development guide's reviewed command sequence. Retained published-template fixtures SHALL keep their original managed bytes/hashes and origin evidence rather than be reconstructed from changed templates; upgrade verification SHALL cover default and Cloudflare consumers, edited user README/configuration/site source, managed documentation conflicts, new-guide path collisions, successful managed-guide delivery and a no-op repeat plan. Existing-site mode SHALL prove its outer README remains unchanged. These checks SHALL NOT require a real Cloudflare account.

#### Scenario: Guide command or local link drifts
- **WHEN** a scenario guide refers to an absent file, anchor or package script, or its setup sequence differs from the reviewed consumer sequence
- **THEN** the focused contract check or acceptance fails and identifies the guide and discrepancy

#### Scenario: 0.14.0 migration evidence
- **WHEN** the current packed CLI upgrades a retained exact published-template fixture (the `0.14.0` fixtures are no longer retained; the scenario applies to whichever published template's fixtures are kept)
- **THEN** guide delivery, conflict refusal, protected user bytes and a repeat no-op plan are verified against its recorded original manifest

**Reason**: The onboarding feedback log (alpha.1 field trial) is fully resolved; every regression it produced is a permanent stage of the acceptance suite, so a map from log items to stages no longer protects anything. The owner decided on 2026-11-01 that pre-release-era evidence files are not kept in the repository.
**Migration**: The regression journeys stay in `scripts/generated-project-acceptance.mjs` and its journey modules. The log and its map are removed from `docs/archive/step-32` in Session RF1B; git history retains them.

### Requirement: Alpha.2 field-trial feedback is traceable to evidence
**Reason**: Same as above for the alpha.2 field-trial log: every item is resolved or decided and its regression journeys are permanent acceptance stages; the owner-check items are recorded in the archived alpha release changes.
**Migration**: The field-trial regression journeys remain required by `prepublication-consumer-security`. The log and its map are removed from `docs/archive/step-33` in Session RF1B; git history retains them.
