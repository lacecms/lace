## Context

In `SqlContentReader`, `loadPublic`, `loadPublicGlobal`, `listPublic` and `listPublicRecords` select a route or model row first. Later statements fetch snapshot payloads, blocks and media. `snapshotIdsOf` includes both snapshot IDs, although `publicEntry` ultimately substitutes published content for the draft. A republish moves the published pointer and deletes the old snapshot and its children in the same write. A reader that crosses that commit can throw, silently omit media or return a page assembled from different states.

## Goals / Non-Goals

Give each ordinary response one database view and keep draft size out of public payload reads. Preserve the existing HTTP response mappers, kind eligibility, cursor encoding and ordering. The guarantee ends at the response boundary. The build export has a separate contract that detects version changes across pages. Published history retention, static artifacts and unrelated draft/admin reads are outside this change.

## Decisions

1. **Prepare all selects from request inputs.** Put the shared public selection and row assembly in the DB delivery area. Use the current path, global-key or collection-and-cursor predicates with bound parameters. For lists, select lightweight ordered candidate keys with the existing publication-time/entry-ID tie-breaker and a one-row lookahead. For payload queries reuse the same selection capped at the requested limit. Join snapshots, visible blocks, delivered link manifests and referenced active media by the selected published snapshot ID. Keep each child row separate to avoid multiplying blocks by media or repeating a large snapshot per block. Compute the next cursor from the last returned candidate when the lookahead exists. A single-resource lookup uses its existing predicate and a limit of one.
2. **Use one native atomic read.** All statements are known before the first SQL call, so submit them as one read group. On Node execute the group in a synchronous deferred SQLite read transaction. On D1 send one `database.batch` for the ordinary read. Reuse the native adapter code in `node-repository/sql.ts` and `repository/sql.ts`, factoring out single-group execution or omitting an empty follow-up in `readGroups`. The existing export uses two dependent groups and a version check on D1. Copying that pattern directly would allow an interleaving or expose an export-specific version conflict to anonymous callers. Retrying on a missing snapshot would also miss successful responses that silently lost media or blocks.
3. **Build the existing projection from published rows.** Reuse the snapshot and block decoders, public media and link visibility rules, and public DTO mappers. The internal `ContentEntry` shape requires a draft slot. Follow `buildExportPage` and fill it from the already loaded published snapshot before applying the public projection. Preserve SEO eligibility, block position, settings, conditional-field pruning and per-snapshot media ownership. The internal links manifest stays local to the selected source snapshot. Keep public read port signatures and packaged exports compatible. EX5A can supply model-kind policy independently.
4. **Make the race deterministic.** Seed distinguishable old and new fixture bodies, including reordered blocks, changed media IDs and link targets. For lists move the republished entry across the page boundary. Capture the stable old and new response, including the cursor. At the adapter read boundary let an independent writer publish after selection on the old implementation. With the fix, on file-backed SQLite exercise a writer commit after the first SELECT under WAL. On local D1 place the write just before the real atomic batch, and in a second run after it returns rows but before the reader assembles them. Assert the read used one native batch with no follow-up content query. Those two schedules test the possible D1 serial orders without pretending a writer can commit between statements of that batch. Run shared projection cases on in-memory SQLite as well.
5. **Measure data read at the SQL boundary.** Capture the baseline and corrected implementations against the same small publication paired first with a small draft and then with a large draft. Count returned SQL rows and UTF-8 bytes of selected text/JSON payloads before decoding. Report the counting method and D1's native `rows_read` separately. Exclude fixture writes and HTTP serialization. Inspect the selected snapshot IDs and child rows. The public result must be identical in the two draft-size runs, with zero draft payload in the corrected reader. Also check statement count and bind limits at the largest supported list page.

## Risks / Trade-offs

- Repeating the bounded candidate selector across native statements adds database work. Keep candidate columns narrow, inspect query plans and local D1 counters, and restrict child payloads to returned items. This avoids per-item SQL and a single oversized JSON row.
- Filtering out missing children or converting an invariant failure to 404 could hide corruption. A true absence uses the existing endpoint contract. Database and decoding errors retain their existing handling.
- Shared helpers also serve export and editorial reads. Keep the ordinary public read boundary local and run their existing tests when extracting shared SQL.

## Migration Plan

Ship this read-path change with the existing database schema and public API. Existing snapshots, routes and cursors can be read directly. Rollback requires no data rewrite.
