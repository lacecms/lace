## Context

See proposal.md for motivation and owner decisions. Current state:

- SM4B tests (`packages/cli/src/import-apply.test.mjs`, `import-plan.test.mjs`)
  call `runImportCommand` in process against `openImportApi`: Node runtime,
  stub image inspector, `InMemoryObjectStorage`, no rate limiter, an injected
  `fetch`. The bin dispatch, real `fetch`, real image inspection, MinIO/R2,
  D1 and rate limits were never exercised.
- The workspace cross-runtime suite (`vitest.cross-runtime.config.mjs`, run by
  `pnpm verify:34a` or directly; local only, not CI) opens each runtime with
  `openProductRuntime(kind)` in `tests/support/cross-runtime-fixture.mjs`:
  Node with a Docker MinIO container, or `createCloudflareWorker` over
  `openLocalCloudflare` (miniflare D1/R2), both behind one real HTTP listener
  on `http://127.0.0.1:<port>`, with an administrator, editor and viewer
  signed in. It imports the root `lace.config.ts` statically.
- The generated-project journeys run from packed tarballs:
  `nodeJourney` in `scripts/generated-project-acceptance.mjs` (Docker Compose,
  `acceptance:generated`/`acceptance:release`), `cloudflareConsumerJourney` in
  `scripts/cloudflare-consumer-acceptance.mjs` (`wrangler dev` of the generated
  `cf:dev`, `acceptance:cloudflare`), and `starterJourney` (`acceptance:starter`,
  the only one in CI).
- `lace import` loads `lace.config.ts` from its working directory, requires
  HTTPS except for loopback hosts, reads the token only from
  `LACE_IMPORT_TOKEN`, and uses exit codes 0, 2 (conflict), 4 (invalid,
  mismatch, settings) and 6 (unauthorized, rate limited, failed).
- Import tokens are created with `POST /api/v1/admin/import-tokens`
  (`{name, expiresInDays, allowPublish}`, session with `settings:manage`) and
  revoked with `DELETE /api/v1/admin/import-tokens/:tokenId`.
- Public docs pages live under `apps/docs/src/content/docs/en/latest/<section>/`
  with autogenerated sidebars; `apps/docs/public/` is served as is.

## Goals / Non-Goals

**Goals:** prove import on both real runtime compositions through the real
process boundary; prove the packed CLI in generated projects; one sample that
documentation, tests and journeys share so it cannot drift.

**Non-Goals:** extending the CLI, testing `429` against the real limiter
(unit-tested in SM4B with an injected clock; waiting a minute per run is not
worth it), interrupted-run resume on real runtimes (covered in SM4B),
browser-level admin checks of imported content.

## Decisions

### D1. One sample package, published by the docs site

The sample lives at `apps/docs/public/examples/content-import/`
(`lace-import.json`, `media/studio.jpg`, `media/workshop.jpg`). Both images are
original, generated for the sample (simple shapes, at most 50 KiB each, real
JPEGs with dimensions) so they pass real image inspection. It targets the
starter configuration (`packages/create-lace/templates/lace.config.ts`):

- media `studio` (alt, focal point, tags `sample`, `studio`) and `workshop`
  (caption, tag `sample`);
- global `settings` (`siteName`, `tagline`, `description`, `image` →
  `$media studio`);
- page `home` (hero, richText and gallery of both images; SEO title,
  description and image);
- posts `hello-lace` (`summary`, `relatedUrl` → `$entry first-project`, an
  image block) and `first-project`.

Block data uses each block's current version in the starter. Serving it from
`apps/docs/public` makes it downloadable from the docs site and keeps it a
declared public build input. The page shows `lace-import.json` in a fenced
block; a root test compares that block with the file.

Rejected: a sample under `docs/` (internal, not published), or inline JSON
only (tests and journeys would need generated images and could drift from the
guide).

### D2. Sample validity test in the root suite

`tests/content-import-sample.test.mjs` (root `pnpm test`, CI) runs
`node packages/cli/dist/bin.js import <sample> --validate-only --json` with a
working directory holding a copy of the starter `lace.config.ts` inside the
workspace (so `@lacecms/*` resolve), requires exit 0, and compares the guide's
JSON block with the file. `--validate-only` applies the Valibot format schema
that `lace-import.schema.json` is generated from (its drift test already
exists) plus the model rules, so no JSON Schema validator is added. Rejected:
adding `ajv` as a root dev dependency only to repeat the format check.

### D3. Workspace journey in the cross-runtime suite

`tests/content-import.acceptance.mjs`, added to
`vitest.cross-runtime.config.mjs`. `openProductRuntime` gains an optional
`config` (the loaded configuration object, default the root config) used for
runtime composition and synchronization; nothing else changes. The journey
copies the starter `lace.config.ts` into a temporary directory inside the
workspace (`tests/.import-journey-*`, removed afterwards), loads it for the
fixture, and runs the CLI there:

```
node packages/cli/dist/bin.js import <copy of sample> --url <origin> [...] --json
```

with `env = {PATH, LACE_IMPORT_TOKEN}` only (no inherited `LACE_*`). Steps per
runtime follow the spec. State snapshots for "nothing changed" are read with
the administrator's session: media list (ids, `version`), each imported
entry's draft revision and published revision, and build history. The rerun
without the state file deletes `<sample>/lace-import.state.json` first. The
conflict step saves a draft through `PUT /entries/:id/draft` with the session.

Canonical comparison across runtimes replaces IDs with package keys, drops
times, origins and revision-independent identifiers, and keeps order, values,
links (as `entry:<key>`), media dimensions and tags. The CLI's requests carry
no `cf-connecting-ip`, as a real command-line client behind `wrangler dev`
would not; Bearer import requests are rate limited per user.

Rejected: calling `runImportCommand` in process (misses bin dispatch, real
`fetch` and environment handling); a separate fixture for import (duplicates
the cleanup and signal handling of the 34A fixture).

### D4. Packed smoke in generated-project journeys

A helper module `scripts/import-smoke.mjs` exports
`importSampleSmoke({project, base, cookie, origin, run, readExport, sanitize})`:

1. `POST {base}api/v1/admin/import-tokens` with the session cookie and Origin
   (`{name: "Acceptance import", expiresInDays: 1, allowPublish: true}`).
2. Copy the sample from the workspace into a fresh temporary directory outside
   the project.
3. `pnpm exec lace import <dir> --url <origin> --publish --json` in the project
   root with `LACE_IMPORT_TOKEN` added to the environment; require exit 0.
4. Read the published export with the journey's build token and require the
   posts `hello-lace`, `first-project` and the `settings` global values.
5. Rerun; require exit 0 and every plan item `unchanged`.

The token is added to the journey's sanitizer before the first call.
`nodeJourney` calls it after its build checks with the Compose API origin;
`cloudflareConsumerJourney` after its Astro build check with the Worker origin.
The starter phase runs only `--validate-only` (no API), which is what CI can
afford.

Importing Home into these projects replaces the journey's own Home draft (no
state record, so a normal update). Placing the smoke after all Home
expectations avoids changing them.

### D5. Documentation layout

- Public page `apps/docs/src/content/docs/en/latest/editing-content/import.md`
  (*Import content*): task flow first (token → validate → dry run → import →
  rerun), then options and plan states, exit codes, limits, the format
  reference (top-level fields, media items, entries, blocks, references, rules
  per model kind), the sample with download links, and *Write a converter*.
  `reference/cli-environment.md` gains the command row and the
  `LACE_IMPORT_TOKEN` row.
- `docs/content-import.md` (internal): verification tiers and how to run them,
  coverage and what is not covered (real `429`, remote Worker, real accounts),
  invariants (HTTP client only, no deletion, same-release CLI and server), and
  a link to the public page and ADRs 0016/0017.
- `docs/documentation-maintenance.md` topic map: Editing content row adds the
  internal sources (`content-import.md`, CLI README, `content-import-cli`
  spec).
- `packages/cli/README.md`: drop the session label from the heading and link
  to the public page for the format.

### D6. Generated project guidance and template version

`docs/lace-operations.md` gains *Import content* after *Publish content without
a site*, with the Cloudflare origin inside the existing Cloudflare markers.
`README.md` mentions `pnpm exec lace import` next to the other commands.
`TEMPLATE_VERSION` becomes 0.44.0 with a configuration note (guidance only, no
migration, CLI and server of the same release). Snapshot fixtures under
`tests/fixtures/generated-project/` are refreshed with `snapshots --update`.
`tests/consumer-guides.test.mjs` and `scripts/consumer-guides.mjs` are updated
only if their command extraction treats the new commands as setup steps.

## Package boundaries

No production package dependency changes. Test and script code may import
`@lacecms/cli` build output and the root fixture; the docs app gains static
files only.

## Risks / Trade-offs

- [The journeys expose a CLI or server defect] → fix it in this change with a
  unit test in the owning package and record it in `verification.md`; stop and
  update the change if the fix alters accepted behavior.
- [Real upload rate limit (30/min per user) in the Node Compose journey, which
  uploads media earlier] → the sample has two images; `Retry-After` handling
  covers an unlucky window within the journey timeout.
- [The cross-runtime suite needs Docker and is not in CI] → the CI starter
  phase and the root sample test keep the sample and packed CLI checked on
  every push; the full matrix is part of the documented local verification.
- [Starter config changes break the sample] → the root sample test fails and
  names the sample, as specified.
- [Images in `apps/docs/public` inflate the docs build] → two images of at
  most 50 KiB each.

## Migration Plan

No database or runtime change. Template 0.44.0 changes only managed guides;
`lace upgrade` applies them with the usual hash review. Rollback is reverting
the documentation and test changes.
