## Goals / Non-Goals

**Goals:**

- A fresh database on either runtime is created by one migration whose
  resulting schema equals the schema the 16 migrations produced.
- An existing pre-baseline database is refused with one clear diagnostic,
  never partially migrated.
- Every compatibility branch listed in the proposal is deleted with its tests,
  not left unreachable.

**Non-Goals:**

- No change to the declared Drizzle schema, column nullability or indexes, even
  where a column is now always written (for example `media.sha256`): a schema
  change would need its own migration and review.
- No data export/import tooling for the owner's database; the existing
  `lace import` and build export cover moving content if wanted.
- No removal of `hasBaseline`/`record-baseline` handling: a model row without
  a baseline still occurs before its first synchronization and when its
  identity is written without a baseline (accepted spec scenario).
- No change to release history (`release/alpha.json` `publishedVersions`,
  CHANGELOG) or to release-scoped specification text (RF8Y).

## Decisions

### D1 Baseline generated by Drizzle Kit, verified against the old chain

Delete `packages/db/drizzle/` and run `pnpm db:generate --name baseline`, which
writes `0000_baseline.sql`, its snapshot and a one-entry journal from the
declared schema. `checkedInMigrations` becomes that one entry. Before deleting
the old chain, a one-off check (recorded in the task, not committed) migrates
two in-memory SQLite databases, one with the old 16 files and one with the
baseline, and compares normalized `sqlite_master` rows (type, name, table,
SQL with whitespace collapsed) plus `pragma table_info`, `index_list`,
`foreign_key_list` per table. Any difference that is not cosmetic (column
order inside a rebuilt table, quoting) is either a schema declaration gap,
which stops the task for a decision, or SQL Drizzle cannot declare, which is
appended to the baseline file as a custom statement. `pnpm db:check` must then
pass, and the shared column-list test runs against the baseline.

*Rejected:* dumping `sqlite_master` from the old chain as the baseline: it
would equal the old schema exactly, but the snapshot chain would not match the
declared schema, so `db:check` would report a pending migration. *Rejected:*
keeping the old chain behind a "squashed" marker: the owner chose a clean
baseline and recreates the database.

### D2 One shared pre-baseline rule, enforced before any write

`@lacecms/db` `schema/migrations.ts` gains a pure helper that, given ledger
entries (Node `created_at` values or D1 names), returns the entries that are
not checked in. Callers:

- `migrateNodeDatabase` reads `__drizzle_migrations` when the table exists,
  before setting pragmas or calling the migrator, and throws a new
  `UnsupportedDatabaseError` (platform-node, extending the application
  `RuntimeConfigurationError` base like `NodeEnvironmentError`, so the REST
  classifier keeps `500` if it ever surfaces) naming the database as created
  by an engine older than the baseline.
- `cli/src/migrate.ts` maps that error, and for D1 reads `d1_migrations`
  through the `D1Database` it already receives (local Miniflare or the remote
  HTTP transport) before spawning Wrangler; a missing table is a fresh
  database. Both raise `CliError("SCHEMA_UNSUPPORTED", …, EXIT.SCHEMA)`; the
  code joins the CLI code union and the recovery-diagnostics table.
- Doctor reports `SCHEMA_UNSUPPORTED` (fail in setup and ready) from the same
  helper for the Node ledger and the remote D1 SELECT; local Cloudflare stays
  API-derived (the Worker is not ready because the baseline name is missing).
- Node API startup and the Worker readiness need no change: the baseline is
  not in their ledger, so they already report not ready.

*Rejected:* relying on the failing `CREATE TABLE` of the baseline: Drizzle
would roll back the Node transaction, but Wrangler's error is opaque and the
operator would not learn to recreate the database. *Rejected:* auto-recreating
the database: destructive and outside an explicit migration command.

### D3 Built-in blocks keep their versions and lose their migrations

Removing the identity migrations keeps definition versions (`image` 4,
`gallery` 5, `videoEmbed` 2), registry item `blockVersion` values, lock files
and stored `schema_version` values unchanged, so rc1 content and the starter
are untouched and no new migration is needed. A stored older block gets the
existing `BLOCK_MIGRATION_MISSING` diagnostic. Tests that used built-in
migrations to exercise the mechanism (content `blocks/migration` tests,
`test-utils` sync contract cases, CLI `content sync` tests) switch to a custom
versioned block definition, so the mechanism keeps its coverage. Repository
contract case names that change are updated in both pins (Node and D1).

*Rejected:* resetting built-ins to version 1: it changes stored data, the
registry manifests and every site lock, and would itself need a migration.

### D4 Configuration identity without legacy proofs

Delete `legacyStructureForHash`, the `legacyStructureHash` field of the
normalized model and its hash-input exclusions, and `legacyMatch` in
`plan.ts`. `publicProjectionChanged` without a trusted baseline returns
`stored.projectionHash !== current.projectionHash`; the record-baseline branch
keeps `!hasBaseline || !trustedPublicBaseline(stored)`. The contract case
"accepts a legacy structural hash once when fields use display-like keys"
and the legacy public-identity cases are deleted or rewritten to the new
conservative rule, with both pins updated.

### D5 Export contracts require the current shape

`buildExportSchema` makes `globals` and `seo` required (no defaults). The
tolerant build-export format schema accepts integers `>= BUILD_EXPORT_FORMAT_VERSION`
and the `formatVersion === 1` bypass in `tolerantBuild` goes, so a format 1
payload fails the format check before the manifest check. The SDK needs no
code change beyond tests: it already rejects higher formats and relies on
tolerant validation for the rest. OpenAPI output does not change because the
API emits only first and continuation pages. SDK, contracts and loader
fixtures that use format 1 or omit `globals`/`seo` are updated.

### D6 Planner requires the site record

`upgrade-input.ts` refuses a manifest without `site` with the existing
`UPGRADE_INPUT` manifest error; the rc1 template already writes the record, so
the rc1 fixture upgrade is unaffected.

### D7 rc1 fixtures come from the published package

Pack `create-lace@0.1.0-rc1` from npm into a scratch directory, record its
registry integrity and archive SHA-256, generate the default and
`--cloudflare` projects with the packaged generator, and write
`tests/fixtures/template-0.46.0/{default,cloudflare}.json` in the existing
fixture format with `provenance` (`generator`, `templateVersion` `0.46.0`,
`sourceRevision` `430661f6…`, digests). Then delete `template-0.35.0` and
`template-0.39.0`. The fixture test and acceptance script already discover
`template-*` directories, so they need no version names; the conflict file
used by acceptance is checked against the rc1 project. Owner decision 7 is
amended in the roadmap (done while planning).

### D8 Documents

`docs/database-migrations.md` is rewritten around the baseline: how fresh
databases are created, the pre-baseline refusal and how to recreate a database,
and how later migrations are added. Internal notes that name a removed
migration (`node-api.md`, `cloudflare-worker.md`, `configuration-synchronization.md`,

`content-configuration.md` goes. `docs/compatibility.md`, `docs/alpha-release.md`
and `apps/docs` release guidance are RF8Y.

## Risks / Trade-offs

- [The baseline misses SQL the old chain created (a trigger, a check or an
  index outside the declared schema)] → D1's schema comparison before the old
  chain is deleted; a non-cosmetic difference stops the task.
- [The owner's local development databases (`.lace/data`, `.wrangler` state,
  `packages/platform-node/lace.sqlite`) are pre-baseline] → the refusal names
  the file; `docs/database-migrations.md` lists the local paths to delete.
- [rc1 operators upgrading packages without recreating the database] → only
  the owner exists; the refusal and doctor give the action. Rollback to rc1
  packages works on the old database because nothing was written.
- [Archiving order with `prepare-rc1-release`] → that change must be archived
  first (its delta modifies the requirement this change removes); the archive
  task checks it.
- [Removing built-in migrations hides a forgotten stale block in the owner's
  content] → irrelevant after recreation; on any other database sync reports
  `BLOCK_MIGRATION_MISSING` without writing.

## Migration Plan

1. Owner: keep the rc1 database or its export if content matters; after this
   change ships, recreate the database (`lace db migrate` on an empty path or
   new D1 database), run `content sync`, bootstrap, and import or re-enter
   content.
2. Rollback: revert the change; databases created from the baseline are not
   readable by the old chain's ledger rules, so recreate again after a
   rollback.
