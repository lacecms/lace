## Why

Lace has one user, and owner decision 11 (2026-11-08) makes `0.1.0-rc1` the
oldest supported state. The code still carries compatibility paths for data,
schemas and projects that predate rc1: 16 incremental database migrations,
identity migrations of built-in blocks, a legacy configuration hash, legacy
public-identity proofs, export format 1 and two published-template fixtures
from alpha.7 and alpha.8. Each path costs tests, specification text and
review time, and none can be reached by a database created from rc1 onward.

This is roadmap Step RF8, session **RF8X — rc1 baseline**
([refactoring roadmap](../../../docs/refactoring-roadmap.md), inserted before
RF8Y and RF8B). It is the code side of decision 11; RF8Y removes release
history from specifications and documents, and RF8B then reorganizes the
specifications.

## What Changes

- **BREAKING** The 16 Drizzle migrations in `packages/db/drizzle/` become one
  baseline migration generated from the declared schema, applied identically
  by Node SQLite and D1. The declared schema does not change.
- **BREAKING** A database migrated by an engine before the baseline is refused:
  `lace db migrate` (Node and both Cloudflare targets) stops before any write
  with the new code `SCHEMA_UNSUPPORTED` (exit 5) and tells the operator to
  recreate the database; `lace doctor` reports the same state. The owner
  recreates the rc1 database (owner decision).
- **BREAKING** Built-in blocks lose their identity migrations (`image` to 2–4,
  `gallery` to 2–5, `videoEmbed` to 2). Definition versions stay (`image` 4,
  `gallery` 5, `videoEmbed` 2). A stored built-in block below its version
  fails synchronization with the existing `missing_step` diagnostic. The block
  migration mechanism stays for custom blocks.
- Configuration synchronization loses `legacyStructureHash` and the legacy
  hash-equality proofs of public identity. A model without a trusted public
  identity always takes the conservative path (public-state advance and one
  coalesced build).
- **BREAKING** The assembled build-export schema requires `globals` and `seo`;
  the tolerant variant no longer accepts format 1 and requires internal-link
  manifests. The format version number stays 2.
- **BREAKING** The upgrade planner requires the project manifest's site
  record; a manifest without one is refused as malformed.
- Template upgrade fixtures `template-0.35.0` and `template-0.39.0` are
  replaced by `template-0.46.0`, generated by the rc1 generator; template
  upgrade acceptance starts from rc1.
- The generated template advances to `0.47.0` (owner decision during apply):
  its upgrade instructions carry only the step from rc1 (recreate the
  database, because the baseline replaces every earlier migration), and the
  generated operations guide describes the baseline instead of numbered
  migrations.
- Internal documents that name a removed migration describe the baseline.

Non-goals: block definition and export format numbers are not reset; the
schema-evolution and block-migration mechanisms stay; release- and
template-numbered requirements, `docs/compatibility.md` and public upgrade
guidance are RF8Y; spec reorganization, roadmap codes and the RF8A spec
defects are RF8B; reading legacy reason-only site-build errors stays (it is
also the fallback for malformed rows).

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `sqlite-schema-and-migrations`: one baseline migration; schema requirements
  describe tables instead of numbered migrations; a pre-baseline database is
  refused; the site-build reclassification migration is removed.
- `operational-cli`: `lace db migrate` refuses a pre-baseline database on
  every target with `SCHEMA_UNSUPPORTED`.
- `environment-doctor`: migration diagnosis reports a pre-baseline database.
- `block-registry`: built-in blocks declare no migrations; migration
  scenarios of older built-in versions are removed.
- `collection-query-options`: public identity without a trusted baseline uses
  only the conservative path.
- `rest-contracts`: assembled export requires `globals` and `seo`; tolerant
  parsing drops format 1.
- `public-sdk`: the SDK reads only build-export format 2; a lower format is a
  contract error.
- `media-use-cases`: the scenario for media stored before the hash column is
  removed.
- `upgrade-planner`: the manifest site record is required.
- `generated-project-acceptance`: the published-template upgrade starts from
  the rc1 template.
- `project-generator`: upgrade instructions cover only the upgrade from the
  latest published template.

## Impact

- Code: `packages/db` (migrations, `checkedInMigrations`), `packages/platform-node`
  (migrator guard, migration tests), `packages/platform-cloudflare` (test
  harness ledger), `packages/cli` (migrate guard, doctor, upgrade input),
  `packages/content` (built-in definitions), `packages/config` and
  `packages/application` (structure hash, sync planning), `packages/contracts`
  (build-export schemas), `packages/sdk` (format tests), `packages/test-utils`
  (contract case pins).
- Fixtures: `tests/fixtures/template-*`, `scripts/template-upgrade-acceptance.mjs`.
- Generator: `packages/create-lace` template version, `.lace/upgrade-instructions.json`,
  `templates/docs/lace-operations.md`, generated-project snapshots.
- Documents: `docs/database-migrations.md` and the internal notes that name
  migrations; `docs/refactoring-roadmap.md`.
- Operators: databases created before this change must be recreated; this is
  the only installation today. Architecture: §22 in
  `docs/architecture/distribution.md` gains the baseline rule, and the format 1
  sentence in `docs/architecture/content-configuration.md` goes.
- Depends on RF8A (archived). Precedes RF8Y and RF8B.
