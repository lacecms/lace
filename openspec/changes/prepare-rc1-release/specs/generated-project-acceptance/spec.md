## MODIFIED Requirements

### Requirement: Upgrade from the published alpha template is proven

The repository SHALL keep fixtures holding the exact default and `--cloudflare` projects generated by the generator of the latest published prerelease (after verified rc1 publication, `create-lace@0.1.0-rc1`, template `0.46.0`), recording that package's published digests and source revision, and a test SHALL verify each retained fixture's manifest version, provenance and managed-file digests without naming a template version in the test. After the post-release retirement step, fixtures of earlier templates SHALL NOT be kept once a later published template has fixtures. During rc1 preparation only, alpha.7 fixtures SHALL remain alongside the alpha.8 baseline until verified rc1 publication, preserving the owner-requested retirement order. Acceptance SHALL materialize each fixture, add a user README and user edits to `lace.config.ts` and a `site/` source file, generate the current template with the same options, and upgrade with the packed CLI:

- a modified managed file SHALL be reported as a conflict, and apply SHALL fail without changing any project file other than its conflict-review and recovery records under `.lace/`;
- after the operator restores that file, the plan SHALL have no conflict, apply SHALL make every changed or new managed file equal the current template, remove a retired managed file that was unmodified, record the current template version, and leave the README, `lace.config.ts` and all `site/` files byte-for-byte unchanged without adding files under `site/`;
- a following plan SHALL report no changes.

#### Scenario: Alpha project upgrade
- **WHEN** a project on the latest published prerelease template with user edits is upgraded to the current template
- **THEN** managed infrastructure is current and the user's README, configuration and site source are unchanged

#### Scenario: Modified managed infrastructure
- **WHEN** a managed file of the published-template project was edited by the operator
- **THEN** the upgrade reports the conflict and apply writes nothing

#### Scenario: Fixture integrity
- **WHEN** a retained fixture's managed file bytes no longer match the digests in its recorded manifest
- **THEN** the fixture test fails naming the fixture and file

Retirement of alpha.7/template 0.35.0 upgrade fixtures and exclusively historical upgrade assertions SHALL happen only after complete verified rc1 publication. Before publication, the latest published alpha.8/template 0.39.0 default and Cloudflare fixtures SHALL establish the shipping upgrade baseline. Each replacement SHALL be generated from the actual immutable published package with recorded source, archive hash and registry integrity, never reconstructed from the current workspace. Post-release fixture changes SHALL use a later source revision and SHALL NOT alter the released source/tag/evidence. Generic upgrade conflict, user-file preservation, digest-tampering, recovery, idempotence and image-identity tests SHALL remain; a historical version string alone SHALL NOT justify deletion of a current regression test. Historical specs, release evidence and public versions SHALL remain intact.

#### Scenario: Release has not completed
- **WHEN** rc1 is only prepared, acceptance fails or registry/GitHub publication is incomplete
- **THEN** alpha.7-specific upgrade retirement remains pending and the verified shipping baseline is retained

#### Scenario: Released baseline replaces historical checks
- **WHEN** rc1 publication and evidence are fully verified
- **THEN** exact rc1 default/Cloudflare fixtures replace older upgrade fixtures in a later commit, obsolete alpha.7-only checks are removed and generic upgrade safety passes
