## Goals / Non-Goals

**Goals:** preserve package boundaries and portable behavior, ship one accepted immutable graph, make recovery explicit, and gate historical test retirement on actual release completion.

**Non-Goals:** redesign release tooling, change runtime authority beyond accepted SM behavior, weaken audit or acceptance, complete pending RF units, or delete local release data automatically.

## Decisions

1. **Add bounded RC support and keep existing filenames.** Extend the shared candidate/history validation to accept alpha.N and rcN, including exact `0.1.0-rc1`, with focused valid/invalid, history, packing and lifecycle checks. Keep `release/alpha.json` and the existing lifecycle entrypoints to avoid unrelated renames. Preserve `next`, private packages, sixteen-package allowlist and both platforms. Update all candidate-sensitive manifests, platform version modules, registry requirements, Docker defaults, generated dependency/image references and delivered commands. Advance ownership template to 0.46.0, refresh upgrade instructions, six snapshots and lockfile. Reject accepting arbitrary unchecked strings or silently changing to rc.1.
2. **Update authoritative release guidance before downstream prose.** Refresh architecture §§22/25 release references and record this owner-requested release checkpoint in the roadmap without making pending RF2–RF8 prerequisites. Refresh compatibility, concise changelog, public catalog/target assertions, generated operations and public topic map. The migration guide names the actual two SQL migrations, conditional visibility adoption and gallery v5 synchronization. MCP guidance reflects the separate consented content:publish scope; deletion and unpublication stay forbidden. RC status is experimental, with preparation, publication and real deployment evidence distinct.
3. **Keep implementation responsibilities in existing packages.** Runtime behavior stays in accepted config/content/application/contracts and narrow Node/D1 adapters; release code orchestrates packages and images. Reuse release scripts, shared consumer journeys and MCP compatibility fixtures. Saved consumer tests resolve the saved generator/CLI/archives/images, never source-workspace runtime imports. Add only missing post-alpha.8 artifact scenarios, preserving persistence atomicity, build failure/recovery, consent/revocation and log redaction. Source concurrency and D1-query-budget results are labeled separately from saved-artifact evidence.
4. **Use alpha.8 as the pre-release upgrade baseline.** Obtain the actual published create-lace alpha.8 archive, verify npm integrity and source, generate exact default/Cloudflare fixtures outside the workspace, and record original managed bytes/provenance. Keep alpha.7 fixtures until the post-release retirement step requested by the owner; the harness must support the retained baselines during this transition. Do not fabricate fixtures from the changed generator. Verify conflict refusal, protected user README/config/site bytes, managed updates, recovery and repeat no-op through the packed candidate CLI.
5. **Freeze, accept and publish exact bytes.** After source/docs/audit gates, commit reviewed shipping source, verify frozen dependencies and clean status, then prepare `.release-artifacts/rc1` (or a distinct recorded retry). Run independent verify and exact-artifact acceptance, retaining inventory/source fingerprint/checksums/local IDs/platform coverage and harness revision. Push shipping and reviewed notes commits unchanged before GitHub finalization. The owner's request includes creating the release: following the separate apply request required by repository workflow, publication is part of implementation, with no extra blanket permission checkpoint. Use previews before live npm/image/GitHub commands and existing identity checks, locks, journals and resume behavior. Publish all packages and public manifests before announcing completion; leave latest unchanged. Credentials stay in local operator authentication and never enter reports.
6. **Retire historical upgrade checks only after finalization.** Freshly verify the published rc1 release/assets/registries. Obtain its exact published generator and create latest-published default/Cloudflare fixtures, including recorded npm integrity, archive SHA-256 and source revision. In a subsequent commit, remove older fixture directories (including alpha.7) and genuinely alpha.7-only upgrade assertions and update maintained historical test pointers. Keep generic fixture validation, upgrade conflict/recovery/user ownership/idempotence and OCI identity/GIF/cache tests; neutralize obsolete release-number labels if useful. Verify the new baseline against the packed released CLI and generic current tests. Do not move the release tag, rewrite accepted artifacts or rebuild the released set for post-release test cleanup. If publication is incomplete, leave this task pending.

## Risks / Trade-offs

- RC format is rejected by existing validators → add focused format/history/lifecycle coverage before selecting coordinates; preserve compatibility with historical inventories.
- Historical alpha.8 saved journeys assert draft-only MCP while current behavior permits separately authorized publishing → update current candidate journeys to accepted scope semantics while retaining default-off and denial coverage.
- Permission or registry/network failure → report incomplete publication, retain exact saved bytes/journals and resume matching items; never overwrite conflicts or declare success from local preparation.
- Fixture rotation can erase upgrade safety or violate the requested timing → replace with provenance-backed published baselines, keep alpha.7 until rc1 completion and commit retirement after the release source.
- Conditional/gallery synchronization makes package-only rollback unsafe → require matching configuration, database, media and source backups; no reverse migration is promised.
- Audit or acceptance exposes a new design/scope issue → stop implementation and use openspec-update-change; do not silently waive gates.

## Migration Plan

Back up database, media, config, source-owned blocks and deployment settings. Upgrade API/admin/site dependencies and builder together, apply 0014/0015 on Node and D1 using the maintained migrators, review source/deployment conflicts and synchronize model/block definitions including gallery 5. Validate existing content and new projection behavior before rebuilding. Enable MCP publication only by explicit grant/consent after migration; retain current role attenuation and revocation. Rollback restores the matching saved state rather than assuming package downgrade reverses schemas. Real VPS/Cloudflare deployment remains an owner gate distinct from local runtime acceptance and registry publication.
