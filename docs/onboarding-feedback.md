# Проблемы и пожелания при первом запуске Lace

Журнал наблюдений при установке опубликованных альфа-пакетов Lace и подключении к существующему Astro-приложению. Новые пункты добавляем по мере прохождения установки. Запись здесь фиксирует потребность; реализацию планируем отдельно через OpenSpec.

## 1. CLI-команда для подготовки локального окружения

- Дата: 2026-10-01.
- Статус: пожелание, не реализовано.
- Контекст: после генерации проекта приходится вручную копировать `.env.example` в `.env` и генерировать несколько секретов.
- Ожидаемое поведение: отдельная CLI-команда копирует `.env.example` в `.env` и заполняет необходимые секреты криптографически случайными значениями: `LACE_AUTH_SECRET`, `LACE_MINIO_ROOT_ACCESS_KEY`, `LACE_MINIO_ROOT_SECRET`, `LACE_BUILDER_SECRET`.
- Условия: сохранять остальные настройки шаблона; не перезаписывать существующий `.env`; не выводить секреты в логи. `LACE_BUILD_TOKEN` оставить пустым до создания токена через Admin Settings.
- Название команды: определить при планировании.

## 2. Создание каталогов командой `db:migrate`

- Дата: 2026-10-01.
- Статус: создание каталогов исправлено и проверено в 26A (2026-10-02); расширенная диагностика остаётся в 26B.
- Контекст: первый `pnpm db:migrate` в сгенерированном проекте завершился с кодом 6 и сообщением `Operation failed. Check the selected target, migration state, and configuration.`
- Причина: для `LACE_DATABASE_PATH=./.lace/data/lace.sqlite` отсутствовал каталог `.lace/data/`; мигратор открывал SQLite без создания родительского каталога. Нативный драйвер SQLite работал.
- Ожидаемое поведение: перед открытием файловой SQLite-базы мигратор рекурсивно создаёт отсутствующие родительские каталоги выбранного пути. Существующие каталоги и данные сохраняются; путь `:memory:` не требует создания каталогов.
- Пожелание к диагностике: если каталог нельзя создать, сообщать понятную причину без раскрытия секретов.
- Проверка 26A: общий Node-мигратор создаёт родительские каталоги до открытия SQLite. Изолированный consumer из tarball-пакетов проверяет packaged CLI и runtime migration entry: свежий вложенный путь, повторную миграцию, сохранность данных и отказ при файле вместо родительского каталога. Focused-тесты дополнительно проверяют `:memory:`, конкурентное создание каталога и отсутствие миграций при старте API. Нормальный сценарий с исправленными пакетами — `pnpm db:migrate` без предварительного `mkdir`.
- Доставка: исправление относится к исходникам и вновь собранным артефактам; опубликованные `0.1.0-alpha.1` остаются неизменными. Для обычных consumers требуется будущий согласованный релиз с этим исправлением.
- Исторический проверенный обходной путь для старых артефактов: выполнить `mkdir -p .lace/data` из корня сгенерированного проекта, затем повторить `pnpm db:migrate`. После этого миграция прошла успешно.

- Ожидаемое поведение: добавить в документацию короткий пример `curl` для `POST /api/v1/setup/admin` как альтернативу существующему скрипту, с полями `token`, `email` и `password` и понятными заменяемыми значениями.

## 5. Визуальное создание первого администратора

- Дата: 2026-10-01.
- Статус: пожелание, не реализовано.
- Контекст: при первом открытии Admin показывается страница входа, хотя пользователя ещё нет. Интерфейс не объясняет, что первого администратора сейчас нужно создавать запросом из терминала.
- Ожидаемое поведение: пока первоначальная настройка не завершена, вместо страницы входа показывать форму создания первого администратора с понятными пояснениями и полями email и пароля. После успешной настройки переходить к обычному входу или авторизованной админке.
- Уточнение для планирования: сохранить проверку права на первоначальную настройку; если одноразовый bootstrap-токен остаётся необходимым, объяснить в форме, как его получить, и дать поле для ввода. Конкретный механизм определить отдельно.
- После создания первого администратора форма первоначальной настройки больше недоступна; обычный вход остаётся стандартным сценарием.

## 6. Ознакомительный тур по админке при первом входе

- Дата: 2026-10-01.
- Статус: реализовано в 28B (2026-10-03); проверки и команды записаны в OpenSpec verification.md.
- Контекст: после первого входа не хватает визуального гида, объясняющего назначение разделов и базовый порядок работы.
- Ожидаемое поведение: при первом открытии авторизованной админки предложить пошаговый тур по всем доступным пользователю вкладкам с краткими пояснениями прямо в интерфейсе.
- Содержание: Content — страницы и коллекции, редактирование, сохранение черновика и публикация; Media — загрузка и повторное использование файлов; Users — пользователи и роли; Settings — настройки и build tokens; Builds — сборки, их состояние и повторный запуск. Список шагов должен соответствовать актуальной навигации и правам пользователя.
- Управление: переходы вперёд и назад, возможность пропустить или закрыть тур, сохранение факта прохождения и повторный запуск из доступного места в интерфейсе.

- Решение 28B: необязательная welcome-панель, пошаговый Radix Dialog, повторный запуск Introduction из меню аккаунта. Шаги соответствуют навигации и роли; статус хранится локально по адресу установки, admin base path, пользователю и версии тура. При недоступном storage используется память текущей страницы. Тур сохраняет несохранённый черновик. Уточнение текста для отдельных режимов публикации остаётся в 29.

## 7. На подумать: установка компонентов в существующий сайт

- Дата: 2026-10-02.
- Статус: решение принято 2026-10-04 — реализация запланирована в шаге 30 roadmap (общее ядро рендеринга, Astro-адаптер, `lace add block`). Решение и сравнение вариантов записаны в [ADR 0006](adr/0006-shared-rendering-core-and-installed-block-source.md) (30A); имена пакетов (`@lacecms/render`, `@lacecms/astro`), реестр `registry/`, файл сайта `lace.site.json` и публичные API зафиксированы в разделах 6, 7 и 13 архитектуры.
- Контекст: при подключении Lace к существующему Astro-сайту пришлось вручную копировать загрузчик данных, вспомогательный код и компоненты блоков из `cms/site/src/` в `src/lib/` и `src/components/` основного сайта. Это добавляет ручные шаги и требует разбираться в зависимостях файлов.
- Вопрос: как сделать подключение и отображение блоков удобнее, сохранив возможность пользователя редактировать исходники компонентов?
- Вариант для рассмотрения: команда по образцу shadcn, которая добавляет выбранный компонент или набор рендереров в проект пользователя. Условный пример — `lace add component hero`; синтаксис не утверждён и такой команды сейчас нет.
- При добавлении стоит учитывать связанные компоненты, вспомогательные функции, импорты, зависимости и регистрацию блока в рендерере, чтобы пользователь получал работоспособный набор, а не отдельный файл. Пути назначения должны соответствовать структуре целевого сайта; существующие пользовательские изменения нельзя молча перезаписывать.
- Задел на будущее: механизм установки и каталог компонентов не должны быть жёстко привязаны к Astro. Рассмотреть варианты компонентов для разных фреймворков, например Astro, React, Vue и Svelte, с явным выбором целевого фреймворка и отдельными реализациями рендереров. Это не означает обязательную поддержку всех фреймворков в первой версии.
- Открытые вопросы: отдельные компоненты или стартовый набор; установка общих утилит и загрузчика SDK; определение фреймворка и путей; совместимость версий, повторное добавление и обновление скопированного кода. Сравнить подход с готовыми пакетами рендереров перед выбором решения.

## 10. Явный выбор сайта для сборки

- Дата: 2026-10-02.
- Статус: реализовано в 29A, проверено 2026-10-03; [отчёт](archive/step-29/step-29a-verification.md).
- Контекст: в нашем репозитории основной Astro-сайт находится в корне, а генератор создал пример `cms/site/`. Сгенерированная Compose-конфигурация настроена собирать пример, поэтому пользователь может ожидать обновления другого сайта.
- Ожидаемое поведение: пользователь явно задаёт целевой сайт для сборки; документация и интерфейс сборок позволяют понять, какой проект будет собран. Поддержать сценарий отдельного CMS-каталога и существующего сайта.
- Решение 29A: deployment-конфигурация явно задаёт read-only host mount, относительный Astro-каталог и static output; builder использует корневой frozen lockfile и прямую фиксированную Astro-команду. Builds и администраторские Settings показывают безопасные ID/название текущего сайта отдельно от истории. Проверены standalone/workspace рядом с `cms/`, сохранение релиза при ошибке и исправление/Retry. Нужны совместимые новые артефакты; поведение опубликованных alpha-образов не изменено.

## 12. Пояснение обновления сайта после публикации

- Дата: 2026-10-02.
- Статус: реализовано в 29B, проверено 2026-10-03; [отчёт](archive/step-29/step-29b-verification.md).
- Наблюдение пользователя: в Astro dev-режиме обновления из CMS попадали на сайт без проблем. Не считать обязательный ручной перезапуск установленным требованием для этого сценария.
- Направление: объяснять различие между публикацией контента в CMS и обновлением сайта в dev-режиме, при ручной статической сборке и при автоматической сборке. Показывать применимый следующий шаг или состояние сборки, чтобы пользователь понимал, когда изменения доступны на сайте.
- Перед изменениями: проверить фактическое поведение каждого режима; не требовать перезапуска или пересборки там, где обновления уже поступают автоматически.
- Решение 29B: воспроизведены четыре режима. Собственная интеграция существующего сайта в dev показывает данные, читаемые в коде страницы, после перезагрузки; данные из `getStaticPaths` и новые маршруты — после перезапуска dev. Сгенерированный `site/` кэшировал экспорт до перезапуска — исправлено ETag-ревалидацией в dev и чтением поста по slug; новые/переименованные slug по-прежнему требуют перезапуска dev. Ручная статическая сборка требует новой сборки и развёртывания; Compose отдаёт новый релиз после успешной покрывающей сборки (статус `pending` на всё время синхронной сборки) с `Cache-Control: no-cache`. README/операции (шаблон 0.8.0), Builds, редактор записи и тур объясняют режимы без заявлений о развёртывании.
