# Lace MVP Architecture

## 1. Document purpose

This document defines the product and technical architecture for the first usable version of Lace. It is intended to be the source for a subsequent implementation plan, milestone breakdown, and architectural decision records.

Lace stands for **Lightweight AI Cloud Engine**. It is a lightweight, self-hosted headless CMS paired with a statically generated Astro website. A single Lace installation manages a single website.

The MVP must run in two environments:

1. Cloudflare, using Workers, D1, R2, and optionally KV.
2. A conventional VPS, using Docker Compose, Node.js, SQLite, and MinIO.

The application must remain portable by placing infrastructure-specific behavior behind narrow interfaces. Portability does not mean hiding SQL or every framework API behind custom wrappers. Abstractions are introduced only at boundaries that genuinely differ between environments.

## 2. Product goals

The MVP should allow a user to:

- initialize a new Lace-powered website with one CLI command, with a starter site, against an existing Astro site, or without a site;
- customize the Astro site without modifying the CMS engine or admin application;
- install editable block renderers into a site without copying engine files by hand;
- define pages, collections, fields, and allowed block types in a typed configuration file;
- manage structured content and ordered content blocks in a browser-based admin application;
- upload and reuse media;
- keep draft content separate from published content;
- publish content with an explicit permission;
- trigger a rebuild of the static Astro website after publication;
- run the same content model and domain behavior on Cloudflare or a VPS;
- update the Lace engine without overwriting the user's website source.

The design should also be easy for coding agents to understand and modify. For the MVP, “AI” primarily means that the generated project, configuration, contracts, and site code are structured for reliable AI-assisted development. A built-in LLM provider, chat interface, or autonomous source-code editor is not required for the MVP.

## 3. Explicit MVP scope

### Included

- One installation per website.
- Pages and collections as two content-model kinds.
- Code-first content-model definitions.
- Draft and published snapshots only.
- Ordered block-based content.
- Tiptap rich-text blocks.
- Media upload to R2 or MinIO.
- Email/password authentication through Better Auth.
- Optional OAuth-delegated MCP content assistance (`add-oauth-mcp-server`, MCP1):
  inspect models/entries and create/save drafts; publication, unpublication and
  all content deletion remain forbidden through MCP.
- Admin, editor, and viewer roles.
- Optional transactional email through a provider port (`EmailSender`): SMTP on
  Node, Resend on both runtimes, and the Cloudflare Email Service binding on the
  Worker. An installation without a provider remains fully usable.
- REST API with versioned endpoints and runtime validation.
- Astro build-time SDK.
- Reliable build-trigger dispatch through an outbox.
- Node/Docker and Cloudflare runtime adapters.
- CLI initialization and an upgrade-safe generated-project layout.

### Not included

- Multiple sites or tenants in one installation.
- PostgreSQL, MySQL, or another database dialect.
- Unlimited content revision history.
- A `previousPublished` snapshot.
- Real-time collaborative editing or CRDTs.
- Arbitrarily nested layout-builder blocks.
- User-defined content models created entirely in the admin UI.
- Per-entry or per-collection ACLs.
- Internationalization and localized snapshots.
- Scheduled publication.
- A visual page preview that exactly reproduces the Astro site.
- A built-in AI chat or an LLM-provider integration.
- A plugin marketplace.

These exclusions should be preserved unless a later architectural decision explicitly changes them.

## 4. Architectural principles

### 4.1 Single-site deployment

Every deployment has exactly one `lace.config.ts`, one content database, one media store, one admin application, and one public Astro site.

Multi-tenancy must not influence MVP tables, authentication, routing, or configuration.

### 4.2 Static public site

The public site is generated by Astro. It retrieves published content from the Lace public API during a build. Public page requests should normally be served as static assets and should not require the CMS API.

### 4.3 Code-first structure, CMS-managed content

Content structure is defined in version-controlled code. Content values are managed in the CMS.

This distinction is important because adding a model or route also requires the Astro site to know how to render it. The admin application may display models and generate forms, but it is not the source of truth for model definitions.

### 4.4 Two content states

Each content entry has:

- one mutable draft snapshot;
- zero or one immutable published snapshot.

Publication replaces the current published snapshot. The MVP does not retain application-level revision history.

### 4.5 Portable capabilities, explicit adapters

Domain and application code depend on capability interfaces. Cloudflare and Node packages implement those interfaces.

The MVP should define ports for at least:

- content repositories and transactions;
- object storage;
- cache;
- build triggering;
- background/outbox dispatch;
- clock and ID generation where deterministic tests need them.

The project must not create a custom abstraction over Hono, Drizzle, React, or every Web API.

### 4.6 Media never lives in SQL

D1 and SQLite store media metadata and object keys only. Binary content is stored in R2 or MinIO.

### 4.7 Published content is immutable

An editor may continue changing the draft immediately after publication without changing what public API consumers see.

Published snapshots are immutable to editorial changes. Configuration synchronization may rewrite their stored representation when a schema change requires it (for example, backfilling a new field's default value). Such a rewrite increments `published_state.version` and requests a site build in the same atomic mutation, so public consumers observe it only through a new published version. Block migrations are the one exception: sync rewrites stale blocks in guarded, resumable per-entry units before its final mutation, which then advances the version and requests the build. Between the two, public reads may return migrated blocks under the previous published version; the window ends with the final mutation of the same run, or of the rerun after an interruption. See [ADR 0007](adr/0007-schema-evolution-during-sync.md).

### 4.8 Spec-driven delivery

Implementation uses the repository-local OpenSpec `spec-driven` workflow. Each
roadmap session unit is normally one just-in-time OpenSpec change with proposal,
delta specs, design, and tasks. Planning and implementation are separate actions:
an agent must not write production code in the proposal action, and it must not
apply a change until its required artifacts are ready and the user explicitly
requests the apply action.

Completed changes are validated, their delta specs are synchronized into the
main specs, and then they are archived. If implementation reveals a conflict
with the architecture, the agent pauses implementation and updates the planning
artifacts; a deliberate architectural change updates this document and the
roadmap before code proceeds.

Authority order is:

1. `docs/mvp-architecture.md` for product scope and architectural invariants;
2. `openspec/specs/**` for detailed, accepted capability behavior;
3. active OpenSpec change artifacts for the proposed delta;
4. `backlog.md` for future work; completed delivery order and session boundaries
   are preserved in `docs/archive/content-editor-roadmap.md` and
   `docs/archive/mvp-implementation-roadmap.md`.

Lower levels may add detail but may not contradict a higher level silently.

### Cloudflare deployment

```text
Cloudflare Worker
├── /api/v1/*
├── /api/auth/*
└── /admin/* -> built admin assets

Bindings
├── D1: authoritative SQL data
├── R2: media objects
└── KV: optional derived cache

Separate static deployment
└── Astro output, rebuilt through a deploy hook or CI integration
```

The admin application and authenticated API should use the same origin. This avoids unnecessary cross-origin cookie and CORS complexity.

A generated Cloudflare consumer (`--cloudflare`) owns its Worker in `worker/`: a
managed entry that statically imports the project's `lace.config.ts` and calls
`createCloudflareWorker`, and a user-owned `worker/wrangler.jsonc` with the D1,
R2, packaged admin `ASSETS`, optional KV, cron, and plain-variable settings.
`@lacecms/platform-cloudflare` ships the compiled admin of the same release in
its `admin/` directory, so the consumer bundles and deploys the Worker without
the engine checkout. Secrets are uploaded with Wrangler and kept locally in the
ignored `worker/.dev.vars`. The static Astro deployment is configured separately
(its own workflow and hosting project); deploying it never deploys the CMS.
The reference hook-driven static host is a Cloudflare Pages project connected to
Git: its deploy hook, stored as the Worker secret `LACE_DEPLOY_HOOK_URL`, is the
site build trigger, and Pages builds the site with the Worker origin and a
read-only build token. The generated manual workflow (direct upload) is the
alternative without hook-driven rebuilds. A hook accepted by the provider is
recorded as an `accepted` build, not as a confirmed deployment (see §9.8). With
optional Pages tracking settings (`LACE_PAGES_ACCOUNT_ID`, `LACE_PAGES_PROJECT_NAME`
and the separate Pages-Read-only Worker secret `LACE_PAGES_API_TOKEN`) the
scheduled Worker instead tracks the exact deployment until a proven outcome or
the tracking deadline. The real-account
procedure is `docs/cloudflare-deployment-handoff.md`, used by the owner after
the implementation roadmap as part of `docs/real-application-verification.md`.

### VPS deployment

```text
Docker Compose
├── lace-api
│   ├── Node.js + Hono
│   ├── built admin assets
│   └── mounted SQLite volume
├── minio
│   └── mounted object-storage volume
├── site-builder
│   ├── private authenticated HTTP endpoint
│   ├── read-only generated-project source mount
│   ├── static-output volume
│   └── builder-cache volume (pnpm store, Astro cache)
└── static web server/reverse proxy
    └── Astro build output
```

The production build mechanism is represented by `SiteBuildTrigger`. The initial
VPS implementation calls the first-party builder's private authenticated
endpoint. The builder ignores command, path, and environment overrides from the
request and runs one image-defined build command against fixed mount paths. It
builds into a temporary release directory and atomically switches the served
release only after success. A later adapter may call an external CI webhook. The
API must never accept an arbitrary shell command from an HTTP request. The
builder's own deployment settings, never the request, supply the optional
`LACE_BUILD_SITE_URL` and `LACE_SITE_INDEXING` it forwards to the site build
(section 9.8).

The builder keeps the pnpm package store and the site's Astro cache directory
(`node_modules/.astro`: image variants and placeholders) in a dedicated
`builder-cache` volume. The cache is an optimization only: it is cleared above
2 GiB, its Astro part is dropped after a failed build, an unusable cache means
an uncached build, and it never enters a release or depends on request data.

Static responses revalidate (`Cache-Control: no-cache`) so a switched release
is visible on reload, except Astro's content-hashed `/_astro/` files, which are
served `public, max-age=2592000, immutable` (30 days) on success only. The
same rule reaches Cloudflare Pages through the site's `public/_headers`, which
the VPS proxy refuses to serve; the generated Pages workflow keeps
`node_modules/.astro` between runs with `actions/cache`.

The optional MCP surface lives in the same CMS deployment on both runtimes.
Only `LACE_MCP_ENABLED=true` exposes `/mcp` and its OAuth/discovery routes;
missing/`false` disables them, and other values fail safe configuration validation.
It requires no extra process, Durable Object or KV binding.

## 6. Repository structure

The Lace engine repository uses a pnpm workspace with Turborepo for
dependency-aware task orchestration and caching. pnpm workspaces remain the
package-management foundation.

```text
apps/
├── admin/                     # React/Vite admin SPA
├── api/                       # deployable/reference Hono composition root
├── builder/                   # fixed-command VPS Astro build service
├── docs/                      # private static Starlight public documentation
└── site/                      # engine Astro playground and build fixture (never shipped)

packages/
├── domain/                    # pure domain types, rules, and errors
├── application/               # use cases and capability ports
├── server/                    # Hono routes, middleware, app factory
├── mcp/                       # portable stateless MCP adapter and five tools
├── contracts/                 # shared Valibot transport schemas and DTOs
├── content/                   # field DSL, block registry, validation
├── db/                        # Drizzle SQLite schema and repositories
├── auth/                      # Better Auth configuration and authorization
├── config/                    # lace.config.ts definition and loader
├── sdk/                       # build-time and external REST client, published-site loader
├── render/                    # framework-neutral block parsing, block map, rich-text description
├── astro/                     # Astro adapter: LaceBlocks, RichText, loader environment glue
├── platform-cloudflare/       # D1, R2, KV, Worker and deploy-hook adapters
├── platform-node/             # SQLite, MinIO/S3, Node server adapters
├── cli/                       # create, sync, migrate, upgrade commands
└── test-utils/                # factories, fixtures, and contract test suites

registry/                      # versioned, framework-keyed block sources for `lace add block`

docs/
├── mvp-architecture.md
└── adr/                       # architectural decision records added as needed

openspec/
├── specs/                     # accepted capability specifications
└── changes/                   # active and archived implementation changes
```

Dependency direction (`A -> B` means package A may import package B):

```text
config       -> content
domain       -> content
application  -> domain, content, config
contracts    -> domain, content
mcp          -> application, contracts, domain
db           -> application, domain
auth         -> application, domain
server       -> application, contracts, auth
sdk          -> contracts
render       -> content
astro        -> render, sdk
platform-*   -> application, server, db, auth, config, mcp
cli          -> application, config, platform-*
apps/api     -> platform-*, server
apps/admin   -> contracts, content
apps/site    -> astro, render, sdk, content
```

Generated starter sites and connected existing sites use the same direct
dependencies as `apps/site`. `registry/` is engine data, not a workspace
package: its files are copied into sites and bundled with `@lacecms/cli`, never
imported by any package.

Rules:

- `domain` must not import framework or infrastructure packages.
- `content` and `config` must remain runtime-portable and must not import Node-only APIs.
- `application` may depend on domain rules, content validation, and the normalized configuration, but not on REST DTOs, Hono, Drizzle, Cloudflare, or Node adapters.
- `contracts` defines transport DTOs and schemas; it must not become an application-use-case dependency.
- `db` implements application persistence ports and may depend on Drizzle, domain, and application packages.
- `server` may use Hono and contracts but receives infrastructure through construction.
- `mcp` uses application operations and shared contracts, never server/auth/db,
  platform implementations, configuration loaders or Node-only APIs. Server
  receives an optional structural MCP handler from the platform composition root.
- REST and MCP share application discovery, authorization, reads and mutations;
  contracts own their common pure JSON projections and validation. Application
  never imports contracts or the MCP SDK.
- platform packages may depend on application ports and concrete vendor SDKs.
- `admin` depends on contracts and content metadata and owns a credentialed
  browser transport client; it never depends on database schemas.
- `render` is framework-neutral: it imports no UI framework, Node-only API, the
  SDK, or REST contracts. It accepts a structural block input that the contract
  block DTO satisfies and reuses `@lacecms/content` validation exclusively.
- A framework adapter (`@lacecms/astro` now; `@lacecms/react`, `@lacecms/vue`,
  and `@lacecms/svelte` are reserved names) contains only code that depends on
  its framework; besides the framework, its virtual modules and the render
  core and SDK, it may import only `node:` builtins (server-only build code
  such as the image placeholder cache). It never re-exports `render`, `sdk`, or `content` APIs, so each
  symbol has one canonical import path.
- No package exports visual block components. Block markup is user-owned source
  installed from `registry/` (see sections 7 and 13).
- `sdk` owns transport and the published-site loader and imports neither
  `content` nor `render`.
- `site` depends on the public SDK, the render core and its framework adapter,
  `@lacecms/content` for block definitions, and user-owned block markup.

Workspace dependency checks in CI must reject cycles and imports that violate these rules.

The private `apps/docs` application publishes public documentation independently
of CMS services. It imports no Lace runtime packages and no runtime package may
import it. Public sources live inside that application; all repository `docs/`
materials remain maintained internal engineering documentation. The product
README links to the public site and root `DEVELOPMENT.md` contributor guide.
Documentation uses explicit locale/version routes, initially English/latest for
alpha.7 following main, without changing CMS localization scope.

## 7. Generated user project

The supported MVP onboarding path is a project generator, not copying the entire Lace engine source into an existing arbitrary application.

```bash
pnpm create lace@latest my-site
```

An empty existing repository may use:

```bash
pnpm dlx create-lace@latest init .
```

The first version should require an empty target directory, except for explicitly allowed files such as `.git`, `README.md`, or `LICENSE`. Installing the CMS in place into a nonempty existing project is a later feature; an existing Astro site is instead connected to a separately generated CMS directory (see site modes below).

Generated layout (starter site mode):

```text
my-site/
├── site/                       # user-owned Astro source (starter mode only)
│   ├── lace.site.json          # Lace-managed site configuration and block lock
│   └── src/
│       ├── env.d.ts            # user-owned; lets `tsc` read `.astro` imports
│       ├── lace/blocks.ts      # generated block map file (hash-guarded)
│       ├── lib/lace.ts         # user-owned loader file
│       ├── components/lace/    # installed registry blocks, user-owned
│       ├── layouts/            # user-owned
│       ├── pages/              # user-owned: home and posts routes
│       └── styles/             # user-owned
├── lace.config.ts              # public, typed Lace configuration
├── package.json
├── pnpm-workspace.yaml
├── docker-compose.yml          # managed infrastructure file
├── .env.example
├── .lace/
│   └── manifest.json           # generator version, site mode, managed-file hashes
├── worker/                     # optional (--cloudflare) CMS Worker
│   ├── index.ts                # managed entry importing lace.config.ts
│   ├── wrangler.jsonc          # user-owned Worker bindings and resource IDs
│   └── .dev.vars.example       # managed local Worker variables template
└── .github/workflows/          # optional Cloudflare Pages/CI deployment files
```

### Site modes

Project creation selects one of three site modes with mutually exclusive flags,
recorded in `.lace/manifest.json` as `site: { mode, path }`:

1. **starter** (`--starter`, path `site`) — generates `site/` from the
   `create-lace` starter;
2. **existing** (`--existing-site <path>`) — generates no `site/` and connects
   the CMS to an existing Astro site at a relative path outside the generated
   target, typically `..` for a `cms/` directory. The path must reach an Astro
   project root (`astro.config.*` and an `astro` dependency) without symbolic
   links. The generator never modifies that site; the operator runs
   `lace add block --all --site <path>` and follows the connection guide;
3. **none** (`--no-site`, path `null`) — generates the CMS only, for headless use
   or a later connection; Compose has no builder, so build dispatch reports that
   no build trigger or build site is configured. With `--cloudflare` it
   generates the CMS Worker without the static-site workflow.

An explicit flag always wins. Without one, an interactive terminal asks for the
mode, defaulting to **existing** at `..` when the target's parent directory is an
Astro project and to **starter** otherwise; without a terminal the starter is
generated and the output names the other flags. Manifests without a `site`
record (template `0.10.0` and earlier) are read as starter mode with path `site`.

`init .` keeps the empty-target rule in every mode. Managed files that reference
the site (workspace globs, root scripts, Compose build-site mount, Cloudflare
workflow, README, and operations guide) are rendered from the recorded mode and
path, reusing the build-site selection configuration. `lace upgrade` requires a
target template generated for the same mode and path (and names the flags that
generate one); it never creates `site/` for other modes. `lace doctor` checks the
recorded site. Switching the mode of an existing project means generating a
fresh project and moving configuration manually.

### Starter and reference site

The `create-lace` starter is the single source of what users receive: minimal
`home` and `posts` pages, a `settings` global (`siteName`, `tagline`), a
`navigation` global that allows only the `navigation` block, a layout, global
styles, the eight built-in registry blocks, `lace.site.json`, the block map
file, and the loader file. Each page passes the published site to the layout,
which renders a site header from `site.global("settings")` and the published
`navigation` global's blocks through `LaceBlocks` and the block map, falling
back to static values and a static Home link while either global is
unpublished (a published navigation global without visible blocks renders no
navigation). Gallery and navigation layout CSS lives in the site stylesheet; the
components carry no `<style>` elements; only videoEmbed carries its bounded preview activation script. It contains no tests, fixtures, or
engine-development routes.

`apps/site` is the engine development playground and integration fixture. It may
carry extra models and routes, custom blocks, edge-case content, and the
published-export fixture. Nothing from it is copied into generated projects.

Both consume the same packages and hold committed copies of the built-in blocks
exactly as `lace add block` installs them. A test fails when the starter,
`apps/site`, and `registry/` block sources diverge, and CI builds a project
generated from the packed starter in addition to `apps/site`.

The generated project must not expose the editable source of the admin SPA. The admin UI and CMS engine are delivered as versioned packages, bundles, or container images.

### Ownership rules

```text
site/**                 user-owned; never overwritten by upgrade
lace.config.ts          user-owned public configuration
.lace/**                Lace-managed metadata
deployment files        managed with hash/conflict detection
CMS engine/admin        versioned dependency or container image
```

Inside any connected site tree (the starter `site/` or an existing site), the
user-owned rule has three Lace-managed exceptions maintained only by
`lace add block`, never by `lace upgrade` or the generator after creation:

```text
<site>/lace.site.json        Lace-managed site configuration and block lock;
                             configuration keys are user-editable, `items` and
                             hashes are CLI-maintained
<site>/<blockMap>            generated block map file; rewritten only while its
                             recorded hash matches, otherwise the CLI prints the
                             entries to add
<site>/<componentsDir>/**    installed registry block sources; user-owned after
                             installation, updated only while the recorded hash
                             matches, otherwise reported as a conflict
```

The CLI never edits other site source, never edits the site `package.json`
(it prints the exact `pnpm add` command), and rejects paths outside the site
root.

### Upgrade model

`lace upgrade` treats upgrades in three categories:

1. Engine dependencies and container image tags can be updated automatically.
2. Generated infrastructure files can be updated only when their recorded hash proves that the user has not changed them.
3. User-owned files are never silently rewritten. Required changes are supplied as migration instructions or explicit codemods.

Block-source updates are a separate command: `lace add block` updates installed
registry items, while `lace upgrade` updates the template's managed files. Both
share one three-way hash decision, diff, and guarded atomic-write implementation
in `@lacecms/cli`. `lace add block` needs no rollback journal: every write is
compare-and-swap, `lace.site.json` is written last as the commit record, and a
re-run adopts files that already match the registry.

`.lace/manifest.json` should record the generator/template version and hashes of managed files. A modified managed file produces a diff or conflict instead of being overwritten.

Database migrations are versioned with the engine and must run as an explicit deployment step.

## 8. Content configuration

The root `lace.config.ts` is the source of truth for content structure.

```ts
import {
  builtInBlocks,
  defineCollection,
  defineConfig,
  defineGlobal,
  definePage,
  field,
} from "@lacecms/config";

export default defineConfig({
  blocks: [
    builtInBlocks.hero,
    builtInBlocks.richText,
    builtInBlocks.image,
    builtInBlocks.quote,
    builtInBlocks.cta,
  ],
  content: [
    definePage({
      key: "home",
      version: 1,
      label: "Home",
      path: "/",
      blocks: ["hero", "richText", "image", "cta"],
    }),

    defineCollection({
      key: "posts",
      version: 1,
      label: "Posts",
      route: "/blog/:slug",
      fields: {
        publishedAt: field.date({ required: true }),
        author: field.text(),
        category: field.select({
          options: ["engineering", "design", "news"],
        }),
      },
      listFields: ["category", "author"],
      blocks: ["richText", "image", "quote"],
    }),

    defineGlobal({
      key: "settings",
      version: 1,
      label: "Site settings",
      fields: {
        siteName: field.text({ required: true }),
        tagline: field.text(),
      },
    }),
  ],
});
```

The Worker and Node composition roots import `lace.config.ts` at build time. The
runtime never evaluates an arbitrary TypeScript path supplied through an HTTP
request. The normalized configuration and its serializable admin projection are
created once during application startup.

For the MVP, every snapshot has the following common system fields:

- `title` is required for every entry; for a global it is system-owned: saving
  a global always stores the model label (or key) as its title;
- `slug` is `NULL` for pages and globals (a global rejects a submitted slug);
  it may be absent from an incomplete collection draft but is required for
  publication;
- a collection route contains exactly one `:slug` segment;
- slugs use lowercase ASCII letters, digits, and single hyphens
  (`^[a-z0-9]+(?:-[a-z0-9]+)*$`); the admin may suggest a normalized slug, but
  the API validates rather than silently rewrites submitted values;
- page paths and resolved collection paths start with `/`, contain no query or
  fragment, collapse no implicit aliases, and use no trailing slash except `/`.

Configuration rejects duplicate page paths, duplicate collection route patterns,
and a page path that already matches a collection route pattern. The
`published_routes` constraint still guards runtime collisions and future route
features.

`published_routes.path` remains the final global uniqueness constraint, so two
different models cannot publish the same path even if their individual slugs
are different.

### Content-model kinds

`content_models.kind` uses domain-language values:

```ts
type ContentModelKind = "page" | "collection" | "global";
```

- `page` represents a singleton model with one fixed path and permits exactly
  one content entry.
- `collection` permits any number of content entries, each routed by its slug.
- `global` represents a route-less singleton for site-wide content such as
  site settings or a footer ([ADR 0010](adr/0010-global-models.md)). It is
  declared with `defineGlobal({ key, version, label?, description?, fields?,
  blocks? })` plus the same temporary synchronization hints as a page, and
  never has a `path`, `route` or `listFields`. A global is never served by
  path; it is read by model key.

Pages, collection entries and globals share storage, snapshot, block,
validation, and publication behavior. Model keys are unique across all three
kinds, and a model's kind is part of its structure: a kind change between any
two kinds is breaking and refused by sync, also through `renamedFrom`.

### SEO metadata

Pages and collections may opt into a per-entry SEO system group
([ADR 0011](adr/0011-seo-system-group.md)):

```ts
defineCollection({
  key: "posts",
  version: 4,
  route: "/blog/:slug",
  fields: { excerpt: field.textarea(), cover: field.media() },
  seo: { description: "excerpt", image: "cover" }, // or `seo: true`
});

defineGlobal({
  key: "settings",
  version: 2,
  fields: {
    siteName: field.text({ required: true }),
    titleTemplate: field.text(),
    metaDescription: field.textarea(),
    shareImage: field.media(),
  },
  seoDefaults: {
    siteName: "siteName",
    titleTemplate: "titleTemplate",
    description: "metaDescription",
    image: "shareImage",
  },
});
```

- The group holds `title`, `description`, `image` (a media ID), `canonical` (an
  absolute URL) and `noindex`. It is stored with each snapshot outside
  `fields`, so project field keys never collide with it, and it follows the
  draft and publish flow.
- `seo: { description?, image? }` names fallback fields of the same model: a
  `text` or `textarea` field for the description and a `media` field for the
  image. Globals cannot declare `seo`.
- At most one global declares `seoDefaults`, whose values name its own fields
  (`siteName`, `titleTemplate` and `description` are `text` or `textarea`,
  `image` is `media`). Defaults have no storage of their own.
- Whether SEO is enabled is structural; the fallback mapping and
  `seoDefaults` are projection-only, like `listFields`. A model without the
  option carries no `seo` property, so its hashes are unchanged.
- Values are plain text: `title` (at most 200 code points) and `description`
  (at most 500) are single-line, trimmed and cleared when empty; `canonical`
  is an absolute `http`/`https` URL without credentials or fragment (at most
  2,048 characters); `noindex` is stored only when `true`. The API rejects
  values above these hard limits; the admin warns earlier (60 and 160
  characters). Saving a non-null `seo` for a model without SEO fails with
  `seo_not_allowed` at `/seo`.
- Fallbacks are resolved by the SDK, never stored: title, then the entry title
  formatted by the title template (`%s`, default `%s | {siteName}`);
  description and image, then the model's mapped field, then the site
  default; canonical, then site URL plus path. `noindex` emits
  `noindex, follow` and excludes the entry from the sitemap.
- Site output (CE4B): `site.seo(entry)` returns `{ title, description?,
  image?, canonical?, robots?, siteName? }` from the pure `resolveSeo`
  function. Mapped text counts only when non-blank (whitespace collapsed); a
  title template counts only when it contains `%s` and is applied literally;
  only resolved `image/*` media count as images, with the media alt text.
  Every routable entry resolves, with or without SEO enabled on its model.
  `LACE_SITE_INDEXING=off` resolves every page to `noindex, nofollow`.
  `<LaceSeo>` renders the value (with an `og:type` prop, `website` by default),
  and the sitemap lists every indexable entry whose stored canonical, if any,
  is its own URL. The site URL comes only from `LACE_BUILD_SITE_URL`; Lace
  does not set Astro's `site` option.

### Initial field types

The MVP field DSL should support:

- text;
- textarea;
- rich text;
- number;
- boolean;
- date;
- datetime;
- select;
- URL;
- media.

Reference fields should be anticipated in the DSL design but may be postponed until after the first vertical slice. Arbitrary executable user code must not be serialized and sent to the admin application.

Reference fields are not part of the MVP. The field-definition discriminated
union and validation visitor must be exhaustive so that a reference variant can
be introduced later without changing existing field encodings.

URL fields optionally declare `embedProviders: ["youtube", "vimeo"]`, a non-empty
unique subset canonicalized in that order. The restriction is structural: adding
or narrowing it is breaking; removing or widening it is compatible. Omission
preserves ordinary URL behavior and hashes. Shared portable validation accepts
only bounded HTTPS provider video paths and canonicalizes iframe URLs locally,
preserving Vimeo unlisted hashes while dropping arbitrary playback parameters.
No provider metadata fetch or raw iframe HTML is supported.

### Internal URL links (CE10)

The owner-selected `ce10-internal-url-links` change extends ordinary URL fields
with canonical `entry:<URI-component-encoded-id>` destinations in model/global
fields and block data, including nested groups/lists. The block settings
allowlist stays select/boolean/number/text; URL fields are content, not settings. Rich
text, provider-restricted video URLs and SEO canonical URLs keep their existing
grammar; no reference-field kind is introduced and the MVP reference-field
exclusion remains. Manual URLs are not automatically converted or repaired.

The implementation adds snapshot-scoped indexed reference locations and one
graph revision updated atomically with lifecycle/schema mutations. Published
incoming links require an explicit, current impact acknowledgment before target
entry deletion or unpublication; existing authorization and singleton
restrictions remain. Configuration sync continues to refuse model removal while
entries exist; CE10 adds no model-deletion command or CLI impact override.
Drafts retain missing/unpublished target IDs,
while publication requires delivered targets to have published routes, with a
self-publication exception. Hidden-block references remain tracked but do not
block publication for unavailable targets. Each snapshot has a separate maximum
of 200 internal-reference occurrences, including hidden blocks and defaults.

One complete published export supplies build-time ID-to-path resolution. Missing
targets yield bounded warnings and non-navigating content; transport/consistency
errors remain fatal. Stored snapshots are not rewritten when a target moves or
disappears. One version 1 Link block has button/text appearance and a new-tab
setting; Hero then CTA move to the end of the admin block picker only.

The compatibility boundary is build-export format 2, with coordinated
API/admin, SDK/render/adapter and installed source adoption. Authored public JSON
values remain authored values; consumers adopting this new URL-field grammar
must resolve targets before writing hrefs. Existing manual URLs retain their
meaning. New SDKs retain format 1 support for compatible legacy exports. The
export design permits at most twelve read statements in
the existing two-batch page algorithm, superseding the previous ten-read bound. Complete D1 invocations retain the 50-statement
budget, 100 binds per statement and 40-statement guarded mutation batch ceiling.
There are no per-link DB/HTTP reads during rendering. See
[internal URL links](./internal-url-links.md) and the
[verification evidence](./verification/ce10-internal-url-links.md). The delta specs
were synchronized into accepted specs and the change archived on 2026-10-24 at
`openspec/changes/archive/2026-10-24-ce10-internal-url-links`.

### Field guidance metadata (CE9A)

Text, textarea, URL, number, select and rich-text fields accept an optional
string `placeholder`, including nested model/block fields and scalar list
items. An empty string suppresses the generic prompt; omission preserves it.
Other kinds reject the option. Descriptor placeholders are projection-only:
structural identity excludes them without removing content/default keys named
`placeholder`. Updating them needs no model-version bump or content rewrite.

### Choice-card presentation and list layouts (LIST1)

Select descriptors optionally declare `presentation: { control: "cards", choices }`.
Each option has one plain-text label, optional description and optional diagram of
1–16 nonoverlapping integer rectangles in a 12×12 canvas. This detached portable
metadata is projection-only at descriptor positions, including nested fields and
scalar settings; content/default keys named `presentation` remain structural.
Omission preserves dropdowns and existing hashes. Options/defaults retain their
structural rules. Display-only sync uses existing concurrency guards without
rewriting snapshots, audit fields or media references. Existing sync still advances
the published version and requests/coalesces a build for projection changes.

`listLayoutSettings()` exports ordinary scalar `layoutMode` (`flex-row`,
`flex-column`, `grid`; default `grid`), `layoutWrap` (default true), and
`layoutPreset` (`auto`, `columns-2`, `columns-3`, `columns-4`, `narrow-wide`,
`wide-narrow`, `featured-first`; default `auto`). Arrangement stays visible;
LIST2 shows Wrap items only for flex and Grid preset only for grid, except when
a relevant validation error requires revealing an inactive setting. Inactive
values are retained, submitted and validated unconditionally. Wrap applies to flex; vertical wrap
requires site-defined height. Presets apply to grid. Diagrams explain composition,
not a preview of site styling.

LIST2 is an explicitly selected, bounded exception to deferred conditional forms:
blocks may declare projection-only `settingsVisibility`, mapping scalar setting
keys to `{ setting, values }` predicates over an always-visible required sibling
select with a valid default. Targets/controllers must exist, option lists must
be nonempty and unique, and self references/chains/cycles are rejected. Metadata
is portable, detached and frozen. Hidden controls stay registered and their values
retain ordinary defaults, validation, permissions and public delivery. Rules do
not apply to model fields, block data, group/list items or envelope fields.
`listLayoutSettingsVisibility()` shares the list rules with arbitrary blocks.
General conditional forms and conditional validation remain deferred.

### Visual form organization (CE9B)

Models, block data and group descriptors accept optional serializable
`layout: { mode: "sections" | "tabs", groups: [{ key, label, description?, fields }] }`.
Blocks accept `settingsLayout` for declared settings. References name immediate
sibling fields only, each at most once; keys are unique field-style identifiers,
labels are nonempty, and groups and their field lists are nonempty. Invalid
shapes, unknown properties/references and layout on scalar/list descriptors fail
before startup. Groups used as list items support layout at every CE7 depth.
Unlisted fields follow the layout in declaration order. Layout creates no data
objects or paths, does not change defaults/absence or validation, and excludes
system title/slug/SEO and block envelope controls. Only projection identity
includes it; descriptor-aware structural identity preserves content/default keys
with the same names. Omitted layouts retain previous hashes and metadata.

### Bounded composite fields (CE7A)

`field.group({ fields, ...common })` describes a plain object;
`field.list({ item, minItems?, maxItems?, ...common })` describes an ordered
array of one scalar or group definition. Both are available in model fields
and block data, with recursive portable metadata and nested value inference.
They create no nested blocks, routes, item IDs or independent lifecycle.
See [ADR 0013](adr/0013-bounded-composite-fields.md).

A definition branch permits six group/list containers and two consecutive
groups. A list resets the consecutive-group count, never total depth, and may
not directly contain another list. Scalars, root maps and rich-text nodes do
not count. Definitions must be finite, detached JSON; malformed children,
cycles, unsafe composite defaults and non-portable values fail before startup.
List bounds are integers with effective defaults 0/100 and
`0 ≤ minItems ≤ maxItems ≤ 100`.

Absence selects a declared default, then recursively validates it. An absent
optional container without a default stays absent, even when descendants have
defaults or required flags. Present `{}` and `[]` override container defaults;
child defaults apply inside present groups/items. Required means presence:
a required empty list is publishable unless minItems is positive. Drafts may
omit required descendants or fall below minItems; publication enforces both.
Wrong present types, null, unknown children and sparse/undefined list elements
fail in both modes. Composite defaults may be incomplete draft starting values;
scalar descriptor default compatibility stays unchanged.

Each normalized snapshot has at most 500 list elements, summed across fields
and all block data, including hidden blocks. Nested lengths count independently
(10 categories with 20 links each consume 210). Draft/published budgets are
separate. Defaults count; rich-text arrays and block arrays do not. Fields and
each block retain the normalized JSON byte cap; nested media retain the
200-reference cap. Errors identify exact key/index paths. Hidden blocks use
draft required/minimum checks even on publication, but all maximums apply.

Canonical identity strips display metadata only at descriptor positions,
recursively; child keys and default-value keys named label/description stay
structural. Scalar-only encodings/hashes stay stable. Collection listFields,
SEO mappings and block settings retain their existing scalar restrictions.

CE7B extends CE1 synchronization recursively to group children and list items.
Named model children use sibling-key `renamedFrom`; `removedFields` accepts
schema pointers such as `/links/*/legacy`, with `*` addressing every item.
Root hints remain compatible. Ancestors are paired before descendants; no
cross-parent moves, indexed hints or implicit type conversions are supported.
Defaults fill absent keys only in present containers or containers introduced
by their own applicable default. Present values and list order/length remain.
Actual media-bearing backfills are refused, including descendant defaults.
Nested tightening uses draft/published semantics and rejects offending data.

Preparation checks the combined prospective model/block snapshot, including
hidden and unchanged blocks, JSON limits, 500 list elements and 200 media
locations. Unrelated published required absence remains grandfathered. Block
data changes still use versioned migrations: each resumable unit must also
satisfy limits in its actual intermediate state. Nested model JSON and rebuilt
`$fields` media references commit in the guarded final mutation, preserving
snapshot revisions/audit fields and the existing final version/build behavior.
Reports distinguish schema wildcard paths from concrete indexed value paths.

CE7C list descriptors optionally declare `itemLabel`, naming an immediate
text, textarea, select or URL child of a group item. It is portable presentation
metadata only: exclude it from structural identity at list descriptor positions,
include it in projection identity and preserve content/default keys of that name.
Changing it needs no version bump or migration. Summaries use plain text and
never display media IDs. CE7D ships Gallery and Navigation built on these
descriptors.

### Initial built-in blocks

The starter and browser editor ship with eight blocks. They use only the public
field DSL and do not receive special database treatment; only `image` and
`gallery` declare a setting:

- `videoEmbed` (version 1): required YouTube/Vimeo URL and accessible title,
  optional image-media poster and caption, no settings. A poster defers the
  external iframe until button activation; without it, the iframe is lazy.
  Playback never autostarts. Video-file uploads remain outside this selection;
- `hero`: optional eyebrow, required heading, optional rich-text body, optional
  media, optional primary-action label and URL;
- `richText`: one required Tiptap document;
- `image` (version 4): required media, optional alt text that overrides the
  media item's alt text, optional caption and an optional URL `link` ("Link"),
  plus the boolean setting `lightbox` ("Open full screen", default `false`).
  Version 1 required the alt text, version 2 had no setting and version 3 no
  link; all migrations return the stored data unchanged. A linked image opens
  its link in the same tab instead of the lightbox;
- `quote`: required quote text and optional attribution;
- `cta`: required heading, optional body, required action label, and required URL;
- `gallery` (CE7D/LIST1, version 4): optional title and an `images` list (default `[]`, at
  least one item to publish, at most 50) of groups with required media,
  optional alt text and optional caption that override the media item's and
  the same optional `link`, plus the same `lightbox` setting, with identity
  migrations to versions 2, 3 and 4; shared layout settings are added alongside
  lightbox in Layout/Behavior settings sections;
- `navigation` (CE7D): optional accessible `name` and a `links` list (default
  `[]`, at least one to publish, at most 20) of groups with a required label,
  an optional URL and an optional `children` list (at most 20) of groups with a
  required label and URL. The registry component renders a parent with
  children as a native `<details>` disclosure whose submenu starts with the
  parent's own URL, and marks a root-relative link to the current page with
  `aria-current="page"`.

Projects may define additional blocks in `lace.config.ts`. Custom blocks use the
generic metadata-driven admin form in the MVP; custom React admin editors are
out of scope.

### MVP content limits

Shared contract constants enforce the same limits in config validation, REST
validation, and the admin UI: title at most 200 characters, slug at most 100
characters, at most 200 top-level blocks and 200 media references per entry, and
at most 1,000,000 UTF-8 bytes in either `fields_json` or one block's `data_json`.
Individual field definitions may set stricter limits. These conservative JSON limits leave room
below D1's row/string ceiling and prevent the browser editor from creating
payloads the target runtime cannot persist.

Validation has explicit `draft` and `publish` modes. Draft validation rejects
unknown keys, wrong types, invalid present values, unsafe rich text/URLs, and
size limits, but permits a required model field to be absent so incomplete work
can be saved. Publish validation additionally enforces every `required` field and
the collection slug. `title` is the one required draft system field because it
is relational and needed by entry lists.

### Configuration projection

The API loads the executable configuration and exposes a serializable representation to the admin application. The database stores model identity and synchronization metadata, not a second authoritative copy of every field definition.

An explicit command synchronizes configuration with stored model identities:

```bash
pnpm lace content sync
```

The command:

- creates new model records;
- updates labels, versions, and configuration hashes;
- detects removals and renames;
- refuses destructive removal while entries still exist;
- reports incompatible field changes.

A collection may declare `listFields`, an ordered list of its own scalar fields
(text, textarea, number, boolean, select, date, datetime, or URL) that admin
entry lists show as columns. Rich-text and media fields are rejected: the first
is a document and the second an opaque identifier. `listFields` is presentation
metadata like labels.

Collections may independently opt into `listOptions.sortableFields`,
`filterableFields` and `searchableFields` (at most 16 distinct top-level keys
per operation). Sort/filter targets use those same scalar types; search targets
are text/textarea only. Empty options disappear. Pages/globals reject these
options. Hidden fields may be queried without appearing in `listFields`.
`listOptions` is projection-only: synchronization requires no version bump,
content rewrite, published-state advance or build when the public projection is
proven unchanged by the identity rules below. Legacy unknown identities use a
conservative one-time rebuild.

Every model definition has an integer `version` starting at `1`. Any structural
change to fields, allowed blocks, path, or route must increment it; display-only
label, description, `listFields` and `listOptions` changes do not. Sync compares two canonical
hashes: `structure_hash` excludes display metadata and `projection_hash`
includes the complete serializable projection. Display metadata means the
`label` and `description` properties of model, field, and block definitions;
field keys and default values are structural even when named `label` or
`description`. A changed structure hash without a version
bump fails; a projection-only change is safe and does not require a bump.

CQ1 adds a third, internal identity: `publicProjectionHash` hashes the same
per-model projection as `projectionHash`, omitting only the collection's root
`listOptions`. It preserves labels, `listFields`, SEO mappings and all other
existing projection inputs; consumer field/default keys named `listOptions`
remain included. The new hash is runtime/synchronization metadata, excluded
from serialized configuration and all existing hash inputs. Structural and full
projection hashes retain their prior values for configurations without options.

Synchronization persists this hash with the full projection hash it describes.
Only a valid pair whose source equals the stored `projection_hash` is a trusted
public baseline. Query-only edits update model metadata atomically without
public-state/build work; public changes, including SEO changes combined with
query edits, retain the existing atomic version advance and build coalescing.
A missing or stale baseline may be seeded without a build if the stored full
hash equals either the configured full hash or the configured public hash
(the latter proves equality to a pre-listOptions projection). Otherwise sync
rebuilds conservatively and records the new baseline. Baseline-only recording
is idempotent, and both new fields participate in stale-plan guards.

Renames are never guessed. `definePage`, `defineCollection` and `defineGlobal`
accept a temporary `renamedFrom` key. Sync performs the key migration only when the previous key
exists, the new key does not, and kind/cardinality remain compatible; the option
must be removed after all environments have applied the sync. Without that
explicit hint, a key change is treated as one addition and one removal, and the
removal is refused while entries exist.

Sync keeps the canonical structure of each model from its last successful
run as non-authoritative synchronization metadata (section 9.1). When a model
with draft or published snapshots changes structure, sync compares that
baseline with the configured structure and classifies every difference
([ADR 0007](adr/0007-schema-evolution-during-sync.md)):

| Change | Class | Behavior with existing snapshots |
| --- | --- | --- |
| Add a field; relax a constraint (`minLength`/`maxLength`/`min`/`max`, `required` → optional, new `select` option); add, change or remove a `defaultValue`; allow a new block type | compatible | apply; a declared default is backfilled into drafts and published snapshots lacking the field |
| Reorder `select` options or the block allowlist | display | apply |
| Tighten a constraint on an existing field (including optional → required and a removed `select` option) | validated | apply only if every stored value satisfies it; otherwise refuse and name the snapshots |
| Remove a field or disallow a block type | destructive | without a hint: apply only when no snapshot holds that data, otherwise refuse; with a `removedFields` or `removedBlocks` hint: prune the field values or drop the blocks |
| Rename a field (field-level `renamedFrom` hint) | destructive | move the stored values to the new key; refuse if the new key already holds data |
| Change the definition of an allowed block type | migration | without a block version increase: apply only when no snapshot holds a block of that type, otherwise refuse; with a version increase: migrate every stale block through the declared block migrations, refusing when a step is missing, a migration throws, or a result is invalid |
| Enable `seo` on a page or collection | compatible | apply; stored snapshots are unchanged |
| Disable `seo` | destructive | without a hint: apply only when no snapshot holds an SEO group, otherwise refuse (`SEO_REMOVAL_HAS_DATA`); with `removedSeo: true`: clear the groups and their `$seo` media references |
| Change a field type or an unrecognized field property | breaking | refuse |
| Change a page path or collection route | breaking | refuse while the model has published snapshots |

A required field added without a default is accepted: existing published
snapshots stay valid as published, and the next publication of each entry
enforces it. Data-dependent decisions read stored snapshots through the
repository in bounded pages; apply rejects the plan when any snapshot of a
model changed after planning. Backfill does not change snapshot revisions,
audit actors, or timestamps, and media-field defaults are never backfilled.
When a model has snapshots but no valid baseline, sync refuses a structural
change and tells the operator to restore the previous definition, synchronize
once to record a baseline, and then apply the change. Sync never guesses a
rename or silently transforms content.

Destructive changes to populated data need explicit, temporary hints: a model
field may declare `renamedFrom: "<former key>"` in its field options, and a
model may declare `removedFields` and `removedBlocks`; a page or collection
that disables SEO may declare `removedSeo: true`. Hints are excluded from
the canonical structure, both hashes and the public projection, so adding or
removing one never needs a version bump; block fields cannot declare
`renamedFrom` (block data changes use block versions). A hint takes effect only
when the model's structure changed and is checked against the baseline: a
rename applies when the former key is in the baseline and the new key is not,
is inert once applied, and is refused when both or neither key are in the
baseline; a removal hint for a key or block type absent from the baseline is
inert. In the same guarded mutation that records the model, sync moves
renamed values, prunes removed fields, drops blocks of removed types, and
moves or deletes the matching `content_media_references` rows, so media usage
and the deletion guard stay correct. These rewrites are set-based and do not
change revisions, audit actors or timestamps; renames run before backfills.
Hints are removed from configuration after every environment has synchronized.

Block data changes through block versions. A changed block definition bumps
its `version` and declares `migrations` (section 11); every model that allows
the block also bumps its own version. Sync composes the migrations from each
stored block's `schemaVersion` to the configured version and runs them in
memory during planning, so `--check` is a full dry run: each migration
receives the stored data and settings, and each result is validated against
the new definition, its data in publish mode for visible blocks of published
snapshots and in draft mode for drafts and hidden blocks, its settings with
the declared defaults applied. Results must stay within the block size and
media-reference limits and may reference only media the snapshot already
referenced. Any
missing step, failure, invalid result, or stored version newer than the
configuration refuses the plan without writing. Apply then rewrites the stale
blocks in place in guarded units of one entry — guarded on snapshot revision,
current snapshot identity and each block's stored `schema_version` — and
rebuilds their `content_media_references`. A migrated draft's revision is
incremented with the actor `system:content-sync`, so an open editor gets a
revision conflict; a published snapshot that was in sync with its draft takes
the same new revision, otherwise it keeps its revision, so entry status never
changes. Sync then prepares the plan again and runs the usual guarded final
mutation, which records the baseline, advances the published version and
coalesces one build. A stale guard stops sync before that mutation; committed
units stay, and a rerun migrates only the blocks still stale. The render core
never migrates data.

When a successful sync changes the serializable configuration visible to public
consumers, it increments `published_state.version` and requests a build in the
same atomic mutation.

Sync also ensures that every page and global model has one singleton entry. A
newly created singleton entry receives the model label as its draft title, `NULL` slug, configured
defaults, an empty block list, and the audit actor `system:content-sync`; missing
required model fields remain valid in draft mode until publication. Collections
are created only through the admin/API and require an initial title.

A non-interactive check mode should be available for CI:

```bash
pnpm lace content sync --check
```

## 9. Content data model

All primary IDs should be application-generated sortable string IDs, such as ULIDs. Timestamps should be UTC Unix milliseconds in the database and ISO 8601 strings in REST responses.

### 9.1 Content models

```text
content_models
├── key                 TEXT PRIMARY KEY
├── kind                TEXT NOT NULL CHECK(kind IN ('page', 'collection', 'global'))
├── label               TEXT NOT NULL
├── config_version      INTEGER NOT NULL
├── structure_hash      TEXT NOT NULL
├── projection_hash     TEXT NOT NULL
├── public_projection_hash        TEXT NULL
├── public_projection_source_hash TEXT NULL
├── structure_json      TEXT NULL
├── structure_json_hash TEXT NULL
├── created_at          INTEGER NOT NULL
└── updated_at          INTEGER NOT NULL
```

`structure_json` holds the canonical structure of the model as of the last
successful sync and `structure_json_hash` the structural hash it was written
for. The baseline is valid only while `structure_json_hash` equals
`structure_hash`; it is synchronization metadata, never an authoritative copy
of the configuration.

`public_projection_hash` records the model's public-projection identity and
`public_projection_source_hash` the full `projection_hash` it was computed for.
Both are nullable for legacy records. A mismatched source invalidates the public
baseline, including after an older binary changes the full projection during a
rollback. An additive migration adds these columns on Node and D1 without
rewriting content, backfilling snapshots or adding query indexes. Sync populates
both fields in its existing guarded final mutation; migration itself changes no
published-state version or build work.

`key` is a stable programmatic identifier. Labels may change freely. Renaming a key is a migration, not a display-name edit.

### 9.2 Content entries

```text
content_entries
├── id                    TEXT PRIMARY KEY
├── model_key             TEXT NOT NULL REFERENCES content_models(key)
├── singleton_key         INTEGER
├── draft_snapshot_id     TEXT
├── published_snapshot_id TEXT
├── created_by            TEXT NOT NULL
├── created_at            INTEGER NOT NULL
└── updated_at            INTEGER NOT NULL
```

`draft_snapshot_id` is nullable at the SQL level only to break the insertion cycle between a new entry and its first snapshot. Entry creation inserts the entry, inserts its draft snapshot, and assigns the pointer atomically. Application code treats a committed entry without a draft as invalid. `published_snapshot_id` remains nullable until the first publication.

The API sets `singleton_key = 1` for pages and globals and `NULL` for collection entries. SQLite permits multiple `NULL` values in a unique index, so this partial index enforces a single entry per page or global model:

```sql
CREATE UNIQUE INDEX content_entries_singleton_idx
ON content_entries(model_key)
WHERE singleton_key = 1;
```

Additional index:

```sql
CREATE INDEX content_entries_model_idx
ON content_entries(model_key);
```

The application still validates model cardinality and treats the index as the final consistency guarantee.

### 9.3 Content snapshots

```text
content_snapshots
├── id                  TEXT PRIMARY KEY
├── entry_id            TEXT NOT NULL REFERENCES content_entries(id)
├── revision            INTEGER NOT NULL
├── slug                TEXT
├── title               TEXT NOT NULL
├── fields_json         TEXT NOT NULL
├── seo_json            TEXT NULL
├── schema_version      INTEGER NOT NULL
├── created_at          INTEGER NOT NULL
├── updated_at          INTEGER NOT NULL
└── updated_by          TEXT NOT NULL
```

`fields_json` contains model-specific structured fields, including composite
objects/arrays without item envelopes or separate value tables. `seo_json` holds the
normalized SEO group (section 8) as a JSON object, or `NULL` when the snapshot
has none; an all-empty group is never stored. Save, publication, revert and
duplication copy it with the rest of the snapshot. System fields involved in identity, routing, concurrency, or common queries remain relational columns.

The draft snapshot is mutable. A published snapshot is immutable to editors and can only be replaced through the publish use case or removed through the unpublish use case (section 10); configuration synchronization may rewrite its stored fields and blocks for a classified schema change (section 8), advancing the published version (atomically for field rewrites, after resumable block migrations as described in section 4.7). Reverting a draft sets the published snapshot's `revision` to the new draft revision without changing its content, so an entry whose draft equals its publication is derived as published ([ADR 0008](adr/0008-entry-lifecycle-commands.md)).

The database temporarily contains both snapshots, so text content is duplicated. This is intentional and acceptable for the D1 free-plan database limit because binary assets are excluded. Individual page payloads are split into block rows rather than constrained by one whole-page row.

### 9.4 Content blocks

```text
content_blocks
├── snapshot_id         TEXT NOT NULL REFERENCES content_snapshots(id)
├── block_key           TEXT NOT NULL
├── block_type          TEXT NOT NULL
├── position            INTEGER NOT NULL
├── schema_version      INTEGER NOT NULL
├── data_json           TEXT NOT NULL
├── anchor              TEXT NULL
├── class_name          TEXT NULL
├── hidden              INTEGER NOT NULL DEFAULT 0 CHECK (hidden IN (0, 1))
├── settings_json       TEXT NOT NULL DEFAULT '{}'
├── created_at          INTEGER NOT NULL
└── updated_at          INTEGER NOT NULL

PRIMARY KEY(snapshot_id, block_key)
```

Indexes:

```sql
CREATE INDEX content_blocks_snapshot_position_idx
ON content_blocks(snapshot_id, position);

CREATE UNIQUE INDEX content_blocks_snapshot_anchor_idx
ON content_blocks(snapshot_id, anchor) WHERE anchor IS NOT NULL;
```

The block envelope ([ADR 0012](adr/0012-block-envelope.md)) holds presentation
values outside the block data: an optional in-page `anchor`, an optional CSS
`class_name`, a `hidden` flag and the `settings_json` the block definition
declares (section 11), stored with defaults applied. Every block copy (publish,
revert, duplicate) and every block write (save, sync migration) lists these
columns on both runtimes. Migration `0009` added them without a rebuild;
existing blocks read as visible, without an anchor or class, with `{}`
settings.

`block_key` is stable across draft and published copies. The composite primary key allows a published snapshot to be copied using one `INSERT ... SELECT` statement without generating new per-row IDs.

Block-specific data, including bounded groups/lists, remains JSON and is
validated by the block registry. Composite data does not expand the settings
allowlist. A block type does not receive a dedicated SQL table or columns.

### 9.5 Block ordering and nesting

The MVP uses sparse integer positions such as `1000`, `2000`, and `3000`. Inserting between two blocks normally changes only the inserted block. Positions are normalized when there is no safe gap.

The MVP supports a flat top-level block list. A block may contain its own bounded nested data in `data_json`, but arbitrary parent/child block trees are out of scope.

A block anchor is unique within an entry: entry validation rejects a repeated
anchor (`duplicate_block_anchor`), hidden blocks included, and the partial
unique index enforces the rule per snapshot. A draft and its published copy
therefore share anchors. A save deletes the draft's block rows before inserting
them again, so swapping anchors between two blocks never collides.

All draft mutations are atomic at snapshot scope. A successful mutation changes
the draft fields and complete ordered block list, increments
`content_snapshots.revision` exactly once, and updates `updated_at` and
`updated_by`. There is no state in which block rows have changed while the draft
revision has not. This invariant is required by optimistic concurrency and the
D1 publication batch.

### 9.7 Media

```text
media
├── id                  TEXT PRIMARY KEY
├── storage_key         TEXT NOT NULL UNIQUE
├── filename            TEXT NOT NULL
├── mime_type           TEXT NOT NULL
├── size                INTEGER NOT NULL
├── width               INTEGER
├── height              INTEGER
├── metadata_json       TEXT NOT NULL      -- reserved, always '{}'
├── alt                 TEXT               -- at most 1,000 characters
├── caption             TEXT               -- at most 2,000 characters
├── focal_x             REAL               -- 0..1, set together with focal_y
├── focal_y             REAL               -- 0..1, set together with focal_x
├── status              TEXT NOT NULL CHECK(status IN ('active', 'deleting', 'delete_failed'))
├── last_error          TEXT
├── created_by          TEXT NOT NULL
├── created_at          INTEGER NOT NULL
└── updated_at          INTEGER NOT NULL
```

Content stores `mediaId` references. Storage URLs may be derived or signed and should not be treated as permanent database identity.

Because media IDs occur inside validated JSON, Lace maintains a relational
projection of those references:

```text
content_media_references
├── snapshot_id         TEXT NOT NULL REFERENCES content_snapshots(id)
├── source_key          TEXT NOT NULL
├── field_path          TEXT NOT NULL
├── media_id            TEXT NOT NULL REFERENCES media(id)
└── created_at          INTEGER NOT NULL

PRIMARY KEY(snapshot_id, source_key, field_path)
```

`source_key` is `$fields` for snapshot fields, `$seo` (with `field_path`
`image`) for the SEO image, or the stable block key for block data. Block keys
never start with `$`. Root scalar media paths remain their field keys. Nested
locations use RFC 6901 pointers relative to their source (`/images/0/image`),
with field keys for groups and zero-based list indices. Saves atomically rebuild
the complete projection after list reorders/removals; lifecycle copies retain
nested JSON and references, remapping duplicated block source keys. Usage
locations carry these paths; hidden-only media remains protected but excluded
from public delivery. An index on `media_id` makes deletion checks bounded. Draft saves rebuild
the draft snapshot's reference projection in the same atomic mutation;
publication copies it with `INSERT ... SELECT`. A media item may be selected only
while its status is `active`.

The same projection is the only source of media usage. An entry uses an item
when its current draft or current published snapshot references it in an entry
field, a block field or its SEO image. Every admin media DTO carries `usageCount`, the number
of distinct using entries, and the media detail read lists up to 50 of them with
each location and whether the draft, the published version, or both use it.
Because only current snapshots keep references, usage and the deletion guard
always agree: an item is refused deletion exactly when its `usageCount` is
greater than zero.

`width` and `height` are the displayed dimensions, measured after the image's
EXIF orientation is applied. Every upload records both values.

Media carry optional descriptive metadata that every usage of the item shares:
`alt` text, a `caption`, and a `focalPoint` `{x, y}` whose coordinates run from
0 to 1 across the displayed image, with `{0, 0}` at the top left. The database
enforces the lengths, the coordinate range, and that both coordinates are set
or both are `NULL`; `metadata_json` stays reserved. Uploads leave all three
values unset. The metadata update command (`media:write`) edits only `active`
items. Values are plain text: trimmed, cleared when empty, free of control
characters (the caption may contain line breaks), and counted in Unicode code
points. A writer edits the version identified by `updatedAt`: the strong
`If-Match` tag is its Unix milliseconds, a stale tag fails with
`MEDIA_UPDATE_CONFLICT` (HTTP `409`), and every committed update moves
`updated_at` to the later of now and the previous value plus one millisecond.
A submission that changes nothing writes nothing.

Metadata is global and goes live on the next build: when a current published
snapshot references the item, the same atomic mutation increments
`published_state.version` and enqueues or coalesces a site build with the
reason `media_metadata`. Published snapshots are not rewritten and no
republication is needed. Metadata used only by drafts changes neither the
version nor build work. The effective alt text of a usage is the usage-level
alt (for example the `image` block's `alt`), then the media item's `alt`, then
an empty string; missing alt text never blocks publication
([ADR 0009](adr/0009-media-metadata.md)).

Media deletion is asynchronous and recoverable. The delete use case refuses a
referenced item with `MEDIA_IN_USE` (HTTP `409`), marks an unreferenced item
`deleting`, and writes a
`media.delete.requested` outbox event atomically. The dispatcher deletes the
object and then the metadata row; failures set `delete_failed` and remain
retryable. This avoids either a dangling published reference or an unrecoverable
SQL/object-storage half-delete.

A writer may also delete an item that only drafts use. The delete request's
`detach=drafts` option (`media:write` plus `content:write`) first refuses, with
`MEDIA_IN_USE` and before any change, an item that a current published snapshot
uses or that more entries use than the 50-entry usage read returns. It then
removes the item from each using draft — a media value is cleared, a media list
element is removed, an SEO image is cleared, in entry fields and in visible and
hidden blocks — through an ordinary guarded draft save by the requesting actor,
and finally requests deletion through the unchanged guard above. Published
snapshots are never rewritten, so detaching requests no build. Each draft save
is atomic on its own: a revision conflict or a newly committed reference stops
the request, earlier drafts stay detached, and the item stays `active` for a
retry. The admin offers this only when the loaded usage lists every using entry
and none uses the item in a published version; when only a published version
still uses it, the panel says that publishing or unpublishing the entry
releases it.

The default upload limit is 10 MiB. The initial allowlist is JPEG, PNG, WebP,
GIF, and AVIF; SVG is excluded because safely sanitizing active XML is outside
the MVP. The server verifies magic bytes rather than trusting the multipart
content type or filename and stores a generated object key, never a user path.
The limit and allowlist may be narrowed through deployment configuration but not
expanded without a corresponding validator implementation. Every format is
verified by walking its complete container structure without decoding pixels.
A GIF (GIF87a or GIF89a, static or animated) is walked through its header,
logical screen descriptor, optional global and local color tables, every
extension and image block with its data sub-blocks, and its trailer, which must
be the last byte; it needs at least one frame, and every frame must lie inside
the logical screen. Its recorded dimensions are the logical screen, and the
dimension and pixel limits apply to that screen. GIFs are stored and delivered
as uploaded, never transcoded.

### 9.8 Outbox and site builds

```text
outbox_events
├── id                  TEXT PRIMARY KEY
├── type                TEXT NOT NULL
├── payload_json        TEXT NOT NULL
├── attempts            INTEGER NOT NULL DEFAULT 0
├── available_at        INTEGER NOT NULL
├── processed_at        INTEGER
├── last_error          TEXT
└── created_at          INTEGER NOT NULL

site_builds
├── id                  TEXT PRIMARY KEY
├── reason              TEXT NOT NULL
├── status              TEXT NOT NULL
├── target_version      INTEGER NOT NULL
├── published_snapshot_id TEXT
├── provider_build_id   TEXT
├── requested_by        TEXT NOT NULL
├── requested_at        INTEGER NOT NULL
├── started_at          INTEGER
├── completed_at        INTEGER
├── error               TEXT
├── provider_stage      TEXT
├── provider_checked_at INTEGER
└── provider_check_after INTEGER
```

`site_builds.status` is one closed enum. `succeeded` requires proof that the
site was published:

| Status | Meaning | Terminal |
| --- | --- | :---: |
| `pending` | Queued: debounce, waiting for a retry, not yet claimed | no |
| `running` | Lace is executing the build (VPS builder, hook call) or tracking an accepted provider deployment | no |
| `accepted` | The provider accepted the request; its outcome is not tracked | yes |
| `succeeded` | Publication proven: the VPS release switched, or the tracked provider deploy stage succeeded | yes |
| `failed` | Proven failure: attempts exhausted, builder failure, provider build or deploy failure | yes |
| `cancelled` | The provider cancelled or skipped the deployment | yes |
| `unknown` | Tracking stopped without proof: deadline, missing deployment, or no read permission | yes |

Transitions: `pending → running` when a dispatcher claims the build, on every
runtime; `running → running` when an expired lease is reclaimed (guarded, start
time kept, so no row is orphaned); `running → pending` with a safe error for a
retryable failure; `running → succeeded/failed` for the VPS builder;
`running → accepted` for a provider acceptance that is not tracked (a hook
response without an ID never becomes `succeeded`). A tracked provider
deployment stays `running` with its `provider_build_id` after its outbox event
is completed and ends in `succeeded`, `failed`, `cancelled`, or `unknown` only
through a completion naming that build and provider ID. Terminal rows are never
reopened, so a late provider result does not change `unknown`. Administrator
retry is accepted from `failed`, `cancelled`, `unknown`, and `accepted` and
creates a new request. The site's current version is the highest
`target_version` among `succeeded` builds. The nullable `provider_*` fields hold
the tracked deployment's stage, last check, and next due check; they are
internal tracking state, never provider responses or credentials.

Site output settings: the VPS builder reads optional `LACE_BUILD_SITE_URL`
(absolute HTTP(S), no credentials, query or fragment) and `LACE_SITE_INDEXING`
(`on` or `off`) from its deployment environment, refuses invalid values at
startup without echoing them, and passes configured values unchanged to the
fixed site build. Cloudflare Pages builds receive the same names as workflow
repository variables or Pages environment variables. The API keeps using
`LACE_BUILD_SITE_URL` only for "Open on site"; `LACE_SITE_INDEXING` exists
only for site builds.

Provider tracking (Cloudflare Pages, optional): the tracking start is the
completion time of the build's outbox event, so processed events of `running`
builds must be kept. Each scheduled run claims at most 5 due tracked rows
through a 60-second check lease on `provider_check_after` (guarded by build ID,
provider ID, `running`, and the selected value), reads exactly the stored
deployment, and records the closed stage (`queued`, `initialize`, `clone_repo`,
`build`, `deploy`) and last successful check. Only a successful `deploy` stage is
`succeeded`; build/deploy failure is `failed` (`provider_build_failed`,
`provider_deploy_failed`); cancel or skip is `cancelled` (`provider_cancelled`,
`provider_skipped`); missing permission, a deployment still missing after a
5-minute grace, other rejections, removed tracking settings, or the overall
deadline (default 60 minutes, configurable 5–1440) are `unknown`
(`tracking_forbidden`, `tracking_not_found`, `tracking_rejected`,
`tracking_unconfigured`, `tracking_timeout`). Transient provider errors back off
from 30 seconds to 10 minutes, never past the deadline, and never consume the
outbox retry budget. Progress is polled every 30 seconds.

The optional snapshot ID identifies the publication that initiated a request;
`target_version` is authoritative when requests are coalesced.

The global published state is represented by one singleton row:

```text
published_state
├── singleton_key       INTEGER PRIMARY KEY CHECK(singleton_key = 1)
├── version             INTEGER NOT NULL
└── updated_at          INTEGER NOT NULL
```

Every operation that changes public output increments `version` in the same
atomic mutation. The version supplies the build-export ETag and the target
version for build requests without hashing the full export on every request.
Aligning a published snapshot's `revision` during a draft revert is not a
public-output change: no renderer, SDK helper, or build step reads the
revision, and the public entry shape planned for CE3C drops it.

Outbox rows also contain `locked_at` and `locked_by` nullable columns. A
dispatcher claims only an available, unprocessed row whose lease is absent or
expired, using a conditional write. The lease prevents duplicate concurrent
dispatch while still allowing recovery after a terminated Worker or container.
The default lease is 60 seconds. Retries use full-jitter exponential backoff from
5 seconds, capped at 15 minutes, with 8 total attempts. A terminal failure marks
the event processed, preserves `last_error`, and marks its media/build aggregate
failed; an explicit admin retry creates a fresh event.

Idempotent commands use a small generic table:

```text
idempotency_records
├── scope               TEXT NOT NULL
├── key                 TEXT NOT NULL
├── request_hash        TEXT NOT NULL
├── response_json       TEXT NOT NULL
├── created_at          INTEGER NOT NULL
└── expires_at          INTEGER NOT NULL

PRIMARY KEY(scope, key)
```

For publication, `scope` includes the actor and entry ID. Reusing a key with the
same request hash returns the recorded result; reusing it with different input
returns an idempotency conflict. Expired rows are removed by maintenance work.
Keys are 8–128 printable ASCII characters and publication records expire after
24 hours. The API keeps the key optional for direct clients, while the admin UI
always sends one and reuses it for retries of the same publish action.

Build requests should be coalesced. Several publications made close together should normally result in one site build rather than one build for every entry.

The site-build debounce window is 5 seconds from the most recent coalesced
request.

There is at most one unprocessed, unlocked `site.build.requested` event. A new
publication creates it or extends its debounce deadline. A claimed event is not
modified; publications arriving after claim create the next event. This permits
at most one redundant build around a claim race while ensuring that no published
state is skipped.

```sql
CREATE UNIQUE INDEX outbox_pending_site_build_idx
ON outbox_events(type)
WHERE type = 'site.build.requested'
  AND processed_at IS NULL
  AND locked_at IS NULL;
```

Adapters coalesce with `INSERT OR IGNORE` followed by a guarded update of the
existing unlocked row; media-deletion events are never coalesced.

### 9.9 Referential actions

- deleting an entry cascades to its snapshots, blocks, media-reference rows, and
  published route after application authorization and validation;
- deleting a snapshot cascades to its blocks and media-reference rows;
- entry snapshot-pointer foreign keys use `ON DELETE SET NULL` to avoid a
  deletion cycle, while application invariants still require a committed draft;
- a content model with entries is restricted from deletion;
- `content_entries.model_key` uses `ON UPDATE CASCADE` so an explicit
  `renamedFrom` sync can change the model primary key atomically;
- a referenced media row is restricted from deletion;
- foreign-key enforcement is enabled explicitly for every Node SQLite
  connection and verified in D1 contract tests.

## 10. Content publication

Publication is an admin-only application use case in the default role policy.

Inputs include:

- entry ID;
- expected draft revision;
- authenticated actor;
- optional idempotency key.

Publication recursively validates composite required descendants/minItems and
normalized list/media/byte budgets. Revert and duplicate copy composites with
the existing snapshot/reference rules.

Publication first loads the draft, blocks, active configuration, and current
published pointer, then validates the complete candidate without writing. A
hidden block is validated in draft mode, so an unfinished block can be
published hidden; it is copied into the published snapshot with the rest of
the aggregate but never delivered (see the public responses in section 12). It
then executes the following as one guarded database transaction or D1 atomic
batch:

1. Creates the new snapshot with `INSERT ... SELECT` only if the entry still
   points to the validated draft and its revision still equals
   `expectedDraftRevision`.
2. Copies draft blocks and media-reference rows with set-based
   `INSERT ... SELECT` statements conditional on the new snapshot existing.
3. Removes the entry's old route and inserts the resolved route, also
   conditional on the new snapshot existing. A path collision aborts and rolls
   back the whole batch.
4. Updates `content_entries.published_snapshot_id` to the new snapshot.
5. Increments `published_state.version`.
6. Creates or coalesces the `site.build.requested` outbox event for that version.
7. Stores the idempotency result when a key was supplied.
8. Deletes the old published snapshot; cascading foreign keys delete its blocks
   and media-reference rows.

The adapter returns the affected-row results. If the guarded snapshot insert
affected zero rows, the use case returns `CONTENT_REVISION_CONFLICT` and treats
all conditional statements as no-ops. All ways of mutating a draft must bump the
same revision, so a candidate validated before the batch cannot be published
after any concurrent field, slug, title, or block change.

This is a specialized repository operation, not a promise that Cloudflare D1
supports an arbitrary interactive transaction callback. The application port
models atomic content mutations and publication explicitly; the Node adapter may
implement them with a normal SQLite transaction, while the D1 adapter uses
guarded SQL batches.

The mutable draft remains in place. Immediately after publication, draft and published contain equivalent data but are independent records.

The outbox dispatcher runs after commit and invokes `SiteBuildTrigger`. Failed dispatches remain recoverable and are retried with bounded exponential backoff. A scheduled recovery process must handle events left pending after a Worker or container terminates.

Content publication success and site deployment success are distinct states. The admin UI must be able to show “published, build pending” or “published, build failed.”

Deleting a draft-only entry requires `content:write`. Deleting an entry that has
a published snapshot also requires `content:publish`; the same atomic mutation
removes its public route, increments `published_state.version`, and enqueues a
build. Page entries cannot be deleted: a page singleton is defined by
configuration and is removed by removing its model from `lace.config.ts`. A page
delete request fails with `CONTENT_PAGE_SINGLETON` (HTTP `409`).

Globals follow the page lifecycle without a route
([ADR 0010](adr/0010-global-models.md)). Save, publish, unpublish and revert
apply unchanged, except that publication resolves no path and writes no
`published_routes` row, and unpublication removes only the publication. Like
every publication, publishing or unpublishing a global increments
`published_state.version` and requests a build, because any page may render
it. Delete and duplicate of a global fail with `CONTENT_PAGE_SINGLETON`, whose
message names configuration-defined singletons, and creating a second entry
fails with `CONTENT_MODEL_CARDINALITY_CONFLICT`. Saving a global stores the
model label as its title and rejects a slug.

The entry lifecycle has three further commands
([ADR 0008](adr/0008-entry-lifecycle-commands.md)):

- **Unpublish** (`content:publish`, all model kinds). Inputs: entry
  ID, expected published snapshot ID, actor, optional idempotency key (scoped
  to the entry and actor, with the publication key rules). One guarded atomic
  mutation removes the entry's route, clears `published_snapshot_id`, deletes
  the published snapshot (its blocks and media references cascade), increments
  `published_state.version`, creates or coalesces the build request, and stores
  the idempotency result. The draft and its revision are unchanged. An entry
  without a publication fails with `CONTENT_NOT_PUBLISHED`; a stale snapshot ID
  fails with `CONTENT_REVISION_CONFLICT`. The removed snapshot cannot be
  restored: republishing publishes the current draft under a new snapshot ID,
  and fails with `CONTENT_ROUTE_CONFLICT` if another entry has claimed the
  path meanwhile.
- **Revert draft** (`content:write`). Inputs: entry ID, expected draft revision,
  actor. One guarded atomic mutation, conditional on the expected draft
  revision and the publication read by the use case, copies the published
  title, slug, fields, schema version, blocks, and media references into the
  draft with set-based statements, increments the draft revision once, and sets
  the published snapshot's revision to the new draft revision. Public output,
  `published_state.version`, and build work are unchanged. An entry without a
  publication fails with `CONTENT_NOT_PUBLISHED`.
- **Duplicate** (`content:write`, collection entries only). Creates a new entry
  whose draft copies the source draft's fields and blocks with a ` (copy)` title
  suffix within the title limit, no slug, new block keys, and a rebuilt media
  reference projection. The copy is validated in draft mode, created at
  revision 1, and never published. Creation is guarded on the source draft
  revision that was read. A page or global duplicate fails with
  `CONTENT_PAGE_SINGLETON`.

## 11. Block registry and rich text

Gallery v4 adopts the shared scalar list-layout settings. Its identity migration
4 retains data/settings and lets ordinary normalization fill absent defaults;
migrations 2/3 remain. Model versions including Gallery must advance for this
structural change. Guarded resumable sync preserves draft/published/hidden content,
links, order, envelopes and lightbox, with the existing final version/build rules.

The block registry maps each `block_type` to:

- a stable key;
- a human-readable label;
- a schema version;
- a runtime validation schema;
- serializable form metadata;
- optional default data;
- optional declared settings;
- optional migration functions.

`defineBlock({ fields })` accepts bounded composite data with inferred nested
objects/arrays and portable metadata; rename hints remain forbidden at every
block-data depth.

`defineBlock({ settings })` declares presentational settings, separate from
the block content, with the field builders limited to `select`, `boolean`,
`number` and `text`; every setting declares a `defaultValue`. Settings enter
the block metadata (only when declared, so blocks without settings keep their
hashes) and therefore the structural hash: changing a setting needs a block
version increase and a migration. Stored blocks keep their settings with
defaults applied, and the admin and public block contracts carry them. Among
the built-ins only `image` and `gallery` declare a setting (`lightbox`).

`defineBlock({ version, migrations })` keys each migration by its target
version. The keys form one contiguous range ending at the block's version
(a version 1 block declares none), and each value is a pure, synchronous
function that receives `{ data, settings }` of the previous version and
returns `{ data, settings? }` of the target version; a result without
`settings` keeps the input settings.
Migrations are runtime-only: like the validator they never enter the metadata
projection, the canonical structure or any hash. Only configuration
synchronization runs them (section 8); keep a migration for as long as any
environment may still hold blocks of an older version.

```ts
defineBlock({
  type: "quote",
  version: 2,
  fields: {
    text: field.text({ required: true }),
    attribution: field.text(),
  },
  migrations: {
    2: ({ data: { quote, ...rest } }) => ({ data: { ...rest, text: quote ?? "" } }),
  },
});
```

Runtime schemas are implemented with Valibot. The public field DSL must not expose raw Valibot schemas as its serialized admin contract. A field definition produces serializable form metadata, a Valibot runtime schema, an inferred TypeScript type, and, where needed, JSON Schema.

Example conceptual API:

```ts
defineBlock({
  type: "hero",
  version: 1,
  fields: {
    heading: field.text({ required: true }),
    body: field.richText(),
    image: field.media(),
  },
});
```

Tiptap JSON is stored only inside rich-text field or rich-text block data. The entire page must not become one Tiptap document.

The allowed Tiptap node and mark set is explicit and shared by validation and
rendering. Nodes are doc, paragraph, text, heading (H1–H4), bulletList,
orderedList, listItem, blockquote, hardBreak, horizontalRule and codeBlock;
marks are bold, italic, strike, code and link. Rules have no attributes or
children. Plain code blocks have optional content containing only unmarked text
nodes (no language attribute); empty blocks are valid. Text preserves spaces,
tabs and newlines. Rules and code blocks are allowed at the document root and
inside list items and blockquotes; other nesting rules stay unchanged.
Link attributes are exactly required href and optional target `_blank` and rel
`nofollow`; absence means the current browsing context and no nofollow. Null,
empty strings, other targets and other rel tokens are invalid. The renderer adds
`noopener noreferrer` for `_blank`, followed by `nofollow` when present. Stored
JSON never needs these generated safety tokens. Ordinary URL fields stay strings.
All rich-text fields and defaults, including composite leaves and block data,
share this format, without field-specific feature sets or CE7 budget changes.
Existing H1–H3 and href-only documents keep their meaning. See
[ADR 0014](adr/0014-expanded-rich-text-format.md).

Links permit only `https:`, `http:`, `mailto:`, `tel:`, root-relative,
and fragment URLs. Raw HTML nodes, scriptable URL schemes, inline event handlers,
and arbitrary style attributes are rejected. The allowlist and URL rules have one
implementation in `@lacecms/content`; the render core's `describeRichText`
reuses it exclusively, and framework adapters escape text and render only the
resulting element description. Sites must not keep their own allowlist copies.
Consumers that read structured JSON without the render core remain responsible
for an equally safe renderer.

Sites render blocks through a block map that pairs each block definition with a
user-owned component (section 13). Block definitions used by a site are the same
`defineBlock` definitions the configuration uses; a site that cannot render a
block type, or whose definition version differs from the published block, fails
its build with the model, entry, and block identifiers.

Each block definition may carry an optional one-sentence description next to its label. Both are display metadata: they reach the admin through the block projection, change the configuration projection hash, and never change the structural hash. The built-in blocks ship with labels and descriptions. Block icons are not configuration. The admin maps the built-in types to icons and gives any other block type a default icon.

The initial admin editor should render block forms from serializable field metadata. Exact site rendering and custom React admin editors are not required for every block in the MVP.

## 12. REST API

REST product endpoints are versioned under `/api/v1`. Better Auth retains its conventional `/api/auth` base path.
The optional stateless Streamable HTTP `/mcp` adapter supports the `2025-11-25`
initialize/list/call baseline. Its closed tool set is `list_content_models`,
`list_entries`, `get_entry`, `create_entry` and `save_draft`. It reuses admin
content contracts, complete-draft validation, runtime query budgets and explicit
revision guards without loopback HTTP. Draft writes never publish or queue builds.


### Public endpoints

Representative routes:

```text
GET /api/v1/public/pages/:modelKey
GET /api/v1/public/globals/:modelKey
GET /api/v1/public/collections/:modelKey
GET /api/v1/public/collections/:modelKey/:slug
GET /api/v1/public/content/by-path?path=/blog/hello
GET /api/v1/public/build-export
GET /api/v1/public/media/:mediaId
```

Public routes return published snapshots only. Individual page, collection, path,
and media reads are anonymous and cacheable. `build-export` returns all published
entries, routes, blocks, globals, and referenced media metadata in a
build-efficient representation to avoid an N+1 request pattern during Astro
generation; it requires a read-only build token. It is delivered in bounded
keyset pages (see below) so that no single request has to build, validate, or
serialize the whole site.

Public content responses return the published entry directly, never a draft:

```text
PublicEntry = { id, modelKey, path, slug?, title, fields, blocks, publishedAt, seo? }
PublicGlobal = { id, modelKey, fields, blocks, publishedAt }

GET pages/:modelKey, collections/:modelKey/:slug, content/by-path
  -> { entry: PublicEntry, media }
GET globals/:modelKey
  -> { global: PublicGlobal, media }
GET collections/:modelKey
  -> { items: PublicEntry[], media, nextCursor? }
GET build-export[?limit=1..100]                 // first page
  -> { formatVersion, version, entries: PublicEntry[], globals: PublicGlobal[], seo, media, nextCursor? }
GET build-export?after=<cursor>[&limit=1..100]  // continuation page
  -> { formatVersion, version, entries: PublicEntry[], media, nextCursor? }
assembled export (SDK, tests)
  = { formatVersion, entries: PublicEntry[], globals: PublicGlobal[], media, seo, version }

seo (entry) = { title, description, image, canonical, noindex }   // null when unset
seo (export) = {
  models: { [modelKey]: { description, image } },               // mapped field keys or null
  defaults: { modelKey, siteName, titleTemplate, description, image } | null
}

media = { [mediaId]: { id, url, mimeType, width, height, alt, caption, focalPoint } }
```

`blocks` hold the visible blocks only, ordered by position, each as
`{ key, type, schemaVersion, position, anchor?, className?, settings, data }`
with no `hidden` key (a missing `settings` validates as `{}`; the API always
sends it). Media referenced only by hidden blocks are left out of the `media`
dictionary and are not served by the public media route, while they keep their
reference rows and stay protected by the deletion guard. Admin snapshot DTOs
return every block with `hidden` and `settings`, and create and save requests
accept the envelope with `anchor`, `className`, `hidden` and `settings`
optional, so clients that omit them keep working. Block metadata in model DTOs
carries declared `settings`. `publishedAt` is the creation time of the published snapshot.
The globals read is anonymous like the page read, reads by model key without
`published_routes`, and returns `404` for an unknown key, a page or collection
key, or an unpublished global. Public entries of models with SEO enabled carry `seo` with the stored values,
even when none is set; entries of other models and globals never carry it.
The export's `seo` section describes the fallback mappings and the defaults
global for the SDK resolver; a missing section validates as
`{models: {}, defaults: null}`, and the API always sends it. Changing it is a
configuration projection change, so the published version and the export
ETag advance with sync.
The export's `entries` hold routed entries only,
and `globals` holds every published global ordered by model key; contract
validation treats a missing `globals` as empty so older exports stay valid,
and the API always sends it.
`media` resolves exactly the media items referenced by the returned entries'
published snapshots (from `content_media_references`), keyed by ID in ascending
order; unknown values are `null`. Field and block values keep storing media IDs.
The dictionary never carries storage keys, filenames, uploaders, or lifecycle
status. Media metadata edits reach the export through the published-state
version bump of section 9.7, so the build-export ETag changes with them.

Build-export paging:

- Entries are ordered by `published_routes.path` and paged by an opaque keyset
  cursor that binds the published-state version of the first page and the
  last delivered path. Unknown query keys, an invalid `limit` and a foreign or
  malformed cursor fail with `422 VALIDATION_FAILED`.
- A page ends at `limit` entries (default and maximum 100) or before an entry
  would raise the page's stored JSON (fields, SEO, and visible block data and
  settings; on the first page also the globals) above a fixed 4,000,000-byte
  budget, whichever comes first. A page always holds at least one entry while
  entries remain, so an oversized entry is delivered alone.
- `globals` and `seo` appear on the first page only. Each page's `media`
  resolves exactly the media its own entries and globals deliver.
- Every page is read from one published state. A continuation request whose
  cursor version is no longer current, or a page read interrupted by a
  publication, fails with `409 BUILD_EXPORT_VERSION_CHANGED` and details
  `{expectedVersion, actualVersion}`; clients restart from the first page.
- The API validates every page with the strict page schema before sending it.
  The assembled export remains a shared schema for consumers and tests; the
  sum of the pages of one sequence is what other sections call "the export".

Content DTOs expose a stable absolute media URL formed from the configured
`LACE_PUBLIC_BASE_URL` plus `/api/v1/public/media/:mediaId`, never a short-lived
signed URL. The base URL is validated at startup and is never inferred from an
untrusted `Host` or forwarded header; an API composed without it serves no public
content routes. The endpoint may
stream the object or redirect to a short-lived R2/MinIO URL. Static HTML therefore
keeps a durable URL while storage credentials and object keys stay private.
The public media endpoint returns an object only when the media ID is referenced
by a snapshot that is currently published; authenticated admin media endpoints
provide draft previews. Knowing an unreferenced media ID does not publish it.

Stored media bytes never change: an upload creates a new item and metadata
edits never touch the object. Media binary responses (the public route and the
admin preview) therefore carry a strong `ETag` derived from the media ID alone,
`"m-<mediaId>"`, which a metadata edit does not change; it is separate from the
metadata `ETag` used for `If-Match` on metadata updates. The public route sends
`Cache-Control: public, max-age=86400` and the admin preview `Cache-Control:
private, no-cache`. A matching `If-None-Match` (weak comparison or `*`) gets
`304 Not Modified` with the same headers and no body, without reading object
storage; a malformed header is ignored. Authorization, eligibility and not-found
are decided first, so unpublished, deleted or invisible media never receives
`304`. Consequently a browser may keep media for up to one day after it stops
being published; unbounded or `immutable` caching is deliberately not used.

### Admin collection queries

Authenticated list reads support system sorts plus one configured `field:<key>`
or `-field:<key>` sort and JSON `filters`. Filters combine across fields with
AND; select values combine with OR. Type-specific equality, literal substring,
inclusive ranges and existence operations apply to current drafts. Missing, null
and empty strings are unset and sort last in either direction; zero and false
are present. Datetimes compare UTC instants. Per-status totals apply search and
field predicates before paging, independently of selected status. Input is
bounded to 16 filters, 50 select values and 8192 UTF-8 bytes of filters JSON.
Node/VPS keeps the 200 UTF-16-code-unit q/contains limit. Cloudflare uses a
48-code-unit upper bound plus a 50-UTF-8-byte limit on the final LIKE pattern,
including the two surrounding percent signs and escaping of %, _ and backslash.
The byte bound is authoritative for mixed scripts (for example, at most 24
ordinary Cyrillic letters fit). Text equality keeps its 200-code-unit limit
because it uses = COLLATE NOCASE rather than a LIKE pattern. All text matching
ignores ASCII case only; Cyrillic and other non-ASCII letters are case-sensitive.
The platform supplies this policy to application and persistence, and the admin
content-model response exposes listQueryLimits {maxSearchLength,
maxLikePatternBytes}, with Node values 200/null and Cloudflare 48/50. Limits are
runtime metadata, not model configuration or content hash inputs. Invalid q or
contains patterns fail before SQL at /q or /filters/<index>/value without
truncation; the admin applies the same advertised policy after metadata loads. Invalid direct requests return value-free 422
issues with precise pointers. Cursors bind canonical query operands and effective
query capabilities; labels and column order do not invalidate them. Custom
field cursors remain within the existing 4,096-character transport bound. Custom
string sorts (text, textarea, select and URL) encode a bounded entry/current-draft
identity and revision anchor plus missing rank, rather than the string value.
Continuation resolves the full typed boundary by indexed model/entry lookup and
rejects deleted, replaced or revision-changed anchors with a value-free
`422 VALIDATION_FAILED` issue at `/after`. Boundary lookup and use share a read
snapshot or equivalent atomic validity guard, including empty pages. Numeric,
boolean, date and datetime boundaries remain embedded and typed. Public and
system paging behavior and collection/export/SDK ordering remain unchanged.

Invitation and reset tokens travel only in JSON bodies, never in paths or
queries. An invalid token returns one `410` envelope (`INVITATION_INVALID` or
`RESET_INVALID`) without distinguishing unknown, expired, consumed, or revoked
tokens. `POST /api/v1/password-reset/request` always returns `202` with the same
body and schedules delivery without awaiting it.

The draft `PUT` accepts `expectedRevision` plus the complete editable draft:
`title`, `slug`, `fields`, the ordered block list and, for models with SEO
enabled, the optional `seo` group (absent or `null` stores none). Admin
snapshot DTOs carry `seo` with `null` for unset values for those models, and
content-model DTOs carry the fallback mapping (`seo`) or the defaults mapping
(`seoDefaults`). It validates and persists
that aggregate atomically and returns the incremented revision. The admin may
edit individual blocks locally, but its Save command uses this aggregate
endpoint. Granular block mutation endpoints may be added later only if they
preserve the same snapshot-revision invariant.

### Contract rules

Composite metadata describes recursive group/list alternatives in REST and
OpenAPI. Values remain plain objects/arrays with media IDs in every admin/public
entry, global and export contract. Nested validation issues use precise JSON
Pointers such as `/blocks/0/data/images/2/image`; usage `field` carries a nested
relative pointer or an unchanged scalar key. SDK parsing preserves nested data
and resolves nested media through the existing published dictionaries/helpers.

- Requests and responses use shared Valibot runtime schemas.
- Public read representations (public entry, global, block, media, SEO
  value, export SEO section, the page/global/list responses, the build export
  and the error envelope) are defined once and derived into two variants. The
  **strict** variant rejects unknown keys; the API validates every public
  response with it, OpenAPI describes it, and tests assert it. The
  **tolerant** variant strips unknown keys while enforcing the same required
  keys, types and constraints; `@lacecms/sdk` parses responses with it, so a
  newer API that adds keys does not break an older site build. Consumer-owned
  JSON (`fields`, block `data` and `settings`) passes through unchanged, and
  the tolerant error envelope accepts any non-empty error code. A delivered
  block carrying `hidden` is rejected by both variants, never stripped, so a
  faulty server cannot make a hidden block render. Request and admin schemas
  have no tolerant variant.
- The build export carries a required `formatVersion` (currently `1`). The
  strict schema accepts only the current version; the SDK rejects a newer one
  with an upgrade message.
- Hono request validation uses `@hono/standard-validator`, keeping route integration based on Standard Schema rather than a validator-specific Hono API.
- Database rows are never exposed directly as API DTOs.
- Errors use one stable machine-readable envelope. Validation failures,
  including content validation while creating, saving, or publishing an entry,
  return `422 VALIDATION_FAILED` with one issue per failure: its code, a
  message that never repeats the submitted value, and a JSON Pointer such as
  `/blocks/0/data/body` or `/fields/summary`.
- Collection lists use cursor pagination. Admin entry lists accept `q` (title
  or slug substring), `status` (`draft`, `published`, or `changed`, derived from
  the draft and published revisions), and `sort`; cursors are bound to the
  query that produced them, and each page carries per-status totals.
- Admin entry summaries and entry responses name the last editor with an `id`
  and `displayName`, so lists never render raw user IDs. Public and
  build-export DTOs never carry display names.
- The admin media list accepts `q` (filename substring), `type` (an allowed
  image MIME type), and `sort` (`createdAt`, `filename`, or `size`, either
  direction; default newest first), with cursors bound to that query. Media
  DTOs name the uploader as `createdBy` with an `id` and `displayName`, and
  carry `usageCount` and the `alt`, `caption`, and `focalPoint` values that are
  set. `GET /api/v1/admin/media/:mediaId` adds the bounded `usage` list (each
  location is a model field, a block field, or `{source: "seo", field:
  "image"}`) and an
  `ETag` of the item's `updatedAt` in Unix milliseconds.
- `PATCH /api/v1/admin/media/:mediaId` (`media:write`) takes a strict body with
  any of `alt`, `caption`, and `focalPoint` (`null` clears a value) and requires
  that `ETag` as a strong `If-Match`. It returns `{media, build}` with the
  existing build dispatch outcome and the new `ETag`.
- Mutable operations use optimistic concurrency through a revision or `If-Match` value.
- Publish operations are idempotent.
- Dates in JSON use ISO 8601 UTC strings.
- Build export supports conditional requests with an ETag derived from
  `published_state.version`. `If-None-Match` applies to the first page only
  (`304` without loading content); continuation pages ignore it. Every `200`
  page carries the strong ETag of the version it was read at.
- Build tokens are random opaque credentials stored only as hashes, have only a
  `content:build:read` capability, and are accepted only by build-oriented public
  endpoints. They cannot be exchanged for a browser session.
- OpenAPI output is generated from the same route contracts through `hono-openapi` and `@valibot/to-json-schema`, rather than maintained separately.

Example error:

```json
{
  "error": {
    "code": "CONTENT_REVISION_CONFLICT",
    "message": "The draft was modified by another request.",
    "details": {
      "expectedRevision": 12,
      "actualRevision": 13
    }
  }
}
```

## 13. Site rendering and block installation

Sites consume Lace through three layers ([ADR 0006](./adr/0006-shared-rendering-core-and-installed-block-source.md)):

1. framework-neutral loading in `@lacecms/sdk` and parsing/rich-text description
   in `@lacecms/render`;
2. a thin framework adapter (`@lacecms/astro`) that renders those results;
3. user-owned visual block source installed from the block registry.

This section fixes the public names, inputs, outputs, error behavior, and
server-only constraints that Step 30 implements. Exact DTO fields and spec
wording belong to the implementing OpenSpec changes. Since CE3C the public wire
schema is published-only (section 12): the former v1 representation, which
reused the content-entry schema with a `draft` mirroring the publication, was
replaced during alpha together with the SDK, the template version, and the
upgrade notes ([ADR 0009](./adr/0009-media-metadata.md)).

### 13.1 SDK client

`@lacecms/sdk` is a small fetch-based client usable during site builds and by
external consumers.

```ts
const lace = createLaceClient({
  baseUrl: env.LACE_API_BASE_URL,
  token: env.LACE_BUILD_TOKEN,
});

const home = await lace.getPage("home");
const settings = await lace.getGlobal("settings");
const posts = await lace.getCollection("posts");
const exportData = await lace.getBuildExport();
const firstPage = await lace.getBuildExportPage({ limit: 1 });
```

`getBuildExportPage()` reads one tolerant-validated page. `getBuildExport()`
reads the first page (conditionally when given an ETag), follows every
`nextCursor`, checks that all pages agree on `version` and `formatVersion`,
continue the path order, carry `globals`/`seo` only on the first page and
resolve each media ID identically, and returns the assembled export with the
first page's ETag. When a page fails with `409 BUILD_EXPORT_VERSION_CHANGED`
it restarts from an unconditional first page, at most two traversals in total,
unless the caller disables restarts.

The build token is read-only and may access published content only. It must not
grant admin-session capabilities, and it is used only in server-side build or
dev-server code, never in client bundles.

### 13.2 Published-site loader

`createPublishedSiteLoader(options)` in `@lacecms/sdk` returns a
`PublishedSiteLoader`, a function resolving to a `PublishedSite`. It imports no
framework and never reads `process.env` or `import.meta.env` itself.

- **Input:** an `environment` record (`LACE_API_BASE_URL`, `LACE_BUILD_TOKEN`,
  `LACE_PUBLIC_BASE_URL`, `LACE_EXPECTED_PUBLISHED_VERSION`,
  `LACE_BUILD_SITE_URL`, `LACE_SITE_INDEXING`) and/or explicit `baseUrl`,
  `token`, `publicBaseUrl`, `expectedPublishedVersion`, `siteUrl` and
  `indexing` values that take precedence; an invalid site URL or indexing
  value fails with `missing_configuration` without echoing it; optional `fetch`; `revalidate` (default `false`); optional
  `hints` keyed by error code that are appended to error messages.
- **Static mode** reads one build export (one complete page traversal) per
  loader, shared by concurrent callers, and forgets a failed traversal so the
  next call restarts from the first page.
- **Revalidate mode** (dev servers) issues an ETag-conditional first-page read
  on each call; concurrent calls share one in-flight read, `304` reuses the last
  view without further page requests, and a changed first page starts a
  complete traversal.
- **Consistency:** when an expected published version is configured, the
  loader compares it with the first page's version before requesting any
  continuation page, disables traversal restarts, and maps a difference or a
  `BUILD_EXPORT_VERSION_CHANGED` page failure to `version_mismatch`. Without an
  expected version, restarts are enabled and exhausted restarts fail with
  `version_mismatch`, stating that content kept changing during the export.
- **Output:** `PublishedSite` with `version`, `byPath(path)`,
  `entries(modelKey)` (sorted by path; empty for an unknown model),
  `bySlug(modelKey, slug)`, `global(modelKey)`, `mediaUrl(mediaId)`,
  `media(mediaId)`, and `image(mediaId, usageAlt?)`. `global()` returns a
  `PublishedGlobal` (`id`, `modelKey`, `publishedAt`, `fields`, ordered
  `blocks`, and the same `media()` and `image()` lookups) or `undefined` when
  the global is not published, so layouts can fall back to static values.
  `url` is the site URL with a trailing slash (or `undefined`), `indexing` is
  `false` only for `LACE_SITE_INDEXING=off`, `urlFor(path)` joins a public path
  under the site URL (keeping its base path), `allEntries()` lists every
  published entry by path, and `seo(entry)` resolves the entry's SEO metadata
  (section 8) from the export's `seo` section and the published defaults
  global. The SDK also exports the pure `resolveSeo` and the framework-neutral
  `renderSitemapXml(site, { include? })` (`undefined` without a site URL) and
  `renderRobotsTxt(site)`. Lookups return `undefined` when absent so routes
  choose between 404 and failure. `PublishedEntry` exposes `id`, `modelKey`,
  `path`, optional `slug`, `title`, `publishedAt`, `fields`, ordered `blocks`
  (`PublishedBlock`: `type`, `key`, `position`, `schemaVersion`, `data`,
  `settings` and optional `anchor` and `className`; hidden blocks are never
  delivered), typed
  from contract DTOs, and the same `media()` and `image()` lookups over the
  export's media dictionary. `image()` returns the resolved item with the
  effective alt text: the non-blank usage alt (such as the `image` block's
  `alt`), then the media alt, then `""`. Resolved media URLs use
  `LACE_PUBLIC_BASE_URL` when the site configures it and the export's URLs
  otherwise; `mediaUrl()` returns the resolved URL of a known ID. Each
  resolved item also carries `sourceUrl`, its public media URL under
  `LACE_API_BASE_URL` (the origin the build already reaches), from which site
  builds fetch originals for image variants; the loader option
  `optimizeImages: false` leaves it out. No draft-shaped property exists on
  the view.
- The loader trusts the CMS-resolved `path`, never re-derives route patterns or
  names model keys, and rejects duplicate paths, duplicate slugs within a
  model, duplicate global keys, and a global key shared with an entry.
- **Errors:** `LacePublishedSiteError` (a `LaceSdkError`) with stable codes
  `missing_configuration`, `rejected_token` (HTTP 401/403), `api_unavailable`
  (transport failure), `version_mismatch`, and `invalid_export`. Other SDK
  errors propagate unchanged. Messages are project-neutral and never include the
  token; generated projects pass hints that name their own commands.

### 13.3 Render core

`@lacecms/render` depends only on `@lacecms/content`. Composite parsing reuses
shared publish validation, defaults and standalone block budgets; component
props preserve nested inference and errors retain numeric item paths. It does
not claim to validate fields/hidden blocks absent from its rendering input.

- `BlockContext` identifies a block in errors: `modelKey`, `entryId`, `blockKey`.
- `parseBlock(definition, block, context)` validates `block.data` with
  `validateBlockData` in publish mode, applies definition defaults, and returns
  typed `BlockDataValues`. It works for built-in and user `defineBlock`
  definitions, fails when the block type differs from the definition, and fails
  when `block.schemaVersion` differs from `definition.version`; the render core
  never migrates block data.
- `defineBlockMap(entries)` accepts a record keyed by block type whose values
  are `{ definition, component }`, generic over the adapter's component type,
  rejects a key that differs from its definition type, and returns a frozen
  map. `resolveBlock(map, block, context)` returns the entry or fails on an
  unknown block type, which preserves the build-failure behavior for blocks a
  site cannot render. `prepareBlocks(map, entry, mediaUrl)` leaves out every
  block marked `hidden` before resolving it (a defensive skip: public blocks are
  never hidden), then resolves and parses the remaining blocks in order and
  returns each mapped component with its `BlockProps`, so adapters only render
  the result. `RenderableBlock` carries optional `anchor`, `className`,
  `hidden` and `settings`, so the public and the admin block DTOs both satisfy
  it. A `RenderableEntry` may
  carry `media(mediaId)` resolving its media; `PublishedEntry` does.
- `parseBlockEnvelope(definition, block, context)` checks the anchor with
  `isBlockAnchor`, normalizes the class name with `normalizeBlockClassName`
  and validates the settings with `validateBlockSettings`, applying every
  declared default to a missing or partial record.
- `BlockProps<Definition>` is the prop contract every adapter passes to a block
  component: `block`, parsed `data`, typed `settings`
  (`BlockSettingsOf<Definition>`, every declared key present, `{}` without
  declared settings), `anchor` and the normalized `className` when the block
  has them, `context`, `mediaUrl`, and `image(mediaId, usageAlt?)`. Components
  place `anchor` as their root `id` and merge `className` into their root
  `class`; there is no wrapper element. `image()` returns an `ImageDescription`
  (`src`, effective `alt`, and when known `width`, `height`, `caption`,
  `mimeType`, the build `sourceUrl`, and an `objectPosition` of `X% Y%` from
  the focal point) so blocks avoid layout shift and honour the focal point. An entry without resolved media falls back
  to `mediaUrl` and the usage alt; an unresolved ID on an entry with resolved
  media fails with `missing_media`.
- `describeRichText(value, context?)` validates with `validateRichTextDocument`
  and returns a neutral tree of text nodes (`{ kind: "text", text }`) and
  element nodes (`{ kind: "element", tag, attributes, source, children }`).
  Tags come from a fixed allowlist, attributes are limited to safe attributes
  (a link `href` has passed `isSafeUrl`), and `source` names the originating
  node or mark. No raw HTML string is produced.
- **Errors:** `LaceRenderError` with codes `invalid_block_data`,
  `invalid_block_envelope` (anchor, class name or settings, with the field
  path), `block_version_mismatch`, `unknown_block_type`, `invalid_rich_text`,
  and `missing_media`,
  carrying the context, the field path, and the underlying
  `ContentValidationError` as `cause`. Messages name model, entry, block key,
  and field path.

`describeVideoEmbed(url, context?)` shares the content package's provider parser
and returns provider, video ID, canonical player URL and optional Vimeo hash.
Invalid URLs fail as `invalid_block_data` with context and URL field path. It
performs no network calls and leaves existing BlockProps unchanged.

### 13.4 Astro adapter

`@lacecms/astro` depends on `@lacecms/render` and `@lacecms/sdk`, declares a peer
dependency on the supported Astro range, and ships Astro component source
(copied next to its compiled module in `dist/`). It contains no visual blocks,
no client scripts, and requires no Astro integration. Override components for
`RichText.astro` are typed by the adapter's `RichTextOverrideProps`.

- `createAstroSiteLoader(options?)` (root entry, server-only) accepts `env`
  (default `process.env`), `dev` (enables revalidation), `fetch`, and `hints`,
  and returns a `PublishedSiteLoader`. Sites pass
  `{ env: { ...import.meta.env, ...process.env }, dev: import.meta.env.DEV }`
  from their loader file because `import.meta.env` is not reliably transformed
  inside externalized dependencies. The module fails fast when evaluated in a
  browser; `LACE_BUILD_TOKEN` must never reach a client bundle.
- `@lacecms/astro/LaceBlocks.astro` takes `entry`, `blocks` (the block map), and
  `mediaUrl`, resolves and parses each visible block in order, and renders the
  mapped component with `BlockProps`, including the envelope props and the
  `image()` describer bound to the entry's resolved media. It renders no hidden
  block and adds no wrapper markup.
- `@lacecms/astro/LaceSeo.astro` takes a resolved `seo` value and an optional
  `type` (`website` or `article`) and renders `<title>`, the description,
  canonical and robots tags, Open Graph (`og:image` with width, height and
  alt) and `twitter:card`, emitting nothing for absent values.
- `sitemapResponse(site, options?)` and `robotsResponse(site)` (root entry)
  return endpoint responses; without a site URL the sitemap response has no
  body, so a static build writes no `sitemap.xml`, and one build warning names
  `LACE_BUILD_SITE_URL`.
- `@lacecms/astro/LaceImage.astro` takes an `ImageDescription`, `sizes`
  (default `100vw`), `loading` (`lazy` or `eager`, which adds
  `fetchpriority="high"`), `lightbox` with a `lightboxId`, and attributes for
  the `<img>`. With a `sourceUrl` and dimensions it calls `getImage` from
  `astro:assets` for WebP variants at `min(960, W)` and `min(1920, W)` (GIFs
  become animated WebP), renders them as `srcset` with `decoding="async"`, and
  inlines a blurred SVG placeholder around a 64-pixel WebP made by the
  configured image service from the original, fetched once per build process
  and cached in `node_modules/.astro/lace/placeholders/` by source URL (left
  out for transparent images, GIFs and services without local transforms).
  Without a `sourceUrl` it renders the public URL as before. The lightbox is a
  `button` with `command="show-modal"` and `commandfor` plus a native
  `<dialog closedby="any">` holding a close button and the original public
  URL, loaded lazily; it uses invoker commands and no script.
  `laceImageConfig(env)` (root entry) returns Astro `image.remotePatterns`
  that allow only `<LACE_API_BASE_URL>/api/v1/public/media/*`. Sites declare
  `sharp`, which Astro's image service loads from the site.
- `@lacecms/astro/RichText.astro` takes `document`, optional `components` keyed
  by node or mark name, and optional `context`. It renders the
  `describeRichText` tree with Astro's escaping and never uses `set:html`;
  overrides receive only the validated element and its rendered children.
  Rules render as void `hr`, H4 as `h4`, and plain code as `pre` containing
  `code` with escaped text and unchanged whitespace. Links emit only validated
  href/target and renderer-derived rel. Both pre/code elements originate from
  codeBlock for the existing per-element override contract.

### 13.5 Block registry and `lace add block`

LIST1 registry items contain exactly one component plus optional `.css` stylesheet
companions. SchemaVersion remains 1 for manifests and locks. Sources remain
site-owned; no runtime package exports visual CSS. Gallery revision 4 imports its
own `./ListLayout.css`; all files share the item's hash/conflict protection.
Unsafe paths, symlinks, unsupported roles and case-insensitive target collisions
across selected/installed items fail before writes. A CSS conflict must not advance
the component or lock; `.new` recovery preserves the active pair.

Explicit list container/list/direct-item hooks load zero-specificity structural
rules in `@layer lace-layout`. Container widths at 32/48/64rem control grid presets;
flex preserves order and wrap without imposing height. `--lace-list-gap` defaults
to 0 and `--lace-list-item-min` to 14rem. Unmarked nested lists are untouched.
Site CSS owns decoration, image proportions and cropping, overrides the baseline,
and keeps the maintained theme's 1rem spacing and 4:3 crop. Default grid/auto uses
existing image sizes; other layouts use conservative `100vw`, tunable by the site.

Canonical block sources live in the repository `registry/` directory and are
bundled with, and versioned by, the `@lacecms/cli` release; the CLI never
fetches registry content over the network. `registry/registry.json` lists the
items, and each item lives in `registry/<framework>/<item>/` with a manifest
declaring block type, framework, block definition version, item revision,
required render-core and adapter ranges, files with their target role, and item
dependencies.

The site-local `lace.site.json` records a format version, `framework`,
`componentsDir` (default `src/components/lace`), `blockMap` (default
`src/lace/blocks.ts`), an optional `definitions` module that exports custom
block definitions, and `items` with registry version and per-file SHA-256
hashes, plus the block map file hash.

Registry item manifests (`item.json`, `schemaVersion` 1) carry `name`,
`framework`, `blockType`, `blockVersion`, `revision`, `requires`, `files`
(`source`, `target` relative to the components directory, `role`), and
`dependencies`. `lace.site.json` (`schemaVersion` 1) stores `framework`,
`componentsDir`, `blockMap`, `blockMapSha256` (`null` until Lace first writes the
map), optional `definitions` (a module path relative to the site root, only
imported, never written), `items` keyed by item name with `revision` and
`files` mapping site-relative paths to SHA-256 hashes (the item `revision` is
the recorded registry version), and optional `customBlocks` keyed by block type
with the `files` scaffolded for configured custom blocks.

The block map file imports definitions and components and exports
`blocks = defineBlockMap({...})`, with imports and entries sorted by block type
after a one-line generated-file comment. Built-in definitions come from
`@lacecms/content`; custom definitions come from the recorded `definitions`
module, which `lace.config.ts` also uses. Definitions are imported, never copied.

`lace add block <type...>` (with `--all`, `--dry-run`, `--json`,
`--site <dir>` defaulting to `site`, `--framework <key>`, and `--write-new`)
resolves item dependencies, writes component and stylesheet files, updates the
map file, checks installed package versions against item ranges, checks
built-in definition versions against `lace.config.ts`, and scaffolds a typed
component for a configured custom block that has no registry item. Ownership
and conflict rules are in section 7.

Registry components and scaffolds follow one root-element convention: the
block's `anchor` is the root `id` and its `className` follows the component's
own classes in the root `class` (`class:list={["hero", className]}`, or
`class={className}` for a root without classes). Astro omits `undefined`
attributes, so a block without an envelope renders the markup of earlier
revisions.

Built-in components carry no `<style>`; only videoEmbed carries its bounded
activation `<script>`. Presentation stays in the
site stylesheet. The `image` (revision 6), `gallery` (revision 3) and `hero`
(revision 4) components render media through `LaceImage.astro`; `image` and
`gallery` open the lightbox when their `lightbox` setting is on, with dialog
identifiers `lace-lightbox-<entry id>-<block key>[-<item index>]`, and the hero
image loads eagerly. A linked `image` block or gallery item wraps its image in
`<a data-lace-part="link">` instead, without a lightbox; the link is named by
the alt text, or by an `aria-label` of the caption, then the URL, when the alt
text is empty. The registry ships `gallery` and `navigation` (CE7D) besides
the five earlier items; every Lace-maintained site installs all seven.

The `astro/videoEmbed` registry component is the sole exception to script-free
block sources: a small local activation script replaces an inert player template
on a native preview button click and focuses its iframe, once per block. It uses
no player SDK or framework hydration. The adapter remains free of client scripts.
The optional poster uses LaceImage and ordinary media references; a companion
structural stylesheet reserves 16:9 geometry. Source links remain available with
or without JavaScript. Player URLs use youtube-nocookie.com or player.vimeo.com,
never autoplay, and keep only Vimeo's privacy hash. Rendering stays static.

### 13.6 Framework selection

Registry items, `lace.site.json`, and adapters are keyed by framework. `astro`
is implemented and is the default; `react`, `vue`, and `svelte` are reserved
keys that fail with an explicit "framework not supported yet" error, and their
adapters would be named `@lacecms/react`, `@lacecms/vue`, and `@lacecms/svelte`.

## 14. Authentication and authorization

Better Auth provides sign-in, sessions, account records, and password hashing. Invitations, password resets, and account self-service are Lace routes over the same tables. Its Drizzle SQLite schema is managed alongside the application schema.

The role is stored as a validated field on the Better Auth user record and
defaults to `viewer`; public sign-up is disabled. Only the bootstrap flow
creates an account directly. Every other account is created when its invitee
accepts an invitation issued by an administrator with `users:manage`, who also
changes roles; no administrator ever chooses another person's password. Domain and
application code receive an `Actor` value from the auth adapter and do not import
Better Auth session types.

The MVP uses global installation-level roles:

```ts
type Role = "admin" | "editor" | "viewer";
```

Authorization is permission-based internally:

```ts
type Permission =
  | "content:read"
  | "content:write"
  | "content:publish"
  | "media:write"
  | "users:manage"
  | "settings:manage";
```

Default matrix:

| Permission | Admin | Editor | Viewer |
| --- | ---: | ---: | ---: |
| `content:read` | yes | yes | yes |
| `content:write` | yes | yes | no |
| `content:publish` | yes | no | no |
| `media:write` | yes | yes | no |
| `users:manage` | yes | no | no |
| `settings:manage` | yes | no | no |

Handlers must check permissions rather than comparing role strings throughout the codebase.

The admin application follows the same rule. `GET /api/v1/admin/session` returns
the signed-in user's identifier, email, display name, role, and the permission
list computed on the server from the domain policy (`permissionsFor(role)`, the
same function that backs `hasPermission`). The admin reads its session only from
this contract-validated summary and decides every route guard, navigation item,
tour step, and screen affordance through one `can(session, permission)` check.
The role is used only for presentation. A repository test fails when admin
source compares the session role with role names, so a later change to the role
policy does not require editing admin screens.

The first administrator should be created through a one-time bootstrap command or one-time setup token. There must be no hard-coded default password.

The MVP uses a one-time setup token so the flow works identically against local
Node and remote Cloudflare deployments. `lace auth bootstrap` creates a random
token, stores only its hash and expiry, and prints the token once. While setup is
incomplete, `POST /api/v1/setup/admin` accepts that token plus email and password.
It atomically claims the token for a hash of the requested email, creates the
first Better Auth user with the admin role, and then marks setup complete and the
token consumed. A retry with the same token and email resumes safely after an
interruption; a different email cannot take over an existing claim. The endpoint
returns `404` after setup is complete so it does not remain an account-creation
surface. This guarded protocol is used instead of assuming Better Auth user
creation can join an arbitrary D1 transaction.

```text
setup_tokens
├── token_hash          TEXT PRIMARY KEY
├── expires_at          INTEGER NOT NULL
├── created_at          INTEGER NOT NULL
├── claimed_email_hash  TEXT
├── claimed_at          INTEGER
└── consumed_at         INTEGER
```

```text
installation_state
├── singleton_key       INTEGER PRIMARY KEY CHECK(singleton_key = 1)
├── setup_completed_at  INTEGER
└── setup_admin_user_id TEXT
```

Completing setup updates this singleton and consumes all outstanding setup
tokens. `lace auth bootstrap` refuses to mint another token after completion.

Build credentials are stored separately from human users:

```text
api_tokens
├── id                  TEXT PRIMARY KEY
├── name                TEXT NOT NULL
├── token_prefix        TEXT NOT NULL
├── token_hash          TEXT NOT NULL UNIQUE
├── capabilities_json   TEXT NOT NULL
├── created_at          INTEGER NOT NULL
├── last_used_at        INTEGER
└── revoked_at          INTEGER
```

Only the plaintext token is shown at creation. The initial capability set
contains only `content:build:read`.
Setup and API tokens contain 32 cryptographically random bytes encoded as
base64url. Lace stores their SHA-256 digests because the source tokens already
have high entropy; comparisons are constant-time. Human passwords remain wholly
inside Better Auth's password-hashing implementation.

Invitations and password resets use Lace-owned tokens rather than the provider's
reset flow, so Node and D1 share one lifecycle and an administrator can receive a
link once when email is not delivered:

```text
invitations
├── id                  TEXT PRIMARY KEY
├── email               TEXT NOT NULL          (normalized lower case)
├── role                TEXT NOT NULL CHECK(role IN ('admin','editor','viewer'))
├── token_hash          TEXT NOT NULL UNIQUE
├── invited_by          TEXT NOT NULL
├── created_at          INTEGER NOT NULL
├── expires_at          INTEGER NOT NULL      (72 hours)
├── accepted_at         INTEGER
├── accepted_user_id    TEXT
└── revoked_at          INTEGER
-- unique (email) where accepted_at is null and revoked_at is null

password_reset_tokens
├── token_hash          TEXT PRIMARY KEY
├── user_id             TEXT NOT NULL REFERENCES user(id) ON DELETE CASCADE
├── created_at          INTEGER NOT NULL
├── expires_at          INTEGER NOT NULL      (1 hour)
├── consumed_at         INTEGER
└── requested_by        TEXT                  (administrator, when admin-issued)
```

Both tokens are 32 random bytes stored only as SHA-256 digests. An invitation
is accepted atomically (one `better-sqlite3` transaction on Node, one guarded
D1 batch on Cloudflare): the user and credential account are created with the
invited role and the invitation is marked accepted, so concurrent acceptances
create exactly one account. Resending rotates the token and restarts the
expiry; revoking invalidates the link. Links have the form
`<LACE_PUBLIC_BASE_URL>/admin/accept-invite#token=…` or
`…/admin/reset-password#token=…`; the fragment keeps the token out of server
logs and `Referer`, and the admin screens remove it from the address bar after
reading it. When delivery is not `sent`, the invite or administrator reset
response contains the link once.

A reset request returns the same `202` for enabled, disabled, and unknown
addresses, issues a token only for enabled accounts, supersedes earlier
unconsumed tokens, and defers delivery. Confirming a reset replaces the
credential and deletes every session of the account. Passwords are hashed and
verified with Better Auth's own `hashPassword`/`verifyPassword`, so provider
sign-in keeps working. Every signed-in user can change their display name,
change their password with the current one (optionally signing out other
sessions, with a password-changed notice when email is configured), list their
sessions with a browser and OS summary but never tokens or IP addresses, and end
any other session. Administrators can sign a user out everywhere, and disabling
an account deletes its sessions as well as failing actor resolution. The
current session's identifier comes from the auth boundary alongside the actor.

The auth boundary forwards only `POST /api/auth/sign-in/email`,
`POST /api/auth/sign-out`, and `GET /api/auth/get-session` to Better Auth.
When MCP is disabled, every other `/api/auth/*` path returns `404` before the provider runs, so
provider routes such as change-password or list-sessions cannot bypass Lace
rules or reveal session tokens. Exposing another provider route is an explicit,
tested change.

MCP1 extends this boundary only when explicitly enabled. The Better Auth OAuth
provider may expose a literal, tested method/path allowlist for authorization,
consent submission, token exchange/refresh, public-client registration,
revocation and required discovery/signing-key aliases. Other provider endpoints
stay closed. Canonical issuer/resource URLs derive from validated
`LACE_PUBLIC_BASE_URL`, never request forwarding headers. Use S256 PKCE,
explicit first consent and the existing sign-in form through a short-lived,
server-bound continuation. No client-controlled URL metadata is fetched.

Browser REST actors still require sessions. Only MCP resolves resource-bound
OAuth credentials into the current persisted enabled user/role, attenuated by
an immutable provider-neutral permission and content-operation ceiling.
`content:read`, `content:write` (including read) and renewal-only `offline_access`
are the supported scopes. The shared application authorizer checks every
operation before protected work; delegated operations default to deny.
Publishing, unpublishing, deletion, revert/duplicate, media and administrative
operations are never grantable, even to an administrator. A cookie/build token
does not authenticate MCP and an MCP token does not authenticate admin REST.

Codes last at most five minutes, access tokens fifteen minutes and rotating
refresh tokens thirty days, bounded by the grant. Code redemption and refresh
must have one winner through guarded SQLite transactions or D1 batches;
refresh replay revokes the family. Durable grant state and current roles are
checked on every request/refresh without positive cross-request caching.
Credentials are hashed/encrypted at rest and signing keys, if required, durable.
Disable, password reset, administrator sign-out-everywhere and password-change
revoke-others invalidate grants alongside sessions, even with MCP disabled;
re-enabling cannot revive them. Ordinary sign-out leaves connections independent.
Owner-scoped session-only connection list/revoke routes disclose no credentials.
Additive migrations and bounded indexed cleanup reuse existing infrastructure.

MCP requests are limited to 60/minute/user, registration to 10/15 minutes/trusted
client address, token requests to 60/minute/client/address and connection revoke
to 20/hour/user, using the shared SQL limiter and `Retry-After`. Host/Origin
policy remains explicit, permitting origin-less native clients without widening
cookie trust. Bodies retain admin ceilings; logs exclude credentials, arguments
and authorization query strings. Disabling blocks issuance, renewal and use
without dropping tables or undoing account-security invalidation.

Rate limits use a portable fixed-window SQL projection so behavior does not
depend on one process or Worker isolate:

```text
rate_limit_buckets
├── bucket_key          TEXT PRIMARY KEY
├── window_started_at  INTEGER NOT NULL
├── request_count      INTEGER NOT NULL
└── expires_at          INTEGER NOT NULL
```

The key is an HMAC of operation plus the relevant actor, email, or client IP;
raw IPs and emails are not stored. Defaults are 10 sensitive auth attempts per
15 minutes, 5 setup attempts per hour, 30 upload attempts per minute per actor,
20 token-management attempts per hour per admin, 20 invitation and
administrator-reset attempts per hour per admin, and 3 reset requests per hour
per email address. Invitation inspection and acceptance, reset requests and
confirmations count against the per-client sensitive auth limit; password
changes count against the same limit per actor. Successful requests still
count. Deployments may lower these limits. Expired buckets are removed by the
same scheduled maintenance mechanism as expired idempotency rows.

Security requirements:

- secure, HTTP-only cookies in production;
- CSRF and origin protection according to Better Auth requirements;
- explicit trusted origins;
- rate limiting for authentication and upload endpoints;
- MIME type, file-size, and filename validation for uploads;
- no secrets in generated client bundles;
- same-origin admin and API deployment by default;
- audit-friendly actor IDs on all content mutations;
- the Cloudflare bundle enables the Better Auth compatibility flag required for
  `AsyncLocalStorage`, and its presence is covered by the Cloudflare smoke test.

## 15. Infrastructure ports

Representative application-facing interfaces:

```ts
interface ObjectStorage {
  put(input: PutObjectInput): Promise<StoredObject>;
  get(key: string): Promise<ReadableStream | null>;
  delete(key: string): Promise<void>;
  createReadUrl(key: string, options?: ReadUrlOptions): Promise<string>;
}

interface Cache {
  get<T>(key: string): Promise<T | null>;
  set<T>(key: string, value: T, options?: CacheOptions): Promise<void>;
  delete(key: string): Promise<void>;
}

interface SiteBuildTrigger {
  trigger(input: SiteBuildRequest): Promise<BuildTriggerResult>;
}

interface EmailSender {
  readonly provider: "none" | "log" | "smtp" | "resend" | "cloudflare";
  readonly from?: string;
  send(message: EmailMessage): Promise<EmailDeliveryOutcome>;
}
```

Implementations:

| Capability | Cloudflare | Node/VPS |
| --- | --- | --- |
| SQL | Drizzle D1 | Drizzle SQLite |
| Object storage | native R2 binding | S3 client configured for MinIO |
| Cache | Workers KV | in-memory or no-op initially |
| API runtime | Cloudflare Worker | Hono Node server |
| Build trigger | Cloudflare deploy hook | authenticated fixed-command builder |
| Deployment tracking | optional Pages API reader (Pages Read token, Worker secret) | not needed (builder result is proof) |
| Recovery dispatch | scheduled Worker | container timer/worker |
| Email delivery | Resend over `fetch`, or the Email Service `send_email` binding (Workers Paid) | SMTP through nodemailer, or Resend over `fetch` |

Email delivery is selected by `LACE_EMAIL_PROVIDER` (`none` by default, `log`,
`smtp`, `resend`, or `cloudflare`) and requires a `LACE_EMAIL_FROM` sender for
every provider except `none`. Each send resolves to `sent` or `failed` with a
closed reason (`not_configured`, `invalid_message`, `rejected`, `rate_limited`,
`unavailable`). Recipients and subjects are validated against header injection
before any provider is contacted. `log` writes messages to standard output and
is refused in production; production SMTP requires STARTTLS or implicit TLS.
Startup names invalid email variables without repeating their values, and
provider secrets never appear in logs, errors, status, or doctor output. Sends
are synchronous with a bounded timeout; there is no email outbox or retry queue.

R2 and MinIO use different concrete adapters even though both expose S3-compatible concepts. Cloudflare code should prefer the native R2 binding, while Node uses the S3 client against MinIO.

KV is a derived cache, never an authoritative source. The MVP may begin with a no-op cache where caching provides no measured value. Correctness must not depend on immediate KV consistency.

The default MVP configuration uses the no-op cache in both runtimes. A KV cache
adapter may ship as opt-in, but enabling it requires cache-key contract tests and
must not be on the critical path to the first production deployment.

## 16. Database portability and D1 constraints

The MVP supports the SQLite dialect only:

- Cloudflare D1 in production and Cloudflare-compatible development;
- a local SQLite file in Node and Docker.

Drizzle schemas and migrations should stay within the SQL subset supported by both environments.

Important D1 free-plan design constraints include:

- 500 MB maximum size for one free-plan database;
- 2 MB maximum string, BLOB, or row size;
- 50 database queries per free-plan Worker invocation;
- daily row-read and row-write quotas.

The architecture responds to those constraints by:

- placing binary media outside SQL;
- storing one block per row rather than one potentially huge page row;
- loading a snapshot's blocks in one indexed query;
- providing a bulk build-export endpoint delivered in bounded pages: each
  page request (including build-token verification) stays within the 50-query
  limit, using at most two D1 batches with at most ten range-bounded read
  statements and no identifier lists that grow with page size, while the
  4 MB stored-JSON page budget bounds memory and CPU per invocation (the
  Free-plan 10 ms CPU limit is best effort, since one maximal entry can exceed
  it);
- avoiding N+1 queries;
- copying blocks with set-based SQL;
- retaining only draft and current published snapshots;
- using focused indexes rather than indexing every field.

Collection queries execute model-scoped, prepared JSON predicates before LIMIT
on both SQLite and D1, with fixed statement counts and no application JSON scan.
Literal search/contains use bound ordinary LIKE patterns with ESCAPE, and text
equality uses = COLLATE NOCASE. ASCII case is ignored; Cyrillic case is retained
and Е/е/Ё/ё are distinct. Search policy is runtime-specific as in §12; matching
results and boundaries agree across runtimes for queries accepted by both.
No GLOB case-pair compiler, segmented/recursive matcher, ICU, FTS or persisted
search projection is introduced. String sorting retains SQLite NOCASE ordering. Configured queries may scan model drafts; the
unconfigured indexed default path remains intact. CQ1 adds only the nullable
public-projection identity columns described in §9.1; queries add no persisted
field index or content backfill. Node and actual local D1 performance evidence must cover
1,000 entries and near-limit fields; backend limits must fail visibly. String-sort
continuations may add at most one constant indexed anchor lookup, independent of
page size. No per-entry reads or full JSON loads are allowed to resolve anchors;
query counts must distinguish first pages from anchored continuations.

JSON values are stored as SQLite `TEXT` and validated before persistence. Fields that later require indexed filtering may be promoted to generated columns or a dedicated index table through a future migration.

Additive columns use a plain `ALTER TABLE … ADD` on both runtimes, as
migration `0008` does for the nullable `content_snapshots.seo_json`; it
rewrites no rows and needs no backfill. Migration `0009` adds the block
envelope columns the same way (`NOT NULL` columns carry constant defaults) and
creates the partial unique anchor index.

A migration that must rebuild a table referenced by foreign keys (for example
`0007`, which widens the `content_models.kind` check) runs
`PRAGMA defer_foreign_keys = on`, creates the replacement table, copies every
row, drops the old table and renames the replacement, all in one migration
file. D1 applies the file as one batch and accepts the deferred drop and
rename; D1 cannot switch foreign keys off. Node SQLite does not clear the
deferred violation counted by the drop, so the explicit Node migrator follows
SQLite's documented rebuild procedure instead: it suspends `foreign_keys` on
its own connection while the migrations run, runs `PRAGMA foreign_key_check`,
and fails unless the check is empty before restoring enforcement. Application
connections always keep foreign keys on.

## 17. Admin application

MCP2 (`add-mcp-settings-and-local-enablement`) adds a read-only MCP section in
Settings for administrators, visible whether MCP is enabled or disabled. The
existing authenticated Settings status response supplies the parsed enabled
state and canonical `/mcp` URL from deployment configuration. The section offers
copyable client setup examples with read-only access selected by default,
activation guidance, and a link to owned Account connections. Enabled describes
configuration, not verified client connectivity. Deployment configuration remains
operator-owned; no browser toggle or new public status endpoint is introduced.

When MCP is enabled, `/admin/mcp/consent` uses the existing session/sign-in and
controls to show escaped client identity, callback hostname and read/read-write
consent, explicitly stating the publication/unpublication/deletion ban.

hides this section when disabled; OAuth credentials never enter browser storage.

Select choice cards use generic metadata-driven native radio groups, neutral
aria-hidden diagrams, visible labels/descriptions and the existing field error/
guidance paths. Arrow keys wrap; Home/End and Space select; ordinary Tab enters
and leaves. Optional selects offer No selection. Validation summaries reveal
containing tabs/disclosures and focus the selected or first radio. Viewers see
readable choice text, and lifecycle locks prevent edits. Cards reflow at 320px
and support both themes without media requests or Gallery-specific branches.

LIST2 settings visibility is reactive within each block for writers and viewers.
Hidden control wrappers stay mounted and are absent from accessibility/keyboard
navigation. Empty setting sections/tab navigation disappear; values survive
mode switches, Save/Publish, discard/revert, duplicate/move and revision conflicts.
Relevant errors temporarily reveal inactive settings with associated explanatory
text. Summary activation opens containing tabs/disclosures and focuses the usual
control. Correction restores mode-based visibility; publication issues ignored
for hidden-on-site blocks do not force reveal. Visibility changes affect only
configuration projection; sync preserves snapshots, audit/media references and
baseline concurrency guards. Metadata updates retain existing published-version
advancement and build-request/coalescing behavior.

CE7C authors groups and lists recursively through labelled fieldsets and
repeatable controls, reusing scalar, media and rich-text controls. Lists support
Add, Remove, Duplicate, Move up/down and isolated keyboard/pointer sorting.
Groups and complex items collapse without unmounting editing state; viewers
can operate disclosures but cannot mutate values. UI item identities are
transient sidecars and never enter stored or public JSON. Explicit absence,
empty objects/arrays and shared recursive defaults retain their meanings.
Counts and prospective growth gates include normalized defaults, nested lists
and hidden blocks in the 500-element entry budget. Required/minimum guidance
is publication-only. Exact recursive errors open block tabs and all ancestor

lock content mutations so indexed errors cannot land on another item.
Save/discard, dirty checks, conflict JSON and lifecycle copies retain all
composite values; no list slots are silently removed during serialization.

CE9A displays required markers with publication-only explanations, associated
configured descriptions and applicable text, numeric and list bounds throughout
recursive forms and viewer inspection. Ordinary text/textarea counters count raw
UTF-16 units, matching their existing validators; SEO counts trimmed Unicode code
points and labels 60/160 as recommendations separately from hard limits. Counts
are not live announcements. Inherited SEO/media guidance takes precedence over

CE9B renders visual sections and accessible tabs at each field-map boundary.
Inactive panels remain mounted but hidden from focus and accessibility; nested

select containing tabs and open all disclosures before focusing the exact

Viewers can navigate without mutating content; SEO and block Content/Settings
retain their established behavior. Narrow tab strips remain keyboard accessible.

Collection creation offers an initially automatic editable slug derived from
title: NFKD, ASCII letters/digits, whitespace/underscore/hyphen collapsed to
hyphens, lowercase, trimmed boundaries and the existing length limit (trim again
after truncation). No transliteration or uniqueness promise is made; empty or
non-Latin suggestions remain empty with manual-entry guidance. Any manual slug
edit disables suggestions until explicit re-enable. Creation saves a nonempty
slug atomically and opens a clean editor. Existing entries and slugless
duplicates never enter automatic mode on load; the editor's explicit opt-in
suggestions remain available. Server route/conflict rules stay authoritative.

Core client stack:

Primary routes:

The content-model response drives navigation and field forms. Pages and globals open their singleton editor directly; collections open a paginated entry list. The model route of a page or global (`/content/<key>`) shows only a pointer back to the content overview.

The shell groups its sidebar into Pages, Collections (with entry totals from the entry-list API), Site (globals, linked to their singleton editors), Library (Media and Builds, all roles), and Admin (Users with `users:manage`, Settings with `settings:manage`), omitting empty groups, shows the signed-in user's display name and role in a user menu, and locates each screen with breadcrumbs; a page or global editor is located by Content and the model label only. The content overview has Pages, Collections and Site sections; a global's card shows its label, description, status and last edit but no path. Below the medium breakpoint the same navigation opens in a sheet. Shell surfaces never show internal entry or user IDs. Collection lists are TanStack Table views over the entry-list API: title with slug, derived status, the model's `listFields` columns, publication date, and relative last edit with the editor's display name; search, status filter, and sort live in the route's URL search parameters, while the opaque cursor pages with "Load more" and never enters the URL. Writers get a labeled "Actions for {title}" menu in each row with Open, Duplicate and Delete. Delete appears for draft-only entries, and for published ones only with `content:publish`. Creating or duplicating an entry opens it in the editor.

Collection query controls are metadata-driven: a Sort selector includes hidden
sortable fields, enabled column headers announce direction, and visible column
filter affordances open the shared Filters editor. Type-appropriate controls
validate drafts locally; invalid ranges issue no query. Active conditions are
removable, and clear-all clears search/status/filters while retaining sort.
Search hints name additional configured fields and explain the active search budget. Invalid search/contains drafts keep the last valid results and show a local error instead of issuing an over-budget query. URL shape parsing precedes
metadata-aware resolution; stale conditions are dropped independently, valid
peers survive, and reload/Back/Forward restore canonical queries. Any effective
query change resets paging. Viewer controls and loading/error/no-match recovery
remain available. If a continuation is rejected at `/after`, the list keeps its
loaded entries and offers a keyboard-accessible Restart list action. Activating
it drops cached pages/cursors and loads the first page with the current valid
search, status, sort and field filters; it never repeatedly retries the stale
cursor or appends restarted results to old pages. Recovery is available to every
read role, and no-match/reset behavior still clears predicates as documented.

The sign-in route is a centered card outside the shell: a focused email field, a password field with a show/hide toggle, errors inside the card, and a "Forgot password?" link. The accept-invite, forgot-password, and reset-password screens are the same kind of public card. Accept and reset read the token from the URL fragment, remove it from the address bar, and keep it only in component state, never in the query string, router state, query cache, or browser storage. Forgot-password shows the same confirmation whether or not the address has an account. `/account` is available to every signed-in user from the user menu: it changes the display name, changes the password (signing out other sessions by default), and lists sessions with a "This device" marker and confirmed Sign out actions. Users lists accounts with a "You" marker, role and status badges, and no raw IDs, and below them the pending invitations with Resend and a confirmed Revoke. Inviting a user, changing a role, disabling or enabling an account, sending a password reset, and signing a user out everywhere each happen in a dialog; no admin screen collects another person's password. When an invitation or reset email is not sent, its dialog shows the link once, like a new build token. A failure, including the final-administrator rule, stays in its dialog, and success is announced with a toast. The signed-in administrator is not offered Disable, Send password reset, or Sign out everywhere for their own account and is warned before demoting it. Settings shows API readiness, configured models, active build tokens, and email delivery (provider and sender, with a rate-limited Send test email action addressed only to the signed-in administrator) as status cards over a token table with relative times and a confirmed Revoke. A new token's plaintext is shown once in its creation dialog and lives only in that dialog's state. Any unmatched admin path is a protected catch-all route that renders "Page not found" inside the shell, so anonymous visitors sign in first. Every retryable read failure offers the shared "Try again" action.

The media library at `/media` follows the same URL-state rules for its filename search, type filter, sort, and grid/list view. Tiles and rows load their thumbnails lazily through the authenticated admin preview endpoint. Writers can drop files anywhere over the library or choose several at once. Each file is checked for type and size in the browser and then uploads with its own progress and server error. The default browser client sends uploads through `XMLHttpRequest` so it can report bytes sent; every other request uses `fetch`, and both paths share error mapping and response validation. A details side panel shows an item's facts, its usage from the media detail read, and its public URL. Deletion there requires confirmation and is unavailable while content uses the item.

Model and block media fields choose through a picker dialog built from the same grid, search, type filter, sort, and upload queue. Its query is local state that resets on each opening and never enters the URL. It offers only active items, and a confirmed upload can be used directly from its queue row. A field with a value shows a thumbnail card with filename, Replace, and Remove. The card resolves the stored ID through the media detail read, so it never searches loaded pages. It names pending-deletion, missing (`NOT_FOUND`), and unreadable items explicitly, and it keeps the ID in the draft until the writer replaces or removes it. The raw ID is never shown.

The editor must make draft/published/build status visible and must surface optimistic-concurrency conflicts rather than overwriting a newer draft.

The shell header stays pinned while a screen scrolls. It gives the screen an actions slot beside the breadcrumbs. The entry editor fills that slot with a save-state indicator (unsaved, saving, not saved, saved revision, or view only), one Save button, Publish for administrators, and an "Entry actions" menu for writers. Publish reads "Save and publish" while the form has unsaved changes: after confirmation it validates, saves, and publishes the saved revision with one idempotency key, and a failed validation or save publishes nothing. The entry actions menu offers only what the permissions and entry state allow (see [ADR 0008](adr/0008-entry-lifecycle-commands.md)):

- Duplicate (collections) opens the copy of the last saved draft.
- Revert to published lists what is lost: the saved draft changes since the publication, and unsaved changes. When only unsaved changes differ, it discards them locally.
- Unpublish says that the path stops working after the next build, for a page that its fixed path returns 404, and for a global ("this site content") that pages showing it fall back to their defaults. The draft and unsaved changes are kept, and the card follows the queued build.
- Delete (collections; published entries need `content:publish`) asks a published entry's title to be typed and says the page leaves the site after the next build. It returns to the collection list without the discard prompt.

Both menus are non-modal Radix menus whose confirmations open after the menu closes and return focus to the menu button. Save is bound to the draft form and to `⌘S`/`Ctrl+S`, and the shortcut always suppresses the browser's page save. The title is a large input at the top of the main column, and the blocks follow it. A global has no title input: its system-owned title is the model label, shown as static text with the model description, and its save sends the stored title unchanged. A global's publish confirmation asks to publish "this site content" and says that it affects every page that shows it after the next site build. A right-hand column, which stacks after the blocks on narrow screens, holds two cards, and a third for entries of SEO-enabled models:

- Publication: the derived status, the live and draft revisions, the last editor's display name, relative times with the absolute time on hover, the public path (omitted for a global, which has no URL and no "Open on site" link), and the latest build state. Raw IDs and ISO timestamps never appear. When the entry is published and the operator sets the optional `LACE_BUILD_SITE_URL` (returned by `GET /api/v1/admin/build-site` beside the site ID and label), the path is an "Open on site" link to that base URL; otherwise it stays text.
- Fields: the entry's slug (collections only) and model fields. In the global that declares `seoDefaults`, each mapped field says which site default it provides (site name, title template, default description or default image), for writers and viewers alike.
- SEO (CE4C): the SEO title, SEO description, SEO image (the media picker), canonical URL and a "Hide from search engines" switch, part of the draft form like any field. Every save of an SEO-enabled entry sends the complete group, with `null` for blank values; other entries send no `seo`. Title and description show a character count against the recommended 60 and 160 characters and a warning above it that never blocks saving; the API limits are validated locally and server issues under `/seo/*` map to these controls. Empty values show what the site inherits, following ADR 0011 ("Uses entry title: …", "Uses {field}: …", "Uses site description: …", "Uses this page's URL: …", and which image is shared). A search-result preview shows the resolved title, URL and description and says when the entry is hidden. Inherited values follow unsaved form values and read site defaults from the published defaults global; the admin cannot see `LACE_SITE_INDEXING`, so the preview describes the entry, not the deployment.

Until the Builds screen reads persisted builds in Step 21, the latest build state is the dispatch result of the most recent publish from the editor. The field controls are built on the shared primitives:

- Select is a Radix listbox.
- Date and datetime use a calendar popover. Datetime adds a time input in UTC, and both parse values textually so days never shift.
- Boolean is a switch.
- URL can open http(s) values in a new tab.

Controls hold a cleared value as `null` in form state, because React Hook Form would show the loaded default again for `undefined`. The editor strips those values before it saves or copies a draft. Viewers see the editor read-only: native controls sit in a disabled fieldset, rich text is not editable, media fields show their item without picker actions, and there is no Save or Publish. Publication is confirmed in a dialog that names the revision and path and can be cancelled. The discard-changes prompt is a modal alert dialog.

Blocks render as cards. A card header shows the following:

- a drag handle;
- the block's icon and label, with a *Hidden* badge (part of the card's accessible name) when the block is hidden;
- a one-line summary of its data: the first top-level text value, then rich-text plain text, then a URL or select value, then the first non-empty list or group in rendered order (a list reads as its label and item count followed by its items' summaries, such as "Links (2): Blog, About" or "Images (3)"; a group reads as its item summary), then "Media selected", otherwise "Empty block";
- the block's `#anchor` when it has one.

An expanded card has a *Content* tab with the block's fields and a *Settings* tab with its envelope ([ADR 0012](adr/0012-block-envelope.md)): an *Anchor* input validated as the writer types (format, and uniqueness within the entry including hidden blocks) with *Copy link*, which copies the entry's site URL plus `#anchor` when the build site URL and the entry path are known and `#anchor` otherwise; a *Hide on site* switch; the settings the block declares, through the field controls; and a *CSS classes* input checked with the shared class-name rule. Both panels stay mounted, the tabs use arrow keys, Home and End, and a tab whose controls have problems says so in its name. The selected tab is kept per block key. A hidden card is muted with a muted background and a dashed border, never by lowering text contrast. Viewers get no tabs: the content fields are followed by a read-only *Settings* section. Anchor and class name are held as strings in form state (empty for none) and blank values are left out of saves.

Collapsing hides only the fields, so a collapsed card stays recognizable. A block with a validation error stays expanded. The block that focus or a pointer last entered is highlighted. A block that has just been added, inserted, or duplicated is highlighted, expanded, and focused.

Each card's actions menu offers Move up, Move down, Duplicate, Hide block or Show block (announced in a status region by label and position), and Remove. A duplicate starts without an anchor. Removal leaves an inline notice with Undo, which restores the same key and data at the same place. The next structural action makes the removal final.

An insert control between adjacent blocks and an Add block button after the list open the same popover. It lists the model's allowed blocks with icon, label, and description, and it has a text filter.

Keyboard and pointer drag reordering stay on dnd-kit. The screen-reader announcements name blocks by label and position, never by key.

CE8B enables the CE8A shared format in every rich-text field, including
recursive model and block leaves: H1–H4, horizontal rules, plain code blocks
and independent new-tab/nofollow link switches. A compact selection bubble
menu supplements the complete fixed toolbar. Plain code preserves whitespace
and accepts no marks or language attributes. Ordinary paste follows the shared
safe document rules; dedicated Word/Google Docs cleanup remains deferred.

Each editable rich-text field has a fixed toolbar named after the field. It holds the following controls:

- a text style menu (Paragraph, Heading 1–4);
- Bold, Italic, Strike, and Code toggles;
- Bulleted list, Numbered list, and Quote toggles;
- a plain Code block toggle and Insert horizontal rule action;
- a Link control.

The toggles report their pressed state for the selection. The toolbar is one tab stop with arrow-key movement, `Alt+F10` moves focus from the text to it, and Escape returns. Tooltips and `aria-keyshortcuts` name each shortcut. The editor adds undo and redo and keeps Tiptap's mark, list, heading, and Markdown shortcuts. `⌘K`/`Ctrl+K` opens the link popover, which applies only URLs that pass the shared allowlist and says which forms are permitted. The Tiptap schema declares only allowlisted attributes: links carry `href` and optional `target: "_blank"` / `rel: "nofollow"`, with unchecked options omitted; lists and code blocks carry no attributes. The link popover retains the selected range while its URL and switches have focus, and permits applying, updating and removing the link. Rendering derives `noopener noreferrer`, never stores those tokens. The selection bubble offers Bold, Italic, Strike, inline Code and Link without taking focus when it appears, and disappears for collapsed selections, hidden/unfocused editors and viewers. Plain code offers no marks or links. Every document the editor produces therefore passes the shared validator. Empty fields show a placeholder, also exposed as `aria-placeholder`. Viewers get neither the toolbar nor the placeholder.

Validation problems appear where they occur. Field messages are sentences such as "Enter at least 5 characters." A block card shows its block-level problems and a "Has problems" marker: a type that is not allowed, a stale version, a key problem, data for an undefined field, or a value for an undeclared setting. Anchor, class name, and declared setting problems are shown on their Settings controls; activating one in the summary selects the Settings tab first. Summary entries name hidden blocks as hidden. A problem only publication reports (a required field) in a block that is now hidden is listed last as not blocking publication and is not counted, because publication validates hidden blocks in draft mode; every other problem in a hidden block blocks Save as usual. A block whose type the model no longer allows still renders, so it can be removed. When Save is blocked, or the server rejects a save or publish, a summary above the title takes focus. It counts the problems and links each one, in reading order, to its control or block card. The admin maps server JSON Pointers, including deep rich-text paths, to the same locations. Issues it cannot place are listed as text.

### Component source and design tokens

Admin UI components are Lace-owned source. shadcn/ui is used as a generator:
its Radix-based components are copied into the admin source once and then
edited like any other Lace code; no themed component library is a runtime
dependency. See [ADR 0005](adr/0005-admin-owned-component-source.md).

Design tokens are CSS custom properties in the shadcn naming convention
(`background`, `foreground`, `primary`, `muted`, `border`, `ring`, the
`sidebar` family, and Lace `success`/`warning` pairs) plus typography,
spacing, radius, shadow, focus, and motion tokens. One theme file in the admin
source is the only place that may contain color values; Tailwind's default
color palette is removed and components are styled only through utilities that
resolve to tokens. `pnpm lint` rejects raw color literals elsewhere in admin
source, and arbitrary utility values that stand in for a typography, radius,
shadow, focus-width, or motion token. Layout values such as widths and grid
tracks may stay arbitrary.

### Accessibility acceptance

Every admin route and main dialog is audited in the browser with axe against
the WCAG 2.x A and AA rules, and any violation fails the suite. No rule is
disabled globally. The same browser suite completes the main editorial flow
with the keyboard alone, checks visible focus along it, and checks 375px
layouts, including the entry column stacking below the blocks. The local
product acceptance walkthrough repeats the audits on real data.

The admin ships a light and a dark theme. Token values are scoped by a
`data-theme` selector on the document root, so components adopt either theme
without theme-specific source, and both token sets meet the same contrast
pairs. A System/Light/Dark preference in the user menu is remembered in the
browser's local storage; System follows the operating system's color-scheme
preference. The resolved theme is applied before the first screen renders, and
the accessibility audits run in both themes. Inter is self-hosted and body
text uses a 13px base size.

### Source layers

Admin source is organized into layers with a single import direction:

```text
app → pages → widgets → features → entities → shared
```

- `app` owns bootstrap, providers, the router tree, and global styles.
- `pages` holds one slice per route screen.
- `widgets` holds composite screen sections such as the shell or an entry list.
- `features` holds user actions such as publish, upload, or sign in.
- `entities` holds domain-facing models, queries, and presentation of content,
  media, users, and sessions.
- `shared` holds the API client, generic UI primitives, utilities, and
  configuration with no knowledge of Lace domain slices.

A module may import only from layers to its right. Slices within the same
layer do not import each other. Every slice exposes its public API only through
its `index.ts`; imports into a slice's internal files are forbidden. Every
React component lives in its own PascalCase folder containing the component,
its test, and an `index.ts`; code outside that folder imports it only through
its `index.ts`.

- `pages`, `widgets`, `features`, and `entities` are divided into slices
  (`pages/<route>`, `widgets/<section>`, …). `app` and `shared` are not sliced;
  their public units are the shallowest directories that carry an `index.ts`
  (for example `app/router`, `shared/api`, `shared/lib`, `shared/ui/Button`),
  and units of the same unsliced layer may import each other through those
  indexes.
- The source-root entry module (`main.tsx`) may import any layer's public API,
  and `test/` holds only test-environment setup. No other admin source lives
  outside the layers.
- Test files may import any layer's public API, including higher layers, so a
  page or widget test can mount the real router through the `app` test
  harness. They still may not import another unit's internal files.
- Router state is read below `app` through TanStack Router `getRouteApi` with
  string route ids typed by the `Register` augmentation in `app/router`, so no
  runtime import points upward.
- Imports are relative with explicit `.js` extensions; the admin uses no path
  aliases.

Layer direction, slice and component-folder public APIs, and component folder
completeness are enforced by `scripts/check-boundaries.mjs`, run by
`pnpm lint`.

## 18. Development modes

```bash
pnpm dev:cloudflare
```

## 20. Testing strategy

Composite verification covers typed depth-six fixtures, schema bounds 6/7 and
2/3, list-of-list refusal, values 100/101 and snapshot totals 500/501, defaults,
hidden data, exact paths, byte/media limits and scalar hash regressions. Shared
fake/SQLite/D1 contracts cover lifecycle copies, reordered/removed media,
atomic failures, concurrency, migration totals and public filtering; D1 retains
100-bind and 50-query maximum-save budgets without per-item queries.

Documentation participates in root build/typecheck/lint/test gates. Its checks
cover static links/resources, locale/version identity, production-base search
and changed-input main-only Pages publication. Builds require no CMS services.
See `docs/documentation-maintenance.md` for public/internal topic ownership.

### Unit tests

Unit tests cover pure domain and application behavior:

- page cardinality;
- model validation;
- permission policies;
- route resolution;
- block ordering;
- optimistic concurrency;
- publication state transitions;
- outbox coalescing and retry decisions.

### Repository contract tests

The same repository behavior suite must run against:

- Node SQLite;
- local D1/Miniflare.

This is more valuable than attempting to make the two Drizzle drivers look identical through an overly broad abstraction.

### API integration tests

Integration tests cover:

- authentication and authorization;
- REST schema validation;
- draft isolation;
- publish atomicity;
- route conflicts;
- media metadata and storage cleanup;
- idempotent publication;
- build-event recovery.

### Browser tests

Playwright should cover the critical editor path:

1. Sign in.
2. Open a page or collection entry.
3. Add, edit, and reorder blocks.
4. Save a draft.
5. Verify that an editor cannot publish.
6. Publish as an admin.
7. Observe build status.

### Build fixture

`apps/site` acts as the engine playground and integration fixture. CI builds it
from a seeded API export to ensure that public contracts remain compatible with
Astro generation. CI also generates a project from the packed `create-lace`
starter and builds it, so the shipped template is verified as a product, and a
parity test keeps starter, `apps/site`, and `registry/` block sources identical.

Render-core tests prove that rich-text acceptance and rejection match
`@lacecms/content` exactly and that the render core imports no framework.

## 22. Migration and compatibility policy

CE7A adds group/list variants to exhaustive TypeScript consumers. Upgrade
engine/admin/site dependencies together before adoption. No database migration
or scalar data rewrite is required. After storing composites, rollback to a
scalar-only engine needs matching configuration/database backup or an explicit
validated conversion. Recursive schema evolution is described in section 8;
admin authoring restrictions remain in section 17 until CE7C expands the editor.

The published alpha.7 release adds accepted image delivery A–D and the VPS
upload proxy fix to alpha.6. GIF originals remain unchanged; Astro builds WebP
variants, including animation, with eligible blurred placeholders and optional
lightboxes. Links on image/gallery content take precedence over lightboxes.
Upgrade API/admin, SDK, Astro/site components and builder together, review the
managed proxy/Compose/Pages files and synchronize image/gallery schemas 4/3
before the next build. No new SQL migration is introduced relative to alpha.6.
See [alpha.7 upgrade and rollback](./compatibility.md#alpha-7-upgrade-and-rollback)
for matching backups and source-component updates. Automatic database or content
schema downgrade is not promised.

The selected alpha.8 candidate packages accepted list presentation, video embeds,
internal URL links/export format 2, configurable collection queries and optional
OAuth MCP. Upgrade engine/admin/site/builder together and apply migrations
0010–0013; MCP stays disabled until explicitly activated after migration. Review
installed source and matching backups as described in
[alpha.8 upgrade and rollback](./compatibility.md#alpha-8-upgrade-and-rollback).
Preparation, publication and real deployment acceptance remain separate gates.

Compatibility exists at three boundaries:

1. Database schema version.
2. `lace.config.ts` API version.
3. REST/build-export contract version.

Database changes use forward migrations. The MVP does not promise automatic downgrade support.

Content blocks and field objects carry `schema_version`. Stored block data is migrated only by configuration synchronization through the block's declared migrations (sections 8 and 11), never when loaded or rendered. Silent destructive conversion is forbidden.

Public REST endpoints remain under `/api/v1` until a breaking contract requires `/api/v2`. Internal TypeScript types alone are not a compatibility contract.

Public contract evolution follows one policy (details in
[compatibility](./compatibility.md#public-contract-evolution)):

- adding an optional key, or a key older consumers may ignore, is compatible
  within `/api/v1` and within an export `formatVersion`;
- removing a key, changing its type, or changing the meaning of a value
  consumers rely on requires a new export `formatVersion` or `/api/v2`;
- within one major line, the API must be the same or a newer minor than the
  site's `@lacecms/sdk`;
- rich-text grammar, block `schemaVersion` matching and block data validation
  stay strict by design, because they are safety and rendering contracts, not
  transport shapes.

## 24. Decisions captured by this document

- One Lace installation manages one site.
- Astro generates the public static site.
- Hono exposes a versioned REST API.
- Valibot is the canonical runtime schema library for REST contracts, configuration, content, blocks, and admin forms.
- Hono integrates with schemas through Standard Schema validation, and OpenAPI is derived through the Valibot JSON Schema conversion path.
- The admin is a React/Vite SPA using TanStack Router and TanStack Query.
- Admin UI components are shadcn/ui-generated, Lace-owned source styled only through design tokens, organized in the `app → pages → widgets → features → entities → shared` layers.
- Drizzle uses the SQLite dialect for both D1 and VPS SQLite.
- Better Auth provides authentication.
- Authorization uses admin, editor, and viewer roles mapped to permissions.
- Only admin has `content:publish` by default.
- Tiptap is used for rich-text fields/blocks, not as the entire page document.
- `content_models.kind` distinguishes `page`, `collection` and the route-less
  singleton `global` ([ADR 0010](adr/0010-global-models.md)).
- Pages, collection records and globals share `content_entries`.
- Content has draft and published snapshots only.
- Media carry global descriptive metadata (alt text, caption, focal point);
  editing published media advances the published version without
  republication ([ADR 0009](adr/0009-media-metadata.md)).
- Routable models may opt into an SEO system group stored with each snapshot;
  one global maps site defaults, and the SDK resolves fallbacks
  ([ADR 0011](adr/0011-seo-system-group.md)).
- Blocks are separate relational rows with type-specific JSON payloads.
- Blocks carry an envelope (anchor, CSS class, hidden flag, declared settings);
  hidden blocks stay stored but are never delivered
  ([ADR 0012](adr/0012-block-envelope.md)).
- Top-level blocks are flat and sparsely ordered.
- Content models are defined in code and projected into the database.
- Configuration sync classifies structural changes against a stored baseline
  and applies compatible and validated ones to existing content
  ([ADR 0007](adr/0007-schema-evolution-during-sync.md)).
- Node uses SQLite and MinIO; Cloudflare uses D1 and R2.
- Infrastructure-specific behavior is implemented through narrow capability adapters.
- Publishing writes an outbox event and triggers a static rebuild.
- The supported onboarding path is a generator for a new/empty project.
- The user's Astro site is not overwritten during Lace upgrades.
- Site loading, block parsing, and rich-text safety are packaged
  (`@lacecms/sdk`, `@lacecms/render`) and rendered through a thin framework
  adapter (`@lacecms/astro`); visual block markup is never a runtime package and
  is installed as user-owned source by `lace add block` from a versioned,
  framework-keyed registry.
- The generated starter site is optional; projects may connect an existing
  Astro site or run without a site.
- Implementation changes follow the repository-local OpenSpec workflow.
- Oxlint and Oxfmt are the linting and formatting toolchain.

## 25. Planning defaults and remaining release decisions

The implementation plan uses these resolved defaults:

- pnpm workspaces plus Turborepo;
- `better-sqlite3` for the Node adapter;
- Tailwind CSS over Lace design tokens and shadcn/ui-generated, Lace-owned
  admin components on Radix UI primitives;
- the `hero`, `richText`, `image`, `quote`, and `cta` built-in blocks (CE7D
  later adds `gallery` and `navigation`);
- no reference fields in the MVP;
- no-op cache by default and optional KV only after the uncached path is correct;
- a first-party fixed-command VPS builder rather than an arbitrary command or
  external CI dependency;
- owner-confirmed public npm organization/scope `@lacecms/*` and generator
  name `create-lace` (unscoped availability must be rechecked before publication);
- GHCR organization `lacecms`, with `ghcr.io/lacecms/api` and
  `ghcr.io/lacecms/builder`;
- experimental package/image versions on npm channel `next` with an
  independent ownership template version: `0.1.0-alpha.1` (template `0.4.0`),
  `0.1.0-alpha.2` (template `0.14.0`) and `0.1.0-alpha.3` (template
  `0.17.0`, npm publication recorded 2026-10-07) are published and immutable;
  `0.1.0-alpha.4` (template `0.20.0`) package publication and real VPS/Cloudflare
  application testing, restore, upgrade, credential rotation and build recovery
  were owner-confirmed on 2026-10-10. Alpha.5 (template `0.29.0`) was prepared and locally accepted on
  2026-10-14; public npm/image availability was verified read-only on 2026-10-16
  and alpha.5 is now recorded as published and immutable. Alpha.6 (template
  `0.30.0`) is also confirmed published and immutable. Alpha.7 (template
  `0.35.0`) has verified public packages/images and remains immutable. The next selected
  candidate is `0.1.0-alpha.8` (template `0.39.0`) on `next`; fresh artifact acceptance and
  owner-operated deployment checks remain distinct from historical alpha.4
  evidence. Beta/stable approval remains separate;
  `release/alpha.json` records the candidate and published versions. See [`alpha-release.md`](./alpha-release.md) for preparation and
  owner publication.

Release lifecycle: reviewed entries in root `CHANGELOG.md` supply concise GitHub
Release descriptions. An explicit owner operation finalizes a prerelease only
for the exact verified artifact source, after full npm/GHCR publication and
byte-verified public JSON evidence. Explicit cleanup may then remove only the
selected local artifact/evidence directories; active operations, incomplete
publication and unavailable remote verification block deletion. Tracked history
and development data remain outside cleanup. Node/Cloudflare deployment gates
and actual platform coverage remain separate from publication. See
[release lifecycle](alpha-release.md#github-release-and-cleanup).

The following choices are release and operations work, not blockers for the
first local vertical slices:

- rechecking availability/publishing rights for the unscoped generator name
  immediately before first publication;
- selecting the signing/provenance process for published artifacts;
- defining hosted release channels and update metadata for `create-lace`;
- confirming, during the owner-operated real-deployment release gate after
  the implementation roadmap, the Cloudflare Pages Git integration selected as
  the reference static host for hook-driven rebuilds (see
  `docs/real-application-verification.md` and
  `docs/cloudflare-deployment-handoff.md`).

Step 34 completes local cross-runtime, security and operations verification and
prepares the owner handoff. Real VPS and Cloudflare deployment acceptance remains
a separate release requirement after the roadmap; local simulation does not
satisfy it. The owner records exact candidate versions and results using
`docs/real-application-verification.md` before claiming deployment readiness.

If package-name ownership differs, only published names and generator templates
change; internal package boundaries and domain contracts remain the same.
