# Lace MVP Architecture

## 1. Document purpose

This document defines the product and technical architecture for the first usable version of Lace. It is intended to be the source for a subsequent implementation plan, milestone breakdown, and architectural decision records.

Lace stands for **Lightweight AI Cloud Engine**. It is a lightweight, self-hosted headless CMS paired with a statically generated Astro website. A single Lace installation manages a single website.

The MVP must run in two environments:

1. Cloudflare, using Workers, D1, R2, and optionally KV.
2. A conventional VPS, using Docker Compose, Node.js, SQLite, and MinIO.

The application must remain portable by placing infrastructure-specific behavior behind narrow interfaces. Portability does not mean hiding SQL or every framework API behind custom wrappers. Abstractions are introduced only at boundaries that genuinely differ between environments.

## 2. Product goals

The MVP should allow a user to:

- initialize a new Lace-powered website with one CLI command, with a starter site, against an existing Astro site, or without a site;
- customize the Astro site without modifying the CMS engine or admin application;
- install editable block renderers into a site without copying engine files by hand;
- define pages, collections, fields, and allowed block types in a typed configuration file;
- manage structured content and ordered content blocks in a browser-based admin application;
- upload and reuse media;
- keep draft content separate from published content;
- publish content with an explicit permission;
- trigger a rebuild of the static Astro website after publication;
- run the same content model and domain behavior on Cloudflare or a VPS;
- update the Lace engine without overwriting the user's website source.

The design should also be easy for coding agents to understand and modify. For the MVP, “AI” primarily means that the generated project, configuration, contracts, and site code are structured for reliable AI-assisted development. A built-in LLM provider, chat interface, or autonomous source-code editor is not required for the MVP.

## 3. Explicit MVP scope

### Included

- One installation per website.
- Pages and collections as two content-model kinds.
- Code-first content-model definitions.
- Draft and published snapshots only.
- Ordered block-based content.
- Tiptap rich-text blocks.
- Media upload to R2 or MinIO.
- Email/password authentication through Better Auth.
- Admin, editor, and viewer roles.
- REST API with versioned endpoints and runtime validation.
- Astro build-time SDK.
- Reliable build-trigger dispatch through an outbox.
- Node/Docker and Cloudflare runtime adapters.
- CLI initialization and an upgrade-safe generated-project layout.

### Not included

- Multiple sites or tenants in one installation.
- PostgreSQL, MySQL, or another database dialect.
- Unlimited content revision history.
- A `previousPublished` snapshot.
- Real-time collaborative editing or CRDTs.
- Arbitrarily nested layout-builder blocks.
- User-defined content models created entirely in the admin UI.
- Per-entry or per-collection ACLs.
- Internationalization and localized snapshots.
- Scheduled publication.
- A visual page preview that exactly reproduces the Astro site.
- A built-in AI chat or an LLM-provider integration.
- A plugin marketplace.

These exclusions should be preserved unless a later architectural decision explicitly changes them.

## 4. Architectural principles

### 4.1 Single-site deployment

Every deployment has exactly one `lace.config.ts`, one content database, one media store, one admin application, and one public Astro site.

Multi-tenancy must not influence MVP tables, authentication, routing, or configuration.

### 4.2 Static public site

The public site is generated by Astro. It retrieves published content from the Lace public API during a build. Public page requests should normally be served as static assets and should not require the CMS API.

### 4.3 Code-first structure, CMS-managed content

Content structure is defined in version-controlled code. Content values are managed in the CMS.

This distinction is important because adding a model or route also requires the Astro site to know how to render it. The admin application may display models and generate forms, but it is not the source of truth for model definitions.

### 4.4 Two content states

Each content entry has:

- one mutable draft snapshot;
- zero or one immutable published snapshot.

Publication replaces the current published snapshot. The MVP does not retain application-level revision history.

### 4.5 Portable capabilities, explicit adapters

Domain and application code depend on capability interfaces. Cloudflare and Node packages implement those interfaces.

The MVP should define ports for at least:

- content repositories and transactions;
- object storage;
- cache;
- build triggering;
- background/outbox dispatch;
- clock and ID generation where deterministic tests need them.

The project must not create a custom abstraction over Hono, Drizzle, React, or every Web API.

### 4.6 Media never lives in SQL

D1 and SQLite store media metadata and object keys only. Binary content is stored in R2 or MinIO.

### 4.7 Published content is immutable

An editor may continue changing the draft immediately after publication without changing what public API consumers see.

### 4.8 Spec-driven delivery

Implementation uses the repository-local OpenSpec `spec-driven` workflow. Each
roadmap session unit is normally one just-in-time OpenSpec change with proposal,
delta specs, design, and tasks. Planning and implementation are separate actions:
an agent must not write production code in the proposal action, and it must not
apply a change until its required artifacts are ready and the user explicitly
requests the apply action.

Completed changes are validated, their delta specs are synchronized into the
main specs, and then they are archived. If implementation reveals a conflict
with the architecture, the agent pauses implementation and updates the planning
artifacts; a deliberate architectural change updates this document and the
roadmap before code proceeds.

Authority order is:

1. `docs/mvp-architecture.md` for product scope and architectural invariants;
2. `openspec/specs/**` for detailed, accepted capability behavior;
3. active OpenSpec change artifacts for the proposed delta;
4. `docs/mvp-implementation-roadmap.md` for sequence and session boundaries.

Lower levels may add detail but may not contradict a higher level silently.

## 5. System context

```text
Content editor
    |
    v
Admin SPA ---- REST ----> Lace API ----> SQLite/D1
                             |  |
                             |  +------> MinIO/R2
                             |
                             +---------> Build trigger/outbox
                                             |
                                             v
                                      Astro static build
                                             |
                                             v
                                      Static site hosting
```

### Cloudflare deployment

```text
Cloudflare Worker
├── /api/v1/*
├── /api/auth/*
└── /admin/* -> built admin assets

Bindings
├── D1: authoritative SQL data
├── R2: media objects
└── KV: optional derived cache

Separate static deployment
└── Astro output, rebuilt through a deploy hook or CI integration
```

The admin application and authenticated API should use the same origin. This avoids unnecessary cross-origin cookie and CORS complexity.

### VPS deployment

```text
Docker Compose
├── lace-api
│   ├── Node.js + Hono
│   ├── built admin assets
│   └── mounted SQLite volume
├── minio
│   └── mounted object-storage volume
├── site-builder
│   ├── private authenticated HTTP endpoint
│   ├── read-only generated-project source mount
│   └── static-output volume
└── static web server/reverse proxy
    └── Astro build output
```

The production build mechanism is represented by `SiteBuildTrigger`. The initial
VPS implementation calls the first-party builder's private authenticated
endpoint. The builder ignores command, path, and environment overrides from the
request and runs one image-defined build command against fixed mount paths. It
builds into a temporary release directory and atomically switches the served
release only after success. A later adapter may call an external CI webhook. The
API must never accept an arbitrary shell command from an HTTP request.

## 6. Repository structure

The Lace engine repository uses a pnpm workspace with Turborepo for
dependency-aware task orchestration and caching. pnpm workspaces remain the
package-management foundation.

```text
apps/
├── admin/                     # React/Vite admin SPA
├── api/                       # deployable/reference Hono composition root
├── builder/                   # fixed-command VPS Astro build service
└── site/                      # engine Astro playground and build fixture (never shipped)

packages/
├── domain/                    # pure domain types, rules, and errors
├── application/               # use cases and capability ports
├── server/                    # Hono routes, middleware, app factory
├── contracts/                 # Valibot REST schemas and DTOs
├── content/                   # field DSL, block registry, validation
├── db/                        # Drizzle SQLite schema and repositories
├── auth/                      # Better Auth configuration and authorization
├── config/                    # lace.config.ts definition and loader
├── sdk/                       # build-time and external REST client, published-site loader
├── render/                    # framework-neutral block parsing, block map, rich-text description
├── astro/                     # Astro adapter: LaceBlocks, RichText, loader environment glue
├── platform-cloudflare/       # D1, R2, KV, Worker and deploy-hook adapters
├── platform-node/             # SQLite, MinIO/S3, Node server adapters
├── cli/                       # create, sync, migrate, upgrade commands
└── test-utils/                # factories, fixtures, and contract test suites

registry/                      # versioned, framework-keyed block sources for `lace add block`

docs/
├── mvp-architecture.md
└── adr/                       # architectural decision records added as needed

openspec/
├── specs/                     # accepted capability specifications
└── changes/                   # active and archived implementation changes
```

Dependency direction (`A -> B` means package A may import package B):

```text
config       -> content
domain       -> content
application  -> domain, content, config
contracts    -> domain, content
db           -> application, domain
auth         -> application, domain
server       -> application, contracts, auth
sdk          -> contracts
render       -> content
astro        -> render, sdk
platform-*   -> application, server, db, auth, config
cli          -> application, config, platform-*
apps/api     -> platform-*, server
apps/admin   -> contracts, content
apps/site    -> astro, render, sdk, content
```

Generated starter sites and connected existing sites use the same direct
dependencies as `apps/site`. `registry/` is engine data, not a workspace
package: its files are copied into sites and bundled with `@lacecms/cli`, never
imported by any package.

Rules:

- `domain` must not import framework or infrastructure packages.
- `content` and `config` must remain runtime-portable and must not import Node-only APIs.
- `application` may depend on domain rules, content validation, and the normalized configuration, but not on REST DTOs, Hono, Drizzle, Cloudflare, or Node adapters.
- `contracts` defines transport DTOs and schemas; it must not become an application-use-case dependency.
- `db` implements application persistence ports and may depend on Drizzle, domain, and application packages.
- `server` may use Hono and contracts but receives infrastructure through construction.
- platform packages may depend on application ports and concrete vendor SDKs.
- `admin` depends on contracts and content metadata and owns a credentialed
  browser transport client; it never depends on database schemas.
- `render` is framework-neutral: it imports no UI framework, Node-only API, the
  SDK, or REST contracts. It accepts a structural block input that the contract
  block DTO satisfies and reuses `@lacecms/content` validation exclusively.
- A framework adapter (`@lacecms/astro` now; `@lacecms/react`, `@lacecms/vue`,
  and `@lacecms/svelte` are reserved names) contains only code that depends on
  its framework. It never re-exports `render`, `sdk`, or `content` APIs, so each
  symbol has one canonical import path.
- No package exports visual block components. Block markup is user-owned source
  installed from `registry/` (see sections 7 and 13).
- `sdk` owns transport and the published-site loader and imports neither
  `content` nor `render`.
- `site` depends on the public SDK, the render core and its framework adapter,
  `@lacecms/content` for block definitions, and user-owned block markup.

Workspace dependency checks in CI must reject cycles and imports that violate these rules.

## 7. Generated user project

The supported MVP onboarding path is a project generator, not copying the entire Lace engine source into an existing arbitrary application.

```bash
pnpm create lace@latest my-site
```

An empty existing repository may use:

```bash
pnpm dlx create-lace@latest init .
```

The first version should require an empty target directory, except for explicitly allowed files such as `.git`, `README.md`, or `LICENSE`. Installing the CMS in place into a nonempty existing project is a later feature; an existing Astro site is instead connected to a separately generated CMS directory (see site modes below).

Generated layout (starter site mode):

```text
my-site/
├── site/                       # user-owned Astro source (starter mode only)
│   ├── lace.site.json          # Lace-managed site configuration and block lock
│   └── src/
│       ├── env.d.ts            # user-owned; lets `tsc` read `.astro` imports
│       ├── lace/blocks.ts      # generated block map file (hash-guarded)
│       ├── lib/lace.ts         # user-owned loader file
│       ├── components/lace/    # installed registry blocks, user-owned
│       ├── layouts/            # user-owned
│       ├── pages/              # user-owned: home and posts routes
│       └── styles/             # user-owned
├── lace.config.ts              # public, typed Lace configuration
├── package.json
├── pnpm-workspace.yaml
├── docker-compose.yml          # managed infrastructure file
├── .env.example
├── .lace/
│   └── manifest.json           # generator version, site mode, managed-file hashes
└── .github/workflows/          # optional Cloudflare/CI deployment files
```

### Site modes

Project creation selects one of three site modes with mutually exclusive flags,
recorded in `.lace/manifest.json` as `site: { mode, path }`:

1. **starter** (`--starter`, path `site`) — generates `site/` from the
   `create-lace` starter;
2. **existing** (`--existing-site <path>`) — generates no `site/` and connects
   the CMS to an existing Astro site at a relative path outside the generated
   target, typically `..` for a `cms/` directory. The path must reach an Astro
   project root (`astro.config.*` and an `astro` dependency) without symbolic
   links. The generator never modifies that site; the operator runs
   `lace add block --all --site <path>` and follows the connection guide;
3. **none** (`--no-site`, path `null`) — generates the CMS only, for headless use
   or a later connection; Compose has no builder, so build dispatch reports that
   no build trigger or build site is configured. `--cloudflare` is rejected.

An explicit flag always wins. Without one, an interactive terminal asks for the
mode, defaulting to **existing** at `..` when the target's parent directory is an
Astro project and to **starter** otherwise; without a terminal the starter is
generated and the output names the other flags. Manifests without a `site`
record (template `0.10.0` and earlier) are read as starter mode with path `site`.

`init .` keeps the empty-target rule in every mode. Managed files that reference
the site (workspace globs, root scripts, Compose build-site mount, Cloudflare
workflow, README, and operations guide) are rendered from the recorded mode and
path, reusing the build-site selection configuration. `lace upgrade` requires a
target template generated for the same mode and path (and names the flags that
generate one); it never creates `site/` for other modes. `lace doctor` checks the
recorded site. Switching the mode of an existing project means generating a
fresh project and moving configuration manually.

### Starter and reference site

The `create-lace` starter is the single source of what users receive: minimal
`home` and `posts` pages, a layout, global styles, the five built-in registry
blocks, `lace.site.json`, the block map file, and the loader file. It contains
no tests, fixtures, or engine-development routes.

`apps/site` is the engine development playground and integration fixture. It may
carry extra models and routes, custom blocks, edge-case content, and the
published-export fixture. Nothing from it is copied into generated projects.

Both consume the same packages and hold committed copies of the built-in blocks
exactly as `lace add block` installs them. A test fails when the starter,
`apps/site`, and `registry/` block sources diverge, and CI builds a project
generated from the packed starter in addition to `apps/site`.

The generated project must not expose the editable source of the admin SPA. The admin UI and CMS engine are delivered as versioned packages, bundles, or container images.

### Ownership rules

```text
site/**                 user-owned; never overwritten by upgrade
lace.config.ts          user-owned public configuration
.lace/**                Lace-managed metadata
deployment files        managed with hash/conflict detection
CMS engine/admin        versioned dependency or container image
```

Inside any connected site tree (the starter `site/` or an existing site), the
user-owned rule has three Lace-managed exceptions maintained only by
`lace add block`, never by `lace upgrade` or the generator after creation:

```text
<site>/lace.site.json        Lace-managed site configuration and block lock;
                             configuration keys are user-editable, `items` and
                             hashes are CLI-maintained
<site>/<blockMap>            generated block map file; rewritten only while its
                             recorded hash matches, otherwise the CLI prints the
                             entries to add
<site>/<componentsDir>/**    installed registry block sources; user-owned after
                             installation, updated only while the recorded hash
                             matches, otherwise reported as a conflict
```

The CLI never edits other site source, never edits the site `package.json`
(it prints the exact `pnpm add` command), and rejects paths outside the site
root.

### Upgrade model

`lace upgrade` treats upgrades in three categories:

1. Engine dependencies and container image tags can be updated automatically.
2. Generated infrastructure files can be updated only when their recorded hash proves that the user has not changed them.
3. User-owned files are never silently rewritten. Required changes are supplied as migration instructions or explicit codemods.

Block-source updates are a separate command: `lace add block` updates installed
registry items, while `lace upgrade` updates the template's managed files. Both
share one three-way hash decision, diff, and guarded atomic-write implementation
in `@lacecms/cli`. `lace add block` needs no rollback journal: every write is
compare-and-swap, `lace.site.json` is written last as the commit record, and a
re-run adopts files that already match the registry.

`.lace/manifest.json` should record the generator/template version and hashes of managed files. A modified managed file produces a diff or conflict instead of being overwritten.

Database migrations are versioned with the engine and must run as an explicit deployment step.

## 8. Content configuration

The root `lace.config.ts` is the source of truth for content structure.

```ts
import {
  builtInBlocks,
  defineCollection,
  defineConfig,
  definePage,
  field,
} from "@lacecms/config";

export default defineConfig({
  blocks: [
    builtInBlocks.hero,
    builtInBlocks.richText,
    builtInBlocks.image,
    builtInBlocks.quote,
    builtInBlocks.cta,
  ],
  content: [
    definePage({
      key: "home",
      version: 1,
      label: "Home",
      path: "/",
      blocks: ["hero", "richText", "image", "cta"],
    }),

    defineCollection({
      key: "posts",
      version: 1,
      label: "Posts",
      route: "/blog/:slug",
      fields: {
        publishedAt: field.date({ required: true }),
        author: field.text(),
        category: field.select({
          options: ["engineering", "design", "news"],
        }),
      },
      listFields: ["category", "author"],
      blocks: ["richText", "image", "quote"],
    }),
  ],
});
```

The Worker and Node composition roots import `lace.config.ts` at build time. The
runtime never evaluates an arbitrary TypeScript path supplied through an HTTP
request. The normalized configuration and its serializable admin projection are
created once during application startup.

For the MVP, every snapshot has the following common system fields:

- `title` is required for both pages and collection entries;
- `slug` is `NULL` for pages; it may be absent from an incomplete collection
  draft but is required for publication;
- a collection route contains exactly one `:slug` segment;
- slugs use lowercase ASCII letters, digits, and single hyphens
  (`^[a-z0-9]+(?:-[a-z0-9]+)*$`); the admin may suggest a normalized slug, but
  the API validates rather than silently rewrites submitted values;
- page paths and resolved collection paths start with `/`, contain no query or
  fragment, collapse no implicit aliases, and use no trailing slash except `/`.

Configuration rejects duplicate page paths, duplicate collection route patterns,
and a page path that already matches a collection route pattern. The
`published_routes` constraint still guards runtime collisions and future route
features.

`published_routes.path` remains the final global uniqueness constraint, so two
different models cannot publish the same path even if their individual slugs
are different.

### Content-model kinds

`content_models.kind` uses domain-language values:

```ts
type ContentModelKind = "page" | "collection";
```

- `page` represents a singleton model and permits exactly one content entry.
- `collection` permits any number of content entries.

Pages and collection entries share storage, snapshot, block, validation, and publication behavior.

### Initial field types

The MVP field DSL should support:

- text;
- textarea;
- rich text;
- number;
- boolean;
- date;
- datetime;
- select;
- URL;
- media.

Reference fields should be anticipated in the DSL design but may be postponed until after the first vertical slice. Arbitrary executable user code must not be serialized and sent to the admin application.

Reference fields are not part of the MVP. The field-definition discriminated
union and validation visitor must be exhaustive so that a reference variant can
be introduced later without changing existing field encodings.

### Initial built-in blocks

The starter and browser editor ship with five blocks. They use only the public
field DSL and do not receive special database treatment:

- `hero`: optional eyebrow, required heading, optional rich-text body, optional
  media, optional primary-action label and URL;
- `richText`: one required Tiptap document;
- `image`: required media, required alt text, and optional caption;
- `quote`: required quote text and optional attribution;
- `cta`: required heading, optional body, required action label, and required URL.

Projects may define additional blocks in `lace.config.ts`. Custom blocks use the
generic metadata-driven admin form in the MVP; custom React admin editors are
out of scope.

### MVP content limits

Shared contract constants enforce the same limits in config validation, REST
validation, and the admin UI: title at most 200 characters, slug at most 100
characters, at most 200 top-level blocks and 200 media references per entry, and
at most 1,000,000 UTF-8 bytes in either `fields_json` or one block's `data_json`.
Individual field definitions may set stricter limits. These conservative JSON limits leave room
below D1's row/string ceiling and prevent the browser editor from creating
payloads the target runtime cannot persist.

Validation has explicit `draft` and `publish` modes. Draft validation rejects
unknown keys, wrong types, invalid present values, unsafe rich text/URLs, and
size limits, but permits a required model field to be absent so incomplete work
can be saved. Publish validation additionally enforces every `required` field and
the collection slug. `title` is the one required draft system field because it
is relational and needed by entry lists.

### Configuration projection

The API loads the executable configuration and exposes a serializable representation to the admin application. The database stores model identity and synchronization metadata, not a second authoritative copy of every field definition.

An explicit command synchronizes configuration with stored model identities:

```bash
pnpm lace content sync
```

The command:

- creates new model records;
- updates labels, versions, and configuration hashes;
- detects removals and renames;
- refuses destructive removal while entries still exist;
- reports incompatible field changes.

A collection may declare `listFields`, an ordered list of its own scalar fields
(text, textarea, number, boolean, select, date, datetime, or URL) that admin
entry lists show as columns. Rich-text and media fields are rejected: the first
is a document and the second an opaque identifier. `listFields` is presentation
metadata like labels.

Every model definition has an integer `version` starting at `1`. Any structural
change to fields, allowed blocks, path, or route must increment it; display-only
label, description, and `listFields` changes do not. Sync compares two canonical
hashes: `structure_hash` excludes display metadata and `projection_hash`
includes the complete serializable projection. A changed structure hash without a version
bump fails; a projection-only change is safe and does not require a bump.

Renames are never guessed. `definePage` and `defineCollection` accept a temporary
`renamedFrom` key. Sync performs the key migration only when the previous key
exists, the new key does not, and kind/cardinality remain compatible; the option
must be removed after all environments have applied the sync. Without that
explicit hint, a key change is treated as one addition and one removal, and the
removal is refused while entries exist.

The MVP sync command refuses an incompatible schema change while entries exist.
The report names the affected models, fields, and snapshots; the operator must
restore the old definition or run a separately reviewed content-migration tool.
Designing that general migration runner is post-MVP. Block-local migration
functions may still upgrade a known block payload as described in section 22,
but sync never silently transforms arbitrary content.

When a successful sync changes the serializable configuration visible to public
consumers, it increments `published_state.version` and requests a build in the
same atomic mutation.

Sync also ensures that every page model has one singleton entry. A newly created
page entry receives the model label as its draft title, `NULL` slug, configured
defaults, an empty block list, and the audit actor `system:content-sync`; missing
required model fields remain valid in draft mode until publication. Collections
are created only through the admin/API and require an initial title.

A non-interactive check mode should be available for CI:

```bash
pnpm lace content sync --check
```

## 9. Content data model

All primary IDs should be application-generated sortable string IDs, such as ULIDs. Timestamps should be UTC Unix milliseconds in the database and ISO 8601 strings in REST responses.

### 9.1 Content models

```text
content_models
├── key                 TEXT PRIMARY KEY
├── kind                TEXT NOT NULL CHECK(kind IN ('page', 'collection'))
├── label               TEXT NOT NULL
├── config_version      INTEGER NOT NULL
├── structure_hash      TEXT NOT NULL
├── projection_hash     TEXT NOT NULL
├── created_at          INTEGER NOT NULL
└── updated_at          INTEGER NOT NULL
```

`key` is a stable programmatic identifier. Labels may change freely. Renaming a key is a migration, not a display-name edit.

### 9.2 Content entries

```text
content_entries
├── id                    TEXT PRIMARY KEY
├── model_key             TEXT NOT NULL REFERENCES content_models(key)
├── singleton_key         INTEGER
├── draft_snapshot_id     TEXT
├── published_snapshot_id TEXT
├── created_by            TEXT NOT NULL
├── created_at            INTEGER NOT NULL
└── updated_at            INTEGER NOT NULL
```

`draft_snapshot_id` is nullable at the SQL level only to break the insertion cycle between a new entry and its first snapshot. Entry creation inserts the entry, inserts its draft snapshot, and assigns the pointer atomically. Application code treats a committed entry without a draft as invalid. `published_snapshot_id` remains nullable until the first publication.

The API sets `singleton_key = 1` for pages and `NULL` for collection entries. SQLite permits multiple `NULL` values in a unique index, so this partial index enforces a single page entry per page model:

```sql
CREATE UNIQUE INDEX content_entries_singleton_idx
ON content_entries(model_key)
WHERE singleton_key = 1;
```

Additional index:

```sql
CREATE INDEX content_entries_model_idx
ON content_entries(model_key);
```

The application still validates model cardinality and treats the index as the final consistency guarantee.

### 9.3 Content snapshots

```text
content_snapshots
├── id                  TEXT PRIMARY KEY
├── entry_id            TEXT NOT NULL REFERENCES content_entries(id)
├── revision            INTEGER NOT NULL
├── slug                TEXT
├── title               TEXT NOT NULL
├── fields_json         TEXT NOT NULL
├── schema_version      INTEGER NOT NULL
├── created_at          INTEGER NOT NULL
├── updated_at          INTEGER NOT NULL
└── updated_by          TEXT NOT NULL
```

`fields_json` contains model-specific structured fields. System fields involved in identity, routing, concurrency, or common queries remain relational columns.

The draft snapshot is mutable. A published snapshot is immutable and can only be replaced through the publish use case.

The database temporarily contains both snapshots, so text content is duplicated. This is intentional and acceptable for the D1 free-plan database limit because binary assets are excluded. Individual page payloads are split into block rows rather than constrained by one whole-page row.

### 9.4 Content blocks

```text
content_blocks
├── snapshot_id         TEXT NOT NULL REFERENCES content_snapshots(id)
├── block_key           TEXT NOT NULL
├── block_type          TEXT NOT NULL
├── position            INTEGER NOT NULL
├── schema_version      INTEGER NOT NULL
├── data_json           TEXT NOT NULL
├── created_at          INTEGER NOT NULL
└── updated_at          INTEGER NOT NULL

PRIMARY KEY(snapshot_id, block_key)
```

Index:

```sql
CREATE INDEX content_blocks_snapshot_position_idx
ON content_blocks(snapshot_id, position);
```

`block_key` is stable across draft and published copies. The composite primary key allows a published snapshot to be copied using one `INSERT ... SELECT` statement without generating new per-row IDs.

Block-specific data remains JSON and is validated by the block registry. A block type does not receive a dedicated SQL table or columns.

### 9.5 Block ordering and nesting

The MVP uses sparse integer positions such as `1000`, `2000`, and `3000`. Inserting between two blocks normally changes only the inserted block. Positions are normalized when there is no safe gap.

The MVP supports a flat top-level block list. A block may contain its own bounded nested data in `data_json`, but arbitrary parent/child block trees are out of scope.

All draft mutations are atomic at snapshot scope. A successful mutation changes
the draft fields and complete ordered block list, increments
`content_snapshots.revision` exactly once, and updates `updated_at` and
`updated_by`. There is no state in which block rows have changed while the draft
revision has not. This invariant is required by optimistic concurrency and the
D1 publication batch.

### 9.6 Published routes

```text
published_routes
├── path                TEXT PRIMARY KEY
├── entry_id            TEXT NOT NULL REFERENCES content_entries(id)
├── snapshot_id         TEXT NOT NULL REFERENCES content_snapshots(id)
└── updated_at          INTEGER NOT NULL
```

This table guarantees unique public paths and supports direct lookup by URL.

- Page paths are fixed by their model definition.
- Collection paths are produced from the model route and the published snapshot slug.
- A draft slug change does not change the public path before publication.

### 9.7 Media

```text
media
├── id                  TEXT PRIMARY KEY
├── storage_key         TEXT NOT NULL UNIQUE
├── filename            TEXT NOT NULL
├── mime_type           TEXT NOT NULL
├── size                INTEGER NOT NULL
├── width               INTEGER
├── height              INTEGER
├── metadata_json       TEXT NOT NULL
├── status              TEXT NOT NULL CHECK(status IN ('active', 'deleting', 'delete_failed'))
├── last_error          TEXT
├── created_by          TEXT NOT NULL
├── created_at          INTEGER NOT NULL
└── updated_at          INTEGER NOT NULL
```

Content stores `mediaId` references. Storage URLs may be derived or signed and should not be treated as permanent database identity.

Because media IDs occur inside validated JSON, Lace maintains a relational
projection of those references:

```text
content_media_references
├── snapshot_id         TEXT NOT NULL REFERENCES content_snapshots(id)
├── source_key          TEXT NOT NULL
├── field_path          TEXT NOT NULL
├── media_id            TEXT NOT NULL REFERENCES media(id)
└── created_at          INTEGER NOT NULL

PRIMARY KEY(snapshot_id, source_key, field_path)
```

`source_key` is `$fields` for snapshot fields or the stable block key for block
data. An index on `media_id` makes deletion checks bounded. Draft saves rebuild
the draft snapshot's reference projection in the same atomic mutation;
publication copies it with `INSERT ... SELECT`. A media item may be selected only
while its status is `active`.

The same projection is the only source of media usage. An entry uses an item
when its current draft or current published snapshot references it in an entry
field or a block field. Every admin media DTO carries `usageCount`, the number
of distinct using entries, and the media detail read lists up to 50 of them with
each location and whether the draft, the published version, or both use it.
Because only current snapshots keep references, usage and the deletion guard
always agree: an item is refused deletion exactly when its `usageCount` is
greater than zero.

`width` and `height` are the displayed dimensions, measured after the image's
EXIF orientation is applied. Every upload records both values.

Media deletion is asynchronous and recoverable. The delete use case refuses a
referenced item with `MEDIA_IN_USE` (HTTP `409`), marks an unreferenced item
`deleting`, and writes a
`media.delete.requested` outbox event atomically. The dispatcher deletes the
object and then the metadata row; failures set `delete_failed` and remain
retryable. This avoids either a dangling published reference or an unrecoverable
SQL/object-storage half-delete.

The default upload limit is 10 MiB. The initial allowlist is JPEG, PNG, WebP,
GIF, and AVIF; SVG is excluded because safely sanitizing active XML is outside
the MVP. The server verifies magic bytes rather than trusting the multipart
content type or filename and stores a generated object key, never a user path.
The limit and allowlist may be narrowed through deployment configuration but not
expanded without a corresponding validator implementation.

### 9.8 Outbox and site builds

```text
outbox_events
├── id                  TEXT PRIMARY KEY
├── type                TEXT NOT NULL
├── payload_json        TEXT NOT NULL
├── attempts            INTEGER NOT NULL DEFAULT 0
├── available_at        INTEGER NOT NULL
├── processed_at        INTEGER
├── last_error          TEXT
└── created_at          INTEGER NOT NULL

site_builds
├── id                  TEXT PRIMARY KEY
├── reason              TEXT NOT NULL
├── status              TEXT NOT NULL
├── target_version      INTEGER NOT NULL
├── published_snapshot_id TEXT
├── provider_build_id   TEXT
├── requested_by        TEXT NOT NULL
├── requested_at        INTEGER NOT NULL
├── started_at          INTEGER
├── completed_at        INTEGER
└── error               TEXT
```

`site_builds.status` is one of `pending`, `running`, `succeeded`, or `failed`.
The optional snapshot ID identifies the publication that initiated a request;
`target_version` is authoritative when requests are coalesced.

The global published state is represented by one singleton row:

```text
published_state
├── singleton_key       INTEGER PRIMARY KEY CHECK(singleton_key = 1)
├── version             INTEGER NOT NULL
└── updated_at          INTEGER NOT NULL
```

Every operation that changes public output increments `version` in the same
atomic mutation. The version supplies the build-export ETag and the target
version for build requests without hashing the full export on every request.

Outbox rows also contain `locked_at` and `locked_by` nullable columns. A
dispatcher claims only an available, unprocessed row whose lease is absent or
expired, using a conditional write. The lease prevents duplicate concurrent
dispatch while still allowing recovery after a terminated Worker or container.
The default lease is 60 seconds. Retries use full-jitter exponential backoff from
5 seconds, capped at 15 minutes, with 8 total attempts. A terminal failure marks
the event processed, preserves `last_error`, and marks its media/build aggregate
failed; an explicit admin retry creates a fresh event.

Idempotent commands use a small generic table:

```text
idempotency_records
├── scope               TEXT NOT NULL
├── key                 TEXT NOT NULL
├── request_hash        TEXT NOT NULL
├── response_json       TEXT NOT NULL
├── created_at          INTEGER NOT NULL
└── expires_at          INTEGER NOT NULL

PRIMARY KEY(scope, key)
```

For publication, `scope` includes the actor and entry ID. Reusing a key with the
same request hash returns the recorded result; reusing it with different input
returns an idempotency conflict. Expired rows are removed by maintenance work.
Keys are 8–128 printable ASCII characters and publication records expire after
24 hours. The API keeps the key optional for direct clients, while the admin UI
always sends one and reuses it for retries of the same publish action.

Build requests should be coalesced. Several publications made close together should normally result in one site build rather than one build for every entry.

The site-build debounce window is 5 seconds from the most recent coalesced
request.

There is at most one unprocessed, unlocked `site.build.requested` event. A new
publication creates it or extends its debounce deadline. A claimed event is not
modified; publications arriving after claim create the next event. This permits
at most one redundant build around a claim race while ensuring that no published
state is skipped.

```sql
CREATE UNIQUE INDEX outbox_pending_site_build_idx
ON outbox_events(type)
WHERE type = 'site.build.requested'
  AND processed_at IS NULL
  AND locked_at IS NULL;
```

Adapters coalesce with `INSERT OR IGNORE` followed by a guarded update of the
existing unlocked row; media-deletion events are never coalesced.

### 9.9 Referential actions

- deleting an entry cascades to its snapshots, blocks, media-reference rows, and
  published route after application authorization and validation;
- deleting a snapshot cascades to its blocks and media-reference rows;
- entry snapshot-pointer foreign keys use `ON DELETE SET NULL` to avoid a
  deletion cycle, while application invariants still require a committed draft;
- a content model with entries is restricted from deletion;
- `content_entries.model_key` uses `ON UPDATE CASCADE` so an explicit
  `renamedFrom` sync can change the model primary key atomically;
- a referenced media row is restricted from deletion;
- foreign-key enforcement is enabled explicitly for every Node SQLite
  connection and verified in D1 contract tests.

## 10. Content publication

Publication is an admin-only application use case in the default role policy.

Inputs include:

- entry ID;
- expected draft revision;
- authenticated actor;
- optional idempotency key.

Publication first loads the draft, blocks, active configuration, and current
published pointer, then validates the complete candidate without writing. It
then executes the following as one guarded database transaction or D1 atomic
batch:

1. Creates the new snapshot with `INSERT ... SELECT` only if the entry still
   points to the validated draft and its revision still equals
   `expectedDraftRevision`.
2. Copies draft blocks and media-reference rows with set-based
   `INSERT ... SELECT` statements conditional on the new snapshot existing.
3. Removes the entry's old route and inserts the resolved route, also
   conditional on the new snapshot existing. A path collision aborts and rolls
   back the whole batch.
4. Updates `content_entries.published_snapshot_id` to the new snapshot.
5. Increments `published_state.version`.
6. Creates or coalesces the `site.build.requested` outbox event for that version.
7. Stores the idempotency result when a key was supplied.
8. Deletes the old published snapshot; cascading foreign keys delete its blocks
   and media-reference rows.

The adapter returns the affected-row results. If the guarded snapshot insert
affected zero rows, the use case returns `CONTENT_REVISION_CONFLICT` and treats
all conditional statements as no-ops. All ways of mutating a draft must bump the
same revision, so a candidate validated before the batch cannot be published
after any concurrent field, slug, title, or block change.

This is a specialized repository operation, not a promise that Cloudflare D1
supports an arbitrary interactive transaction callback. The application port
models atomic content mutations and publication explicitly; the Node adapter may
implement them with a normal SQLite transaction, while the D1 adapter uses
guarded SQL batches.

The mutable draft remains in place. Immediately after publication, draft and published contain equivalent data but are independent records.

The outbox dispatcher runs after commit and invokes `SiteBuildTrigger`. Failed dispatches remain recoverable and are retried with bounded exponential backoff. A scheduled recovery process must handle events left pending after a Worker or container terminates.

Content publication success and site deployment success are distinct states. The admin UI must be able to show “published, build pending” or “published, build failed.”

Deleting a draft-only entry requires `content:write`. Deleting an entry that has
a published snapshot also requires `content:publish`; the same atomic mutation
removes its public route, increments `published_state.version`, and enqueues a
build. The MVP has no separate unpublish command. Deleting a page does not delete
its model and a later edit recreates the singleton entry.

## 11. Block registry and rich text

The block registry maps each `block_type` to:

- a stable key;
- a human-readable label;
- a schema version;
- a runtime validation schema;
- serializable form metadata;
- optional default data;
- optional data migration functions.

Runtime schemas are implemented with Valibot. The public field DSL must not expose raw Valibot schemas as its serialized admin contract. A field definition produces serializable form metadata, a Valibot runtime schema, an inferred TypeScript type, and, where needed, JSON Schema.

Example conceptual API:

```ts
defineBlock({
  type: "hero",
  version: 1,
  fields: {
    heading: field.text({ required: true }),
    body: field.richText(),
    image: field.media(),
  },
});
```

Tiptap JSON is stored only inside rich-text field or rich-text block data. The entire page must not become one Tiptap document.

The allowed Tiptap node and mark set is explicit and shared by validation and
rendering. Links permit only `https:`, `http:`, `mailto:`, `tel:`, root-relative,
and fragment URLs. Raw HTML nodes, scriptable URL schemes, inline event handlers,
and arbitrary style attributes are rejected. The allowlist and URL rules have one
implementation in `@lacecms/content`; the render core's `describeRichText`
reuses it exclusively, and framework adapters escape text and render only the
resulting element description. Sites must not keep their own allowlist copies.
Consumers that read structured JSON without the render core remain responsible
for an equally safe renderer.

Sites render blocks through a block map that pairs each block definition with a
user-owned component (section 13). Block definitions used by a site are the same
`defineBlock` definitions the configuration uses; a site that cannot render a
block type, or whose definition version differs from the published block, fails
its build with the model, entry, and block identifiers.

Each block definition may carry an optional one-sentence description next to its label. Both are display metadata: they reach the admin through the block projection, change the configuration projection hash, and never change the structural hash. The built-in blocks ship with labels and descriptions. Block icons are not configuration. The admin maps the built-in types to icons and gives any other block type a default icon.

The initial admin editor should render block forms from serializable field metadata. Exact site rendering and custom React admin editors are not required for every block in the MVP.

## 12. REST API

All product endpoints are versioned under `/api/v1`. Better Auth retains its conventional `/api/auth` base path.

```text
/api/auth/*

/api/v1/public/*
/api/v1/admin/*
```

### Public endpoints

Representative routes:

```text
GET /api/v1/public/pages/:modelKey
GET /api/v1/public/collections/:modelKey
GET /api/v1/public/collections/:modelKey/:slug
GET /api/v1/public/content/by-path?path=/blog/hello
GET /api/v1/public/build-export
GET /api/v1/public/media/:mediaId
```

Public routes return published snapshots only. Individual page, collection, path,
and media reads are anonymous and cacheable. `build-export` returns all published
models, entries, routes, blocks, and referenced media metadata in a
build-efficient representation to avoid an N+1 request pattern during Astro
generation; it requires a read-only build token.

Content DTOs expose a stable absolute media URL formed from the configured
`LACE_PUBLIC_BASE_URL` plus `/api/v1/public/media/:mediaId`, never a short-lived
signed URL. The base URL is validated at startup and is never inferred from an
untrusted `Host` or forwarded header. The endpoint may
stream the object or redirect to a short-lived R2/MinIO URL. Static HTML therefore
keeps a durable URL while storage credentials and object keys stay private.
The public media endpoint returns an object only when the media ID is referenced
by a snapshot that is currently published; authenticated admin media endpoints
provide draft previews. Knowing an unreferenced media ID does not publish it.

### Admin endpoints

Representative routes:

```text
GET    /api/v1/admin/content-models
GET    /api/v1/admin/models/:modelKey/entries
POST   /api/v1/admin/models/:modelKey/entries
GET    /api/v1/admin/entries/:entryId
PUT    /api/v1/admin/entries/:entryId/draft
POST   /api/v1/admin/entries/:entryId/publish
DELETE /api/v1/admin/entries/:entryId

GET    /api/v1/admin/media
POST   /api/v1/admin/media
GET    /api/v1/admin/media/:mediaId
DELETE /api/v1/admin/media/:mediaId
POST   /api/v1/admin/media/:mediaId/retry-deletion

GET    /api/v1/admin/site-builds
POST   /api/v1/admin/site-builds

GET    /api/v1/admin/users
POST   /api/v1/admin/users
PATCH  /api/v1/admin/users/:userId

GET    /api/v1/admin/settings/status
GET    /api/v1/admin/api-tokens
POST   /api/v1/admin/api-tokens
DELETE /api/v1/admin/api-tokens/:tokenId
```

The draft `PUT` accepts `expectedRevision` plus the complete editable draft:
`title`, `slug`, `fields`, and the ordered block list. It validates and persists
that aggregate atomically and returns the incremented revision. The admin may
edit individual blocks locally, but its Save command uses this aggregate
endpoint. Granular block mutation endpoints may be added later only if they
preserve the same snapshot-revision invariant.

### Contract rules

- Requests and responses use shared Valibot runtime schemas.
- Hono request validation uses `@hono/standard-validator`, keeping route integration based on Standard Schema rather than a validator-specific Hono API.
- Database rows are never exposed directly as API DTOs.
- Errors use one stable machine-readable envelope. Validation failures,
  including content validation while creating, saving, or publishing an entry,
  return `422 VALIDATION_FAILED` with one issue per failure: its code, a
  message that never repeats the submitted value, and a JSON Pointer such as
  `/blocks/0/data/body` or `/fields/summary`.
- Collection lists use cursor pagination. Admin entry lists accept `q` (title
  or slug substring), `status` (`draft`, `published`, or `changed`, derived from
  the draft and published revisions), and `sort`; cursors are bound to the
  query that produced them, and each page carries per-status totals.
- Admin entry summaries and entry responses name the last editor with an `id`
  and `displayName`, so lists never render raw user IDs. Public and
  build-export DTOs never carry display names.
- The admin media list accepts `q` (filename substring), `type` (an allowed
  image MIME type), and `sort` (`createdAt`, `filename`, or `size`, either
  direction; default newest first), with cursors bound to that query. Media
  DTOs name the uploader as `createdBy` with an `id` and `displayName`, and
  carry `usageCount`. `GET /api/v1/admin/media/:mediaId` adds the bounded
  `usage` list.
- Mutable operations use optimistic concurrency through a revision or `If-Match` value.
- Publish operations are idempotent.
- Dates in JSON use ISO 8601 UTC strings.
- Build export supports conditional requests with an ETag derived from
  `published_state.version`.
- Build tokens are random opaque credentials stored only as hashes, have only a
  `content:build:read` capability, and are accepted only by build-oriented public
  endpoints. They cannot be exchanged for a browser session.
- OpenAPI output is generated from the same route contracts through `hono-openapi` and `@valibot/to-json-schema`, rather than maintained separately.

Example error:

```json
{
  "error": {
    "code": "CONTENT_REVISION_CONFLICT",
    "message": "The draft was modified by another request.",
    "details": {
      "expectedRevision": 12,
      "actualRevision": 13
    }
  }
}
```

## 13. Site rendering and block installation

Sites consume Lace through three layers ([ADR 0006](./adr/0006-shared-rendering-core-and-installed-block-source.md)):

1. framework-neutral loading in `@lacecms/sdk` and parsing/rich-text description
   in `@lacecms/render`;
2. a thin framework adapter (`@lacecms/astro`) that renders those results;
3. user-owned visual block source installed from the block registry.

This section fixes the public names, inputs, outputs, error behavior, and
server-only constraints that Step 30 implements. Exact DTO fields and spec
wording belong to the implementing OpenSpec changes. The public build-export DTO
is unchanged: public entries still reuse the content-entry schema with an
always-present `published` and a mirrored `draft` snapshot, and the loader hides
that shape (a dedicated public schema is a Step 33 question).

### 13.1 SDK client

`@lacecms/sdk` is a small fetch-based client usable during site builds and by
external consumers.

```ts
const lace = createLaceClient({
  baseUrl: env.LACE_API_BASE_URL,
  token: env.LACE_BUILD_TOKEN,
});

const home = await lace.getPage("home");
const posts = await lace.getCollection("posts");
const exportData = await lace.getBuildExport();
```

The build token is read-only and may access published content only. It must not
grant admin-session capabilities, and it is used only in server-side build or
dev-server code, never in client bundles.

### 13.2 Published-site loader

`createPublishedSiteLoader(options)` in `@lacecms/sdk` returns a
`PublishedSiteLoader`, a function resolving to a `PublishedSite`. It imports no
framework and never reads `process.env` or `import.meta.env` itself.

- **Input:** an `environment` record (`LACE_API_BASE_URL`, `LACE_BUILD_TOKEN`,
  `LACE_PUBLIC_BASE_URL`, `LACE_EXPECTED_PUBLISHED_VERSION`) and/or explicit
  `baseUrl`, `token`, `publicBaseUrl`, and `expectedPublishedVersion` values that
  take precedence; optional `fetch`; `revalidate` (default `false`); optional
  `hints` keyed by error code that are appended to error messages.
- **Static mode** reads one build export per loader, shared by concurrent
  callers, and forgets a failed read so the next call retries.
- **Revalidate mode** (dev servers) issues an ETag-conditional read on each call;
  concurrent calls share one in-flight request and `304` reuses the last view.
- **Consistency:** when an expected published version is configured, a
  different export version fails the build.
- **Output:** `PublishedSite` with `version`, `byPath(path)`,
  `entries(modelKey)` (sorted by path; empty for an unknown model),
  `bySlug(modelKey, slug)`, and `mediaUrl(mediaId)`. Lookups return
  `undefined` when absent so routes choose between 404 and failure.
  `PublishedEntry` exposes `id`, `modelKey`, `path`, optional `slug`, `title`,
  `fields`, and ordered `blocks` (`PublishedBlock`: `type`, `key`, `position`,
  `schemaVersion`, `data`), typed from contract DTOs. No draft-shaped property
  exists on the view.
- The loader trusts the CMS-resolved `path`, never re-derives route patterns or
  names model keys, and rejects duplicate paths and duplicate slugs within a
  model.
- **Errors:** `LacePublishedSiteError` (a `LaceSdkError`) with stable codes
  `missing_configuration`, `rejected_token` (HTTP 401/403), `api_unavailable`
  (transport failure), `version_mismatch`, and `invalid_export`. Other SDK
  errors propagate unchanged. Messages are project-neutral and never include the
  token; generated projects pass hints that name their own commands.

### 13.3 Render core

`@lacecms/render` depends only on `@lacecms/content`.

- `BlockContext` identifies a block in errors: `modelKey`, `entryId`, `blockKey`.
- `parseBlock(definition, block, context)` validates `block.data` with
  `validateBlockData` in publish mode, applies definition defaults, and returns
  typed `BlockDataValues`. It works for built-in and user `defineBlock`
  definitions, fails when the block type differs from the definition, and fails
  when `block.schemaVersion` differs from `definition.version`; the render core
  never migrates block data.
- `defineBlockMap(entries)` accepts a record keyed by block type whose values
  are `{ definition, component }`, generic over the adapter's component type,
  rejects a key that differs from its definition type, and returns a frozen
  map. `resolveBlock(map, block, context)` returns the entry or fails on an
  unknown block type, which preserves the build-failure behavior for blocks a
  site cannot render. `prepareBlocks(map, entry, mediaUrl)` resolves and parses
  an entry's blocks in order and returns each mapped component with its
  `BlockProps`, so adapters only render the result.
- `BlockProps<Definition>` is the prop contract every adapter passes to a block
  component: `block`, parsed `data`, `context`, and `mediaUrl`.
- `describeRichText(value, context?)` validates with `validateRichTextDocument`
  and returns a neutral tree of text nodes (`{ kind: "text", text }`) and
  element nodes (`{ kind: "element", tag, attributes, source, children }`).
  Tags come from a fixed allowlist, attributes are limited to safe attributes
  (a link `href` has passed `isSafeUrl`), and `source` names the originating
  node or mark. No raw HTML string is produced.
- **Errors:** `LaceRenderError` with codes `invalid_block_data`,
  `block_version_mismatch`, `unknown_block_type`, and `invalid_rich_text`,
  carrying the context, the field path, and the underlying
  `ContentValidationError` as `cause`. Messages name model, entry, block key,
  and field path.

### 13.4 Astro adapter

`@lacecms/astro` depends on `@lacecms/render` and `@lacecms/sdk`, declares a peer
dependency on the supported Astro range, and ships Astro component source
(copied next to its compiled module in `dist/`). It contains no visual blocks,
no client scripts, and requires no Astro integration. Override components for
`RichText.astro` are typed by the adapter's `RichTextOverrideProps`.

- `createAstroSiteLoader(options?)` (root entry, server-only) accepts `env`
  (default `process.env`), `dev` (enables revalidation), `fetch`, and `hints`,
  and returns a `PublishedSiteLoader`. Sites pass
  `{ env: { ...import.meta.env, ...process.env }, dev: import.meta.env.DEV }`
  from their loader file because `import.meta.env` is not reliably transformed
  inside externalized dependencies. The module fails fast when evaluated in a
  browser; `LACE_BUILD_TOKEN` must never reach a client bundle.
- `@lacecms/astro/LaceBlocks.astro` takes `entry`, `blocks` (the block map), and
  `mediaUrl`, resolves and parses each block in order, and renders the mapped
  component with `BlockProps`.
- `@lacecms/astro/RichText.astro` takes `document`, optional `components` keyed
  by node or mark name, and optional `context`. It renders the
  `describeRichText` tree with Astro's escaping and never uses `set:html`;
  overrides receive only the validated element and its rendered children.

### 13.5 Block registry and `lace add block`

Canonical block sources live in the repository `registry/` directory and are
bundled with, and versioned by, the `@lacecms/cli` release; the CLI never
fetches registry content over the network. `registry/registry.json` lists the
items, and each item lives in `registry/<framework>/<item>/` with a manifest
declaring block type, framework, block definition version, item revision,
required render-core and adapter ranges, files with their target role, and item
dependencies.

The site-local `lace.site.json` records a format version, `framework`,
`componentsDir` (default `src/components/lace`), `blockMap` (default
`src/lace/blocks.ts`), an optional `definitions` module that exports custom
block definitions, and `items` with registry version and per-file SHA-256
hashes, plus the block map file hash.

Registry item manifests (`item.json`, `schemaVersion` 1) carry `name`,
`framework`, `blockType`, `blockVersion`, `revision`, `requires`, `files`
(`source`, `target` relative to the components directory, `role`), and
`dependencies`. `lace.site.json` (`schemaVersion` 1) stores `framework`,
`componentsDir`, `blockMap`, `blockMapSha256` (`null` until Lace first writes the
map), optional `definitions` (a module path relative to the site root, only
imported, never written), `items` keyed by item name with `revision` and
`files` mapping site-relative paths to SHA-256 hashes (the item `revision` is
the recorded registry version), and optional `customBlocks` keyed by block type
with the `files` scaffolded for configured custom blocks.

The block map file imports definitions and components and exports
`blocks = defineBlockMap({...})`, with imports and entries sorted by block type
after a one-line generated-file comment. Built-in definitions come from
`@lacecms/content`; custom definitions come from the recorded `definitions`
module, which `lace.config.ts` also uses. Definitions are imported, never copied.

`lace add block <type...>` (with `--all`, `--dry-run`, `--json`,
`--site <dir>` defaulting to `site`, `--framework <key>`, and `--write-new`)
resolves item dependencies, writes component files, updates the
map file, checks installed package versions against item ranges, checks
built-in definition versions against `lace.config.ts`, and scaffolds a typed
component for a configured custom block that has no registry item. Ownership
and conflict rules are in section 7.

### 13.6 Framework selection

Registry items, `lace.site.json`, and adapters are keyed by framework. `astro`
is implemented and is the default; `react`, `vue`, and `svelte` are reserved
keys that fail with an explicit "framework not supported yet" error, and their
adapters would be named `@lacecms/react`, `@lacecms/vue`, and `@lacecms/svelte`.
The framework is taken from `lace.site.json`, else `--framework`, else detected
from the site `package.json`, else `astro`. All adapters share the render core.

### 13.7 Typical Astro site files

Loader file (`src/lib/lace.ts`, user-owned):


## 14. Authentication and authorization

Better Auth provides authentication, sessions, account records, and password flows. Its Drizzle SQLite schema is managed alongside the application schema.

The role is stored as a validated field on the Better Auth user record and
defaults to `viewer`; public sign-up is disabled. Only the bootstrap flow and an
administrator with `users:manage` may create users or change roles. Domain and
application code receive an `Actor` value from the auth adapter and do not import
Better Auth session types.

The MVP uses global installation-level roles:

```ts
type Role = "admin" | "editor" | "viewer";
```

Authorization is permission-based internally:

```ts
type Permission =
  | "content:read"
  | "content:write"
  | "content:publish"
  | "media:write"
  | "users:manage"
  | "settings:manage";
```

Default matrix:

| Permission | Admin | Editor | Viewer |
| --- | ---: | ---: | ---: |
| `content:read` | yes | yes | yes |
| `content:write` | yes | yes | no |
| `content:publish` | yes | no | no |
| `media:write` | yes | yes | no |
| `users:manage` | yes | no | no |
| `settings:manage` | yes | no | no |

Handlers must check permissions rather than comparing role strings throughout the codebase.

The first administrator should be created through a one-time bootstrap command or one-time setup token. There must be no hard-coded default password.

The MVP uses a one-time setup token so the flow works identically against local
Node and remote Cloudflare deployments. `lace auth bootstrap` creates a random
token, stores only its hash and expiry, and prints the token once. While setup is
incomplete, `POST /api/v1/setup/admin` accepts that token plus email and password.
It atomically claims the token for a hash of the requested email, creates the
first Better Auth user with the admin role, and then marks setup complete and the
token consumed. A retry with the same token and email resumes safely after an
interruption; a different email cannot take over an existing claim. The endpoint
returns `404` after setup is complete so it does not remain an account-creation
surface. This guarded protocol is used instead of assuming Better Auth user
creation can join an arbitrary D1 transaction.

```text
setup_tokens
├── token_hash          TEXT PRIMARY KEY
├── expires_at          INTEGER NOT NULL
├── created_at          INTEGER NOT NULL
├── claimed_email_hash  TEXT
├── claimed_at          INTEGER
└── consumed_at         INTEGER
```

```text
installation_state
├── singleton_key       INTEGER PRIMARY KEY CHECK(singleton_key = 1)
├── setup_completed_at  INTEGER
└── setup_admin_user_id TEXT
```

Completing setup updates this singleton and consumes all outstanding setup
tokens. `lace auth bootstrap` refuses to mint another token after completion.

Build credentials are stored separately from human users:

```text
api_tokens
├── id                  TEXT PRIMARY KEY
├── name                TEXT NOT NULL
├── token_prefix        TEXT NOT NULL
├── token_hash          TEXT NOT NULL UNIQUE
├── capabilities_json   TEXT NOT NULL
├── created_at          INTEGER NOT NULL
├── last_used_at        INTEGER
└── revoked_at          INTEGER
```

Only the plaintext token is shown at creation. The initial capability set
contains only `content:build:read`.
Setup and API tokens contain 32 cryptographically random bytes encoded as
base64url. Lace stores their SHA-256 digests because the source tokens already
have high entropy; comparisons are constant-time. Human passwords remain wholly
inside Better Auth's password-hashing implementation.

Rate limits use a portable fixed-window SQL projection so behavior does not
depend on one process or Worker isolate:

```text
rate_limit_buckets
├── bucket_key          TEXT PRIMARY KEY
├── window_started_at  INTEGER NOT NULL
├── request_count      INTEGER NOT NULL
└── expires_at          INTEGER NOT NULL
```

The key is an HMAC of operation plus the relevant actor, email, or client IP;
raw IPs and emails are not stored. Defaults are 10 sensitive auth attempts per
15 minutes, 5 setup attempts per hour, 30 upload attempts per minute per actor,
and 20 token-management attempts per hour per admin. Successful requests still
count. Deployments may lower these limits. Expired buckets are removed by the
same scheduled maintenance mechanism as expired idempotency rows.

Security requirements:

- secure, HTTP-only cookies in production;
- CSRF and origin protection according to Better Auth requirements;
- explicit trusted origins;
- rate limiting for authentication and upload endpoints;
- MIME type, file-size, and filename validation for uploads;
- no secrets in generated client bundles;
- same-origin admin and API deployment by default;
- audit-friendly actor IDs on all content mutations;
- the Cloudflare bundle enables the Better Auth compatibility flag required for
  `AsyncLocalStorage`, and its presence is covered by the Cloudflare smoke test.

## 15. Infrastructure ports

Representative application-facing interfaces:

```ts
interface ObjectStorage {
  put(input: PutObjectInput): Promise<StoredObject>;
  get(key: string): Promise<ReadableStream | null>;
  delete(key: string): Promise<void>;
  createReadUrl(key: string, options?: ReadUrlOptions): Promise<string>;
}

interface Cache {
  get<T>(key: string): Promise<T | null>;
  set<T>(key: string, value: T, options?: CacheOptions): Promise<void>;
  delete(key: string): Promise<void>;
}

interface SiteBuildTrigger {
  trigger(input: SiteBuildRequest): Promise<BuildTriggerResult>;
}
```

Implementations:

| Capability | Cloudflare | Node/VPS |
| --- | --- | --- |
| SQL | Drizzle D1 | Drizzle SQLite |
| Object storage | native R2 binding | S3 client configured for MinIO |
| Cache | Workers KV | in-memory or no-op initially |
| API runtime | Cloudflare Worker | Hono Node server |
| Build trigger | Cloudflare deploy hook | authenticated fixed-command builder |
| Recovery dispatch | scheduled Worker | container timer/worker |

R2 and MinIO use different concrete adapters even though both expose S3-compatible concepts. Cloudflare code should prefer the native R2 binding, while Node uses the S3 client against MinIO.

KV is a derived cache, never an authoritative source. The MVP may begin with a no-op cache where caching provides no measured value. Correctness must not depend on immediate KV consistency.

The default MVP configuration uses the no-op cache in both runtimes. A KV cache
adapter may ship as opt-in, but enabling it requires cache-key contract tests and
must not be on the critical path to the first production deployment.

## 16. Database portability and D1 constraints

The MVP supports the SQLite dialect only:

- Cloudflare D1 in production and Cloudflare-compatible development;
- a local SQLite file in Node and Docker.

Drizzle schemas and migrations should stay within the SQL subset supported by both environments.

Important D1 free-plan design constraints include:

- 500 MB maximum size for one free-plan database;
- 2 MB maximum string, BLOB, or row size;
- 50 database queries per free-plan Worker invocation;
- daily row-read and row-write quotas.

The architecture responds to those constraints by:

- placing binary media outside SQL;
- storing one block per row rather than one potentially huge page row;
- loading a snapshot's blocks in one indexed query;
- providing a bulk build-export endpoint;
- avoiding N+1 queries;
- copying blocks with set-based SQL;
- retaining only draft and current published snapshots;
- using focused indexes rather than indexing every field.

JSON values are stored as SQLite `TEXT` and validated before persistence. Fields that later require indexed filtering may be promoted to generated columns or a dedicated index table through a future migration.

## 17. Admin application

The admin is a client-rendered React SPA with no SSR requirement.

Core client stack:

- React;
- Vite;
- TanStack Router;
- TanStack Query;
- React Hook Form;
- Valibot-backed form validation through `@hookform/resolvers/valibot`;
- Tiptap for rich text;
- dnd-kit for accessible block ordering;
- Tailwind CSS utilities over Lace design tokens;
- shadcn/ui components generated on Radix UI primitives as Lace-owned source.

State strategy:

- TanStack Query owns remote/server state.
- TanStack Router owns route and search-parameter state.
- React component state owns transient UI state.
- A separate global state library should not be added until a concrete need appears.

Primary routes:

```text
/login
/content
/content/:modelKey
/content/:modelKey/:entryId
/media
/builds
/users                 admin only
/settings              admin only
```

The content-model response drives navigation and field forms. Pages open their singleton editor directly; collections open a paginated entry list.

The shell groups its sidebar into Pages, Collections (with entry totals from the entry-list API), Library (Media and Builds, all roles), and Admin (Users and Settings, administrators only), shows the signed-in user's display name and role in a user menu, and locates each screen with breadcrumbs. Below the medium breakpoint the same navigation opens in a sheet. Shell surfaces never show internal entry or user IDs. Collection lists are TanStack Table views over the entry-list API: title with slug, derived status, the model's `listFields` columns, publication date, and relative last edit with the editor's display name; search, status filter, and sort live in the route's URL search parameters, while the opaque cursor pages with "Load more" and never enters the URL.

The sign-in route is a centered card outside the shell: a focused email field, a password field with a show/hide toggle, and errors inside the card. Users lists accounts with a "You" marker, role and status badges, and no raw IDs. Creating a user, changing a role, and disabling or enabling an account each happen in a confirmation dialog. A failure, including the final-administrator rule, stays in its dialog, and success is announced with a toast. The signed-in administrator is not offered Disable for their own account and is warned before demoting it. Settings shows API readiness, configured models, and active build tokens as status cards over a token table with relative times and a confirmed Revoke. A new token's plaintext is shown once in its creation dialog and lives only in that dialog's state. Any unmatched admin path is a protected catch-all route that renders "Page not found" inside the shell, so anonymous visitors sign in first. Every retryable read failure offers the shared "Try again" action.

The media library at `/media` follows the same URL-state rules for its filename search, type filter, sort, and grid/list view. Tiles and rows load their thumbnails lazily through the authenticated admin preview endpoint. Writers can drop files anywhere over the library or choose several at once. Each file is checked for type and size in the browser and then uploads with its own progress and server error. The default browser client sends uploads through `XMLHttpRequest` so it can report bytes sent; every other request uses `fetch`, and both paths share error mapping and response validation. A details side panel shows an item's facts, its usage from the media detail read, and its public URL. Deletion there requires confirmation and is unavailable while content uses the item.

Model and block media fields choose through a picker dialog built from the same grid, search, type filter, sort, and upload queue. Its query is local state that resets on each opening and never enters the URL. It offers only active items, and a confirmed upload can be used directly from its queue row. A field with a value shows a thumbnail card with filename, Replace, and Remove. The card resolves the stored ID through the media detail read, so it never searches loaded pages. It names pending-deletion, missing (`NOT_FOUND`), and unreadable items explicitly, and it keeps the ID in the draft until the writer replaces or removes it. The raw ID is never shown.

The editor must make draft/published/build status visible and must surface optimistic-concurrency conflicts rather than overwriting a newer draft.

The shell header stays pinned while a screen scrolls. It gives the screen an actions slot beside the breadcrumbs. The entry editor fills that slot with a save-state indicator (unsaved, saving, not saved, saved revision, or view only), one Save button, and Publish for administrators. Save is bound to the draft form and to `⌘S`/`Ctrl+S`, and the shortcut always suppresses the browser's page save. The title is a large input at the top of the main column, and the blocks follow it. A right-hand column, which stacks after the blocks on narrow screens, holds two cards:

- Publication: the derived status, the live and draft revisions, the last editor's display name, relative times with the absolute time on hover, the public path, and the latest build state. Raw IDs and ISO timestamps never appear.
- Fields: the entry's slug and model fields.

Until the Builds screen reads persisted builds in Step 21, the latest build state is the dispatch result of the most recent publish from the editor. The field controls are built on the shared primitives:

- Select is a Radix listbox.
- Date and datetime use a calendar popover. Datetime adds a time input in UTC, and both parse values textually so days never shift.
- Boolean is a switch.
- URL can open http(s) values in a new tab.

Controls hold a cleared value as `null` in form state, because React Hook Form would show the loaded default again for `undefined`. The editor strips those values before it saves or copies a draft. Viewers see the editor read-only: native controls sit in a disabled fieldset, rich text is not editable, media fields show their item without picker actions, and there is no Save or Publish. Publication is confirmed in a dialog that names the revision and path and can be cancelled. The discard-changes prompt is a modal alert dialog.

Blocks render as cards. A card header shows the following:

- a drag handle;
- the block's icon and label;
- a one-line summary of its data: the first text value, then rich-text plain text, then a URL or select value, then "Media selected", otherwise "Empty block".

Collapsing hides only the fields, so a collapsed card stays recognizable. A block with a validation error stays expanded. The block that focus or a pointer last entered is highlighted. A block that has just been added, inserted, or duplicated is highlighted, expanded, and focused.

Each card's actions menu offers Move up, Move down, Duplicate, and Remove. Removal leaves an inline notice with Undo, which restores the same key and data at the same place. The next structural action makes the removal final.

An insert control between adjacent blocks and an Add block button after the list open the same popover. It lists the model's allowed blocks with icon, label, and description, and it has a text filter.

Keyboard and pointer drag reordering stay on dnd-kit. The screen-reader announcements name blocks by label and position, never by key.

Each editable rich-text field has a fixed toolbar named after the field. It holds the following controls:

- a text style menu (Paragraph, Heading 1–3);
- Bold, Italic, Strike, and Code toggles;
- Bulleted list, Numbered list, and Quote toggles;
- a Link control.

The toggles report their pressed state for the selection. The toolbar is one tab stop with arrow-key movement, `Alt+F10` moves focus from the text to it, and Escape returns. Tooltips and `aria-keyshortcuts` name each shortcut. The editor adds undo and redo and keeps Tiptap's mark, list, heading, and Markdown shortcuts. `⌘K`/`Ctrl+K` opens the link popover, which applies only URLs that pass the shared allowlist and says which forms are permitted. The Tiptap schema declares only allowlisted attributes: links carry `href` and lists carry nothing. Every document the editor produces therefore passes the shared validator. Empty fields show a placeholder, also exposed as `aria-placeholder`. Viewers get neither the toolbar nor the placeholder.

Validation problems appear where they occur. Field messages are sentences such as "Enter at least 5 characters." A block card shows its block-level problems and a "Has problems" marker: a type that is not allowed, a stale version, a key problem, or data for an undefined field. A block whose type the model no longer allows still renders, so it can be removed. When Save is blocked, or the server rejects a save or publish, a summary above the title takes focus. It counts the problems and links each one, in reading order, to its control or block card. The admin maps server JSON Pointers, including deep rich-text paths, to the same locations. Issues it cannot place are listed as text.

### Component source and design tokens

Admin UI components are Lace-owned source. shadcn/ui is used as a generator:
its Radix-based components are copied into the admin source once and then
edited like any other Lace code; no themed component library is a runtime
dependency. See [ADR 0005](adr/0005-admin-owned-component-source.md).

Design tokens are CSS custom properties in the shadcn naming convention
(`background`, `foreground`, `primary`, `muted`, `border`, `ring`, the
`sidebar` family, and Lace `success`/`warning` pairs) plus typography,
spacing, radius, shadow, focus, and motion tokens. One theme file in the admin
source is the only place that may contain color values; Tailwind's default
color palette is removed and components are styled only through utilities that
resolve to tokens. `pnpm lint` rejects raw color literals elsewhere in admin
source, and arbitrary utility values that stand in for a typography, radius,
shadow, focus-width, or motion token. Layout values such as widths and grid
tracks may stay arbitrary.

### Accessibility acceptance

Every admin route and main dialog is audited in the browser with axe against
the WCAG 2.x A and AA rules, and any violation fails the suite. No rule is
disabled globally. The same browser suite completes the main editorial flow
with the keyboard alone, checks visible focus along it, and checks 375px
layouts, including the entry column stacking below the blocks. The local
product acceptance walkthrough repeats the audits on real data.

The MVP ships the light theme only. Token values are scoped by a `data-theme`
selector on the document root so a dark theme can be added later by supplying
alternative values, without component changes. Inter is self-hosted and body
text uses a 13px base size.

### Source layers

Admin source is organized into layers with a single import direction:

```text
app → pages → widgets → features → entities → shared
```

- `app` owns bootstrap, providers, the router tree, and global styles.
- `pages` holds one slice per route screen.
- `widgets` holds composite screen sections such as the shell or an entry list.
- `features` holds user actions such as publish, upload, or sign in.
- `entities` holds domain-facing models, queries, and presentation of content,
  media, users, and sessions.
- `shared` holds the API client, generic UI primitives, utilities, and
  configuration with no knowledge of Lace domain slices.

A module may import only from layers to its right. Slices within the same
layer do not import each other. Every slice exposes its public API only through
its `index.ts`; imports into a slice's internal files are forbidden. Every
React component lives in its own PascalCase folder containing the component,
its test, and an `index.ts`; code outside that folder imports it only through
its `index.ts`.

- `pages`, `widgets`, `features`, and `entities` are divided into slices
  (`pages/<route>`, `widgets/<section>`, …). `app` and `shared` are not sliced;
  their public units are the shallowest directories that carry an `index.ts`
  (for example `app/router`, `shared/api`, `shared/lib`, `shared/ui/Button`),
  and units of the same unsliced layer may import each other through those
  indexes.
- The source-root entry module (`main.tsx`) may import any layer's public API,
  and `test/` holds only test-environment setup. No other admin source lives
  outside the layers.
- Test files may import any layer's public API, including higher layers, so a
  page or widget test can mount the real router through the `app` test
  harness. They still may not import another unit's internal files.
- Router state is read below `app` through TanStack Router `getRouteApi` with
  string route ids typed by the `Register` augmentation in `app/router`, so no
  runtime import points upward.
- Imports are relative with explicit `.js` extensions; the admin uses no path
  aliases.

Layer direction, slice and component-folder public APIs, and component folder
completeness are enforced by `scripts/check-boundaries.mjs`, run by
`pnpm lint`.

## 22. Migration and compatibility policy

Compatibility exists at three boundaries:

1. Database schema version.
2. `lace.config.ts` API version.
3. REST/build-export contract version.

Database changes use forward migrations. The MVP does not promise automatic downgrade support.

Content blocks and field objects carry `schema_version`. A block registry may migrate old JSON data when loaded or through an explicit content migration. Silent destructive conversion is forbidden.

Public REST endpoints remain under `/api/v1` until a breaking contract requires `/api/v2`. Internal TypeScript types alone are not a compatibility contract.

## 24. Decisions captured by this document

- One Lace installation manages one site.
- Astro generates the public static site.
- Hono exposes a versioned REST API.
- Valibot is the canonical runtime schema library for REST contracts, configuration, content, blocks, and admin forms.
- Hono integrates with schemas through Standard Schema validation, and OpenAPI is derived through the Valibot JSON Schema conversion path.
- The admin is a React/Vite SPA using TanStack Router and TanStack Query.
- Admin UI components are shadcn/ui-generated, Lace-owned source styled only through design tokens, organized in the `app → pages → widgets → features → entities → shared` layers.
- Drizzle uses the SQLite dialect for both D1 and VPS SQLite.
- Better Auth provides authentication.
- Authorization uses admin, editor, and viewer roles mapped to permissions.
- Only admin has `content:publish` by default.
- Tiptap is used for rich-text fields/blocks, not as the entire page document.
- `content_models.kind` distinguishes `page` from `collection`.
- Pages and collection records share `content_entries`.
- Content has draft and published snapshots only.
- Blocks are separate relational rows with type-specific JSON payloads.
- Top-level blocks are flat and sparsely ordered.
- Content models are defined in code and projected into the database.
- Node uses SQLite and MinIO; Cloudflare uses D1 and R2.
- Infrastructure-specific behavior is implemented through narrow capability adapters.
- Publishing writes an outbox event and triggers a static rebuild.
- The supported onboarding path is a generator for a new/empty project.
- The user's Astro site is not overwritten during Lace upgrades.
- Site loading, block parsing, and rich-text safety are packaged
  (`@lacecms/sdk`, `@lacecms/render`) and rendered through a thin framework
  adapter (`@lacecms/astro`); visual block markup is never a runtime package and
  is installed as user-owned source by `lace add block` from a versioned,
  framework-keyed registry.
- The generated starter site is optional; projects may connect an existing
  Astro site or run without a site.
- Implementation changes follow the repository-local OpenSpec workflow.
- Oxlint and Oxfmt are the linting and formatting toolchain.

## 25. Planning defaults and remaining release decisions

The implementation plan uses these resolved defaults:

- pnpm workspaces plus Turborepo;
- `better-sqlite3` for the Node adapter;
- Tailwind CSS over Lace design tokens and shadcn/ui-generated, Lace-owned
  admin components on Radix UI primitives;
- the `hero`, `richText`, `image`, `quote`, and `cta` built-in blocks;
- no reference fields in the MVP;
- no-op cache by default and optional KV only after the uncached path is correct;
- a first-party fixed-command VPS builder rather than an arbitrary command or
  external CI dependency;
- owner-confirmed public npm organization/scope `@lacecms/*` and generator
  name `create-lace` (unscoped availability must be rechecked before publication);
- GHCR organization `lacecms`, with `ghcr.io/lacecms/api` and
  `ghcr.io/lacecms/builder`;
- experimental package/image version `0.1.0-alpha.1`, npm channel `next`, and
  independent ownership template version `0.4.0`; see
  [`alpha-release.md`](./alpha-release.md) for preparation and owner publication.

The following choices are release and operations work, not blockers for the
first local vertical slices:

- rechecking availability/publishing rights for the unscoped generator name
  immediately before first publication;
- selecting the signing/provenance process for published artifacts;
- defining hosted release channels and update metadata for `create-lace`;
- selecting the reference Cloudflare static-hosting project and CI provider used
  by deployment documentation.

If package-name ownership differs, only published names and generator templates
change; internal package boundaries and domain contracts remain the same.
