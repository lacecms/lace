# Lace CMS alpha.2: результаты ручного тестирования

Дата: 2026-10-04. Сценарий: подключение опубликованной `0.1.0-alpha.2` к существующему Astro-проекту через `create-lace create cms --existing-site .. --cloudflare`, запуск Docker Compose на OrbStack.

Это список выявленных проблем для будущего исправления в Lace. Изменения продукта пока не выполнялись. Локальные обходы не считаются исправлениями.

Состояние на 2026-10-06 (33H): пункты 1–6 и общее требование к диагностике исправлены в сессиях 33A–33G и доказаны регрессиями против точных артефактов-кандидатов `0.1.0-alpha.3` (шаблон `0.17.0`); соответствие пунктов доказательствам — в [alpha-2-feedback-acceptance.md](alpha-2-feedback-acceptance.md). Повторная проверка пунктов 3–5 в реальном Cloudflare-аккаунте и публикация кандидата — отдельные действия владельца (вход в 34C). Текст ниже сохранён как исходный журнал наблюдений.

## 1. Сохранение после перестановки блоков возвращает 422

Статус: подтверждено на опубликованной alpha.2.

Воспроизведение:

1. Открыть Home, добавить несколько блоков.
2. Переставить блоки местами.
3. Сохранить черновик.

Наблюдение: редактор меняет порядок массива, но не пересчитывает `position`. Фактический запрос содержал image с позицией 2048, richText с позицией 1024 и cta с позицией 3072. `PUT /api/v1/admin/entries/:id/draft` вернул 422 с кодом `CONTENT_INVALID_STATE`. Request ID для воспроизведения: `01M44C1XSD1AEBAN1B05SZ8808`.

Причина по коду: `BlockEditor.tsx` перемещает элементы без изменения позиций. Вставка и дублирование в середине списка также могут нарушать порядок: новый блок получает максимальную позицию плюс 1024. `ContentUseCases.validateDraft` вызывает `assertOrderedBlockPositions`, требующий положительных, строго возрастающих позиций.

Что исправить:

- Обеспечить корректные позиции при сохранении текущего порядка блоков, сохраняя стабильные `key` и содержимое.
- Проверить перестановку мышью и клавиатурой, вставку и дублирование в середине списка, удаление и отмену удаления.
- При отказе показывать понятную причину и действие для восстановления, сохранять несохранённые данные пользователя.

Критерии проверки: после перечисленных операций Save успешно сохраняет порядок; после перезагрузки и публикации порядок остаётся тем же. Некорректный запрос получает безопасную диагностическую информацию о проблеме порядка блоков.

Временный обход: вручную исправить позиции запроса на 1024, 2048, 3072 по текущему порядку либо добавлять блоки в нужном порядке без перестановки.

## 2. Compose builder отклоняет служебную символическую ссылку

Статус: причина подтверждена проверкой исходников внутри контейнера. Пользователь подтвердил успешную публикацию сайта через production Docker Compose после обхода.

Настройки существующего сайта: `LACE_BUILD_SOURCE_ROOT=..`, `LACE_BUILD_SITE_DIR=.`, `LACE_BUILD_OUTPUT_DIR=dist`. Исходники репозитория монтируются в builder как `/source`.

Воспроизведение: в корне Astro-проекта имеется служебная ссылка `CLAUDE.md -> AGENTS.md`; запустить полный Compose и запросить сборку из Admin.

Наблюдение: Builds показывает `Failed — provider failed`. Dispatcher пишет `reason: provider_failed`, builder — `reason: source_invalid`. Build ID: `d33eaa7c-fb33-4e5d-8a60-6ffa00fd0210`. Ни интерфейс, ни эти логи не называют проблемный файл.

Причина по коду: `copySource` в `apps/builder/src/source.ts` допускает только обычные файлы и каталоги, не исключает `CLAUDE.md` и отклоняет ссылку. Проверка по тем же правилам внутри контейнера нашла единственный неподдерживаемый элемент: `CLAUDE.md`.

Что исправить:

- Определить поддерживаемое поведение для служебных ссылок, не нужных для Astro-сборки: например, исключать их из копирования. Не обходить ограничение бесконтрольным следованием ссылкам за пределы исходников.
- Сохранить диагностику конкретной причины и безопасного относительного пути от builder до истории сборки и Admin; общий `provider_failed` не должен скрывать известную причину.
- Давать оператору понятное действие: какой файл не поддерживается и как исправить структуру исходников.
- Проверить служебную ссылку, ссылку в исходниках сайта, недоступный путь и отсутствие обязательных файлов. Убедиться, что неудачная сборка сохраняет предыдущий рабочий релиз.

Временный обход: после проверки ссылки заменить `CLAUDE.md` обычной копией `AGENTS.md` и повторить сборку.

## 3. D1-токен из `.env` незаметно заменяет OAuth-авторизацию Wrangler

Дата: 2026-10-05. Статус: пользователь подтвердил причину отказа при деплое в реальный Cloudflare-аккаунт.

Воспроизведение:

1. Войти через `pnpm exec wrangler login` и подготовить Worker, D1 и R2.
2. По инструкции записать `CLOUDFLARE_ACCOUNT_ID` и `CLOUDFLARE_API_TOKEN` с правами D1 Edit в `cms/.env` для remote-команд Lace.
3. Успешно выполнить remote migration и content sync.
4. Из `cms/` выполнить `pnpm exec wrangler deploy --config worker/wrangler.jsonc`.

Наблюдение: Wrangler начинает использовать API token вместо сохранённого OAuth-входа. Токен с правами только на D1 не даёт доступа к Worker. Деплой возвращает `No access to the specified service` для `workers/services/lace-cms-test`, без понятного объяснения смены способа авторизации. Пользователь предположил, что проблема связана с `LACE_AUTH_SECRET`, хотя это секрет приложения, не авторизация Cloudflare CLI.

Причина: установленный Wrangler 4.129.0 автоматически загружает `.env` и `.env.local` из текущего каталога и использует `CLOUDFLARE_API_TOKEN`. Инструкция Lace рекомендует один `.env` для нескольких инструментов, но не объясняет этот конфликт. Предыдущая рекомендация использовать D1-only token для Lace и одновременно OAuth для обычных команд Wrangler была неполной.

Проверенный по коду установленного Wrangler способ явно исключить загрузку `.env` для отдельной команды на macOS/Linux (команды здесь не выполнялись):

```bash
# Из cms/: убрать token из окружения и загрузить пустой файл вместо default .env.
env -u CLOUDFLARE_API_TOKEN pnpm exec wrangler whoami --env-file /dev/null
env -u CLOUDFLARE_API_TOKEN pnpm exec wrangler deploy --config worker/wrangler.jsonc --env-file /dev/null
```

Это позволяет использовать сохранённый OAuth-вход, если нет других настроенных способов авторизации. Перед деплоем подтвердить аккаунт через `whoami`. Простого `unset CLOUDFLARE_API_TOKEN` недостаточно, если Wrangler снова загружает его из `.env`. Значения секретов не нужно выводить или передавать в аргументах команд.

Что исправить:

- Сделать выбор авторизации явным в onboarding: либо единый API token с необходимыми правами, либо раздельные настройки operator CLI и OAuth-команд Wrangler.
- Для OAuth-сценария исключить неявную загрузку D1-only token при deploy, secret put и других аккаунтных командах. Предпочтительно использовать отдельный приватный env-файл для Lace remote-команд и явно передавать его, а не заставлять пользователя каждый раз обходить конфликт.
- Добавить проверку активного метода авторизации и выбранного аккаунта перед деплоем, с безопасным объяснением недостаточных прав. Не требовать широких разрешений только ради удобства.
- Объяснить различие `LACE_AUTH_SECRET`, Cloudflare API token и OAuth Wrangler; показать, какие настройки локальные, а какие сохраняются у Worker.
- Проверить последовательность login → D1-only operator token → migrate/sync → deploy, включая токен в shell environment и `.env.local`. Убедиться, что документация не рекомендует обход, который повторно загружает тот же токен.

Критерии проверки: пользователь может пройти весь documented onboarding без неожиданной смены авторизации; недостаточные разрешения диагностируются с понятным следующим действием, без раскрытия токена. Remote migration/sync и deploy направляются в явно выбранный аккаунт.

Источники: [Wrangler system environment variables](https://developers.cloudflare.com/workers/wrangler/system-environment-variables/), локальный код Wrangler 4.129.0 (`getDefaultEnvFiles`, обработка `--env-file`, `loadDotEnv`).

## 4. Astro-сборка в Cloudflare Pages падает при проверке ETag

Дата: 2026-10-05. Статус: ошибка подтверждена на опубликованной alpha.2; после временного обхода сборка Pages прошла успешно, сайт открывается с опубликованными данными CMS.

Воспроизведение:

1. Развернуть CMS Worker в Cloudflare, опубликовать Home и создать build token.
2. Настроить Astro-сайт в Cloudflare Pages с URL Worker и build token.
3. Запустить `pnpm build` с обычным `createAstroSiteLoader` без переопределения `fetch`.

Наблюдение: при prerender `/index.html` SDK `@lacecms/sdk@0.1.0-alpha.2` выбрасывает `LaceContractError: The build-export response has an invalid ETag.` в `parseResponseEtag`. Сообщение не показывает полученный заголовок и не предлагает действие для восстановления.

Причина по коду: общий контракт принимает только ETag вида `"2"` (`/^"[0-9]+"$/`), тогда как корректный HTTP weak ETag `W/"2"` отвергается. Cloudflare может преобразовать strong ETag в weak при сжатии ответа. На установленном SDK ответ с `W/"1"` воспроизвёл ту же ошибку. Фактический ETag первоначального неудачного запроса не записан, поэтому преобразование заголовка Cloudflare остаётся вероятной причиной, а не непосредственно измеренным фактом.

Проверенный временный обход: в `src/lib/lace.ts` передать собственный `fetch` в `createAstroSiteLoader`, сохраняя параметры запроса и устанавливая `Accept-Encoding: identity`:

```ts
fetch: async (url, init) => {
  const headers = new Headers(init.headers);
  headers.set("Accept-Encoding", "identity");
  return fetch(url, { ...init, headers });
},
```

После обхода лог сборки показал `[lace build-export] { status: 200, etag: '"2"', encoding: null }`. Пользователь подтвердил успешную сборку и доступность сайта с данными CMS. Обход не является исправлением Lace; диагностический `console.info` можно удалить.

Что исправить:

- Поддержать strong и weak version-derived ETag в SDK и API, согласованно обрабатывая `If-None-Match`, сравнение версии и ответы 200/304. Не принимать произвольные или некорректные значения вместо проверки контракта.
- Обеспечить работу стандартного `createAstroSiteLoader` через Cloudflare без пользовательского обхода сжатия.
- В ошибке указывать безопасное полученное значение ETag, ожидаемый формат и понятное следующее действие; различать отсутствующий и некорректный заголовок, не раскрывать токен или содержимое экспорта.
- Добавить регрессионные проверки strong/weak ETag, некорректных заголовков, условных запросов и повторного чтения после публикации; проверить реальную сборку Pages со стандартным согласованием сжатия.

Критерии проверки: Astro-сборка успешно читает build-export с strong и weak ETag; повторный запрос без изменений корректно обрабатывает 304, а после публикации получает новый экспорт. Неподдерживаемый заголовок даёт полезную безопасную диагностику.

Источник: [Using ETag Headers with Cloudflare](https://developers.cloudflare.com/cache/reference/etag-headers/); локальные `packages/contracts/src/index.ts`, `packages/sdk/src/client.ts`, `packages/server/src/app.ts` в репозитории Lace.

## 5. Cloudflare-сборки остаются в Admin со статусом Running

Дата: 2026-10-05. Статус: пользователь подтвердил зависший Running при работе через Cloudflare; завершение сборки и доступность сайта проверяются отдельно в Pages.

Воспроизведение: настроить Pages deploy hook у CMS Worker, опубликовать контент или запросить сборку из Admin, дождаться завершения deployment в Pages и проверить историю Builds в CMS.

Наблюдение: запись остаётся Running, хотя внешняя сборка уже завершилась. Пользователь не может определить из Admin, опубликован ли сайт или произошла ошибка сборки.

Причина по коду: `DeployHookSiteBuildTrigger` выполняет POST к hook и возвращает `accepted` с ID deployment. Dispatcher сохраняет `providerBuildId` и переводит запись в Running, но текущий Cloudflare runtime не отслеживает дальнейший результат Pages. Это ограничение уже описано в сгенерированной operations-документации, однако интерфейс не объясняет, что статус означает только принятие запроса провайдером. Дополнительный дефект: успешный HTTP-ответ hook без ID трактуется адаптером как `succeeded`, хотя такой ответ также не доказывает завершение сборки и деплоя.

Предлагаемое направление исправления (требует отдельного проектирования):

- Для Cloudflare Pages добавить отслеживание конкретного deployment по сохранённому `providerBuildId`: периодически запрашивать Pages API из существующего scheduled Worker, сохраняя состояние между запусками. Понадобятся account ID, project name и отдельный Worker secret с минимальным правом Pages Read; не смешивать его с D1 operator token.
- Отмечать успех только после успешной стадии deploy, а не после принятия hook или завершения стадии build. Отражать отказ, отмену и пропуск согласно согласованной модели состояний; показывать этап, время последней проверки и ссылку на соответствующий deployment.
- Ограничить число проверок за запуск, использовать повторы с задержкой при временных сбоях API и предусмотреть восстановление после рестарта Worker. Недоступность проверки и истечение срока ожидания не должны выдаваться за доказанный провал внешней сборки или приводить к бесконечному Running.
- Сопоставлять результат с точной сборкой, не с последним deployment проекта: параллельные сборки, повторы и поздние результаты не должны менять другую запись. Обновления завершения должны быть идемпотентными.
- Для универсального deploy hook без API отслеживания честно показывать «Запрос принят, результат не отслеживается» вместо бессрочного Running или ложного Succeeded. Альтернатива — аутентифицированный callback от CI после деплоя; одного callback после `pnpm build` недостаточно для подтверждения публикации сайта.
- В диагностике показывать безопасную причину и следующий шаг, не раскрывая hook URL, API token и полный ответ Pages API, который может содержать настройки окружения.

Критерии проверки: успешный deployment переводит соответствующую запись в Succeeded, неудачный — в Failed с полезной причиной. Проверить ошибку Astro-сборки, ошибку деплоя, отмену/пропуск, временную недоступность API, недостаточные права, параллельные сборки, восстановление Worker и hook без deployment ID. Старые зависшие записи должны иметь понятный путь сверки или статус неизвестного результата.

Временная практика: проверять фактический результат в Cloudflare Pages; Running в текущей alpha.2 не подтверждает, что сборка продолжает выполняться.

Источники: [Pages deployment status API](https://developers.cloudflare.com/api/resources/pages/subresources/projects/subresources/deployments/methods/get/), [Pages Deploy Hooks](https://developers.cloudflare.com/pages/configuration/deploy-hooks/); локальные `packages/platform-cloudflare/src/deploy-hook.ts`, `packages/application/src/dispatchers.ts`, `packages/platform-cloudflare/src/worker.ts` и сгенерированная operations-документация.

## 6. README смешивает сценарии запуска; требования Node.js/pnpm ограничены сверху

Дата: 2026-10-05. Статус: замечание пользователя по итогам полного прохождения Docker dev → Docker production → реальный Cloudflare. Требуется улучшение документации и политики совместимости; изменения в README, настройках и продукте пока не выполняются.

Что есть сейчас:

- `cms/README.md` объединяет установку, подготовку SQLite, настройку администратора, подключение существующего Astro-сайта, dev, production builder и локальный Cloudflare. Production описан внутри подключения сайта, а реальный Cloudflare вынесен в раздел большого `cms/docs/lace-operations.md`.
- `cms/docs/lace-astro-site.md` уже содержит отдельную инструкцию подключения Astro. `cms/docs/lace-operations.md` содержит подробную диагностику, восстановление и выбор исходников; эти справочники полезны и должны оставаться доступными из сценарных руководств.
- Корневой `README.md` остаётся стандартным Astro starter README и не направляет пользователя к инструкциям CMS.
- В `cms/package.json` стоят `engines.node: ">=24.12.0 <25"` и `engines.pnpm: ">=12 <13"`. Те же границы присутствуют в шаблоне генератора `packages/create-lace/templates/package.json` и документации; они также заданы в корневом `package.json` репозитория Lace.
- У Astro-сайта в этом репозитории Node.js уже ограничен только снизу: `>=22.12.0`. Выбранная версия `packageManager: pnpm@12.3.4` и `.nvmrc` — отдельный вопрос воспроизводимости, который не следует смешивать с допустимым диапазоном `engines`.

Предлагаемая структура документации:

1. Короткий CMS README с требованиями, описанием расположения CMS/сайта и ссылками на сценарии.
2. Отдельный файл Docker Compose dev: первоначальная подготовка, миграции/sync/bootstrap при остановленных пользователях базы, Admin, build token, подключение и фоновый запуск Astro dev, проверка публикации и остановка. Это первый путь, который проходил пользователь.
3. Отдельный файл Docker Compose production: переход из dev, выбор Astro-исходников, lockfile и build token, полный стек, Request build/Publish, проверка опубликованного сайта, диагностика, сохранение данных и остановка.
4. Отдельный файл Cloudflare с последовательными разделами локального запуска и реального аккаунта: локальное состояние и secrets, D1/R2, явный выбор OAuth/API token, remote migration/sync/bootstrap, URL и деплой Worker, отдельная сборка Astro в Pages, deploy hook и проверка результата публикации.

Что исправить:

- В каждом руководстве указывать рабочую директорию команд, предварительные условия, ожидаемый результат и следующий шаг. Объяснить, какие действия выполняются один раз и какие нужны при повторном запуске; различать CMS Worker и статический сайт, локальные и удалённые данные, настройки CMS и Astro.
- Включить найденные в этом прохождении проблемы: конфликт Wrangler OAuth с D1 token из `.env`, ETag в Pages, ограничение статуса Running и диагностику builder. Не выдавать временные обходы за исправления продукта.
- Ограничивать Node.js и pnpm только минимальной поддерживаемой версией: для текущих CMS-требований предложены `>=24.12.0` и `>=12`, без `<25` и `<13`. Удалить необоснованные верхние ограничения согласованно из генерируемых проектов, документации и связанных проверок совместимости; отдельно проверить требования самого engine и опубликованных пакетов.
- Разделить минимальные требования и конкретные версии, выбранные для CI, Docker-образов, lockfile и `packageManager`.
