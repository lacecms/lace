# Local operations verification (34C)

Run `pnpm verify:34c` from the engine repository with Node 24.12.0, pnpm 12.3.4, Docker and the installed workspace. It rejects remote account/provider credentials. Each execution writes phase results and sanitized provenance under a new `.lace-acceptance/step-34c-results-*` directory. Required tests cannot be empty, skipped or unavailable; failures mark later phases not-run. Temporary databases, object volumes, persistence roots and listeners belong to that execution and are removed after success/failure/interruption. Backups and plaintext credentials are never committed.

The runner builds the workspace, checks guide extraction, executes generated Node and Cloudflare-local setup journeys, tests both real persistence adapters, and exercises forward migrations and managed-file upgrade/rollback. The exact-artifact release acceptance separately executes the generated scenario commands and uses installed tarball platform exports for these restoration/rotation tests. Its Astro restore checks use the repository reference site; generated starter and independent user-owned Astro builds are covered separately by the full exact-artifact consumer journey. This distinction prevents claiming that the reference-site drill is a generated-site restore.

## Observations and limitations

Administrator Settings shows the platform's generated release literal, not the root project/template version. The bounded required `engineVersion` status field is administrator-only. Update API, contracts and admin coherently. Tests cover refresh, stale/unavailable values and session expiration. No public diagnostic endpoint is added.

Liveness proves that the listener responds. Readiness checks migration-ledger availability; it does not prove config synchronization, object access or a successful static deployment. Invalid configuration can reject startup before either endpoint exists. Request-completion logs provide request ID, method, path, status, duration and resolved actor ID. They are not a complete content audit trail; architecture §21 entry/model/publication context remains an observability gap. Doctor is a read-only setup probe and cannot inspect a running WAL database. With SQLite consumers stopped, its `migrations` check confirms the existing ledger contains every packaged migration; `content:sync --check` separately compares configuration projection/hashes. Local Worker doctor derives readiness through the running API rather than independently inspecting D1. Use the running health endpoints plus explicit config/object/build observations.

`tests/operations.acceptance.mjs` seeds roles, draft/published differences, ordered blocks, routes, references and media. It compares canonical SQL fingerprints and all referenced object checksums after coordinated restore, then signs in, downloads media and builds Astro twice. Missing/corrupt objects fail acceptance. Original installation identity, credentials and data remain independent. SQLite uses the backup API plus paginated MinIO object API copies; the Worker drill stops Miniflare and captures complete local D1/R2 persistence, recording simulator version. Both paths rotate auth secrets and read-only build tokens. Node rotates real MinIO credentials while retaining its data volume; builder shared-secret and hook/Pages replacement use controlled adapters. Existing builder/release journeys verify failure preserves the last complete served release and corrected retry replaces it.

Generated [operations guidance](../packages/create-lace/templates/docs/lace-operations.md#operator-observation-and-recovery) defines the observation checklist, downtime, private backup handling, restore validation, rotation and upgrade recovery. Scenario setup commands are extracted by `scripts/consumer-guides.mjs` and executed by generated-consumer acceptance. Forward migration/upgrade tests cover dry-run, apply, conflict, interruption and filesystem rollback without overwriting user-owned config, Astro, README or edited blocks. Filesystem rollback does not roll back SQL or objects.
